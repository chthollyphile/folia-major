# Development Workflow

一次改动从开工到交付的标准流程。每次修改都自检；独立审查以一个 PR 或一个完整功能为单位，在收尾时做：交给一个独立的子代理审查，逐条核实它的结论，修掉成立的，必要时再审一轮，最多连续两轮。

## 什么时候审查

### 审查的单位

- 审查以一个 PR 或一个完整的功能（含一个独立的修复）为单位，在它做完、准备交付时审一次：开 PR 前，合进 main 前，或者没有 PR 时向用户报告“做完了”之前。
- 做的过程中的中间提交、反复调整、按用户反馈的小改，每次只做第 3 步的自检，不单独审查。交付这些中间改动时写一句“独立审查在功能收尾时做”。
- 范围是整个 PR 或功能相对基点的全部改动，不是最后一次修改。
- 审过的 PR 或功能之后又追加改动（用户反馈、补需求）：不每改一次就审一次。到下一个交付点（例如要合并）时，看上次审查以来累积的改动：整体够得上下面的完整流程就再审，范围只看这部分，重新计轮；够不上的按简单修复处理，在交付里写明。

### 哪些不审

除了下面列出的几种，改了仓库里的代码（含测试、脚本、构建和 workflow 配置）的 PR 或功能都走完整流程，包括审查。按整个 PR 或功能判断，不按其中单次修改判断。

不走这个流程的：

- 文档类：README、`docs/`、skill 的说明文字、注释。
- 文案类：界面文字、i18n 词条、日志措辞。只改字面文字；日志行里新增插值的变量不算文案。
- 简单修复：改动小到一眼能看全（大致一个文件、十来行以内），只影响一处行为，而且不碰下面任何一项：
  - 异步时序、并发、切歌；
  - 持久化（存储键、数据库、同步）；
  - 模块边界、主进程 IPC、窗口安全设置（`contextIsolation` 等）；
  - 在线歌曲和平台的 provider、transport；
  - 依赖和版本号；
  - 生成的文件；
  - 凭据、日志里记下的内容；
  - 热路径（每帧回调、动画帧、监听器，`frontend-runtime-guardrails` 管的范围）。

  例如改错一个比较符、调一个不在热路径上的样式值。拿不准算不算简单，就按完整流程走。
- 发版准备：按 `prepare-folia-release` 改版本号、新功能介绍和 release note，照那个 skill 自己的流程走。发版前顺手修的代码不算发版准备，照常判断。
- 用户只问原因、不要改动。

不走流程的改动照常按 `testing-strategy` 做必要的验证，动了代码的至少跑 `npm run typecheck`。交付时写一句“未做独立审查：按简单修复（或文案、文档）处理”，附一句理由，让用户能看出分类对不对。

## 1. 开工

1. 按 `AGENTS.md` 挑出这次真正相关的 skill 读一遍，不相关的不读。
2. 用 `codebase-navigation` 的顺序定位代码；口头说法先按 `glossary-alignment` 换成符号名。
3. 动手前想清楚改动落在哪（`file-modularization`）、要守哪些边界（依赖方向、omni、i18n、存储键）。需求里有拿不准、且答案会改变做法的地方，先问用户。

## 2. 实现

按 `AGENTS.md` 的开发规范写。只做这次要做的事，顺手看到的别的问题记下来，交付时报告，不混进这次改动。

## 3. 自检

审查之前先把自己能查出来的问题查掉，别让子代理替你跑类型检查：

- `npm run typecheck`。
- 按 `testing-strategy` 选验证方式：逻辑改动跑相关的单测，该加测试的加上；界面改动看热加载的开发服务器或浏览器预览；主进程和 IPC 改动按 `run-desktop` 在真桌面版里看。
- 自己读一遍完整改动：`git diff <基点>` 看已跟踪文件（含未提交的部分）；它不列未跟踪的新文件，用 `git status --short` 找出 `??` 开头的逐个打开读。看有没有调试残留、漏掉的 i18n 语言文件、没清理的监听器和 `requestAnimationFrame`、改了名的存储键。

## 4. 独立审查（PR 或功能收尾时）

### 派谁

- 新开一个子代理（不要用 fork：fork 带着你的整段对话，看不出你自己的盲点）。用推理强度高的通用代理，例如本机 `.claude/agents/` 里的 `opus-high`；改动大或涉及并发、时序、持久化时用更高一档。
- 审查者只读：不改文件、不提交、不切分支、不删任何未跟踪的文件或目录。可以跑只读命令（`git diff`/`status`/`log`/`show`、`rg`、`ls`、读文件）；npm 脚本只跑 `npm run typecheck` 和 `npm run test:unit`，不跑 `test:ui`（截图测试缺基线时会写文件）。单测遇到新的快照断言也会写文件：跑完用 `git status --short` 看一眼，多出来的文件不要删，在报告里说明。
- 你自己是被派来做改动的子代理时（不论整个还是一部分），不开审查，在交回的报告里写明“未做独立审查，交由派发方按 development-workflow 审查”，由派你的一方统一审。
- 没有办法派独立子代理时（工具里没有），不要自己扮演审查者走过场：交付时写明“未做独立审查：没有子代理可用”，问用户要不要另行安排。

### 给它什么

简报写清楚下面几项，自己组织语言，不要把你的实现思路和“为什么这样是对的”塞进去，那会把审查者带到你的结论上：

1. **目标**：用户要的是什么，尽量用用户的原话。
2. **范围**：基点和要看的改动（如 `git diff main...HEAD` 加工作区未提交的改动，新文件列出路径）。
3. **你已经验证过的**：跑了哪些命令、结果如何，以及没验证到的部分。
4. **对照的规则**：`AGENTS.md` 和这次相关的 skill 名字，让它自己去读。
5. **严重度标准**：把下面“严重度”一节原样给它。
6. **输出格式**：每条一项，包含严重度、`文件:行`、一句话说明问题、具体的触发场景（什么输入或状态 → 出什么错）、证据（引用的代码或跑出来的结果）。没有问题就明确说没有。按严重度从高到低排。

### 严重度

- **高**：数据丢失或损坏、崩溃或白屏、主流程（播放、登录、资料库）用不了、凭据进日志或出现在界面上、已发布的存储键被改名、安全问题。
- **中**：某个具体场景下行为错误（边界条件、竞态、平台或系统差异、切歌和异步时序）；违反 `AGENTS.md`“开发规范”里任何一条“不……”“只……”的规定，例如依赖方向、在线歌曲绕过 omni、在 `App.tsx` 里加分支、不用项目控件或 lucide 以外的图标、界面文字没走 i18n 或缺语言文件、新设置没接导入导出或命令面板、改或删 `@note` 注释、手改生成的文件、音乐平台库没钉版本（这些只是例子，不是全部）；热路径上的性能回退（见 `frontend-runtime-guardrails`）；监听器、定时器、动画帧、GPU 资源没释放；`testing-strategy` 要求加测试却没加。
- **低**：不涉及 `AGENTS.md` 规定的命名、注释措辞、可读性、可以更简单的写法、不影响行为的风格问题。

拿不准时，问“用的人会不会碰到、碰到了会不会出错”：会就是中或高，不会就是低。

## 5. 逐条核实和修复

审查结论是线索，不是事实。每一条都自己核实，再决定怎么处理：

1. 打开它指的代码，读到足以判断的上下文（调用方、被调用方、相关测试）。
2. 能复现就复现：逻辑问题先写一个会失败的测试，界面问题在预览里走一遍触发场景，时序问题找出两条交错的执行顺序。
3. 给每条一个结论：
   - **成立**：按真实的严重度处理。高和中要修；低的顺手能改就改，不改的列进交付报告。把审查者标的中、高降成低，必须附 `文件:行` 证据，并在交付报告里单列。
   - **成立但本次不修**：要修就得改需求、做大范围重构，或者要在两种行为之间取舍。不要硬修：停下来问用户，或者在交付报告最前面列为未解决。有这种条目时不算已收敛。
   - **不成立**：写下理由（例如“该分支在 X 处已被拦下”，附 `文件:行`）。
   - **存疑**：既证实不了也排除不了。修起来代价小就修；否则当作未解决的风险报告给用户，不默默放过。
4. 修完重跑第 3 步里相关的检查，确认修复没把别的弄坏。修一条问题时不要顺手重构。

## 6. 第二轮和收敛

- 第一轮核实后**没有成立的中、高严重度问题**：审查结束。
- 第一轮因中、高问题改了代码（成立的，或存疑但修了的）：再派一个**新的**子代理做第二轮。范围是整个改动（不只是修复部分），简报在第 4 步的基础上加上：
  - 第一轮每条结论的处理结果；
  - 判为不成立的条目，只附 `文件:行` 证据，不附推理，说明除非拿出新证据，不要重复提出；
  - 第二轮只报中、高问题。
- 第二轮后同样逐条核实。成立的中、高问题照样修掉并重跑检查，但**不再开第三轮**：在交付报告里写明“第二轮发现的 X 已修复，未再经独立审查”，由用户决定要不要再看。
- 每个 PR 或功能最多连续两轮。之后追加的改动按“审查的单位”一节处理。
- 为了收敛，第二轮只追中、高问题；低严重度的意见不作为再开一轮的理由。

## 7. 交付

向用户报告（中文）：

- 改了什么、改在哪里（`文件:行` 链接）。
- 跑过的验证和结果；没验证到的部分直说。
- 审查情况：进行了几轮；审查者标为中、高的每一条都单列，写最终定级和处理（已修复 / 不成立及理由 / 存疑 / 本次不修），降级的附理由；没处理的低严重度意见一句带过。
- 做的过程中看到、但不属于这次改动的问题。

提交只在用户要求时做。提交信息用中文的 Conventional Commits（参照 `git log`），一次提交只放这一次改动。
