# Spotify：用官方客户端播放

免费账号用不了 Folia 的标准播放方式（librespot）：Spotify 不给它发音频密钥，播放时提示账号无法播放。Soloist 也要 Premium 账号生成 API 密钥。

免费账号能放歌的只有 Spotify 自己的应用，所以这种方式让 **Spotify 桌面版**出声，Folia 控制它，并跟着它的进度显示歌词。歌单、歌词和搜索三种方式都一样。

只在 Windows 上验证过。其他系统不提供这个选项。

## 三种方式怎么选

| 方式 | 谁出声 | 适合 | 需要 |
| --- | --- | --- | --- |
| 标准播放 | Folia 自己 | Premium 且能拿到音频密钥的账号 | 无 |
| Soloist 播放 | Spotify 的 Soloist 程序 | 拿不到密钥的 Premium 账号 | 下载 Soloist、Premium 账号生成的 API 密钥、在 Spotify 应用里配对 |
| 官方客户端播放 | Spotify 桌面版 | **免费账号**；不想配置 Soloist 的账号 | 装好 Spotify 桌面版（Windows） |

能用标准播放就用标准播放：只有它的声音经过 Folia，均衡器、Automix 和视频导出才有用。跟着音频跳动的效果在这种方式下也能动，靠整机声音采集，见下面功能里的"真实频谱"。

入口和 Soloist 一样：

- 登录窗口里选"官方客户端播放"（Windows 上才有这一项）；
- 登录窗口账号那一页的"播放设置"，命令面板里的"平台播放设置"；
- 登录后"检查能否播放"没通过时，提示里除了"改用 Soloist 播放"，也给"改用官方客户端播放"；免费账号只给后者。

选择保存在主进程（`SPOTIFY_PLAYBACK_V1` 的 `client`），三种方式互不影响，随时能换。

## 它怎么工作

- Folia 用本机调试端口启动 Spotify：`--remote-debugging-port=0`，让 Spotify 自己挑一个空闲端口，只监听 `127.0.0.1`。端口每次启动都不同，Folia 这样找出它：
  - 先读 Spotify 写在自己配置目录里的 `DevToolsActivePort`：商店版在 `%LOCALAPPDATA%\Packages\SpotifyAB.SpotifyMusic_zpdnekdrzrea0\LocalCache\Spotify\`，安装版在 `%APPDATA%\Spotify\`；
  - 再扫本机回环地址上的监听端口，逐个问 `/json/version` 是不是 Spotify 自己；
  - 都找不到时才试以前的固定端口 9283。
- 找出来的端口只连 `127.0.0.1`，并且一定要回显自己是 Spotify，另一个程序占着端口时不会被当成它。微软商店版要通过它的 App Execution Alias 启动，直接启动 exe 会被拒绝。
- Folia 通过这个端口调用 Spotify 页面里的播放器：播放、暂停、跳转、音量和队列。调试端口连不上时退到 Windows 的系统媒体会话（SMTC），只能暂停、继续和跳转，精度较低，界面会提示一次。
- 队列归 Folia。当前歌后面的歌会提前放进 Spotify 自己的队列，衔接时不留空隙；放走一首就补回队尾。
  - 第一次写队列时会先试一次清空：播放器有清空队列的接口、并且真的清掉了，就按三首排（对齐"后面永远有三首"）；清不掉或者读不回来，就只排一首，因为这种队列只会越积越长，写进去的歌拿不回来——一首一首排，顺序错也只错一首，而且同一首不会写第二次。
  - 这次试的结果记在这次运行里，之后不再重试，也不会每次写都清一遍。
  - 写过的歌按 Folia 的账本记着（写了什么、App 还没放到的），会不会再写只看这本账，不看写完之后读回来的队列：读回比写入慢一步，拿它当"缺了哪首"就会把同一首再写一遍。
- 队列是 Folia 的，清空队列时你自己排的歌会原位放回：能清空时，Folia 只收自己写进去的那几首，清空之后把你排在队列里的歌按原来的位置放回；回填失败只记一行日志，不再重试（重试要再清一次队列，会把期间你自己排进去的歌一起带走）。清不掉时不动你的队列，Folia 只往后补。
  - 点歌时的清空也按同一本账：起播原本会无条件清空整个队列，那会把你排在 Spotify 窗口里的歌一起带走。现在清空同样只认账本里的位置，你排的歌按原来的顺序落回原位，Folia 预备的后续歌排在它们之后。
  - **整单播放是唯一整清的一次**：在 Folia 里播放整个歌单、专辑或列表，是拿一个新列表替换 Folia 的播放队列，此时 Spotify 的队列整个清空，你自排的歌也一起走、不回填，再写入 Folia 接下来的歌。渲染侧的「播放全部」（`playOnlineQueueFromStart`）给这次播放带上显式的 `replaceQueue: true`，经 `PlaybackNavigationOptions` → `omni.playSongExternally` → `client_play` 交到主进程，`play()` 把 `replaceQueue` 交给 `START_QUEUE_SOURCE` 才不回填。不靠空队列或"看起来像整单"来判断；单曲「加入队列」「下一首播放」、普通切歌与自动衔接都不带这个标记，仍只收回 Folia 写过的歌。
  - Folia 的队列是唯一的来源：队列里加歌、删歌、重排、切换循环或随机时，`refreshPreparedQueue` 把 Spotify 里 Folia 写入的那几首按 Folia 接下来的几首重写（提前量规则不变），你自排的歌不动。
- 单曲循环下，Folia 把写进 Spotify 队列的歌收回去，这一首放完从头重播。清不掉队列（降级）时收不回，那份记录留着：Spotify 自己走到这些歌上时，Folia 按名字认为这一首已经放完，照样重播。
- 这个端口只绑定本机回环地址，也只在这种方式开着时才会用。

## 会改动 Spotify 的哪些状态、何时恢复

这种方式要在 Spotify 里放歌，就绕不开动它的播放状态。原则是：**只改会破坏 Folia 播放所必需的那部分，改之前记下原值，离开这种方式时放回去。**

### 改什么

| 状态 | 什么时候改 | 改成什么 |
| --- | --- | --- |
| 队列（后面的歌） | 点歌后 | 写进 Folia 预备的后续歌；能清空时先清空，清空后把你自排的歌原位放回（见上面"它怎么工作"）。整单播放是例外：见下面"队列归 Folia" |
| 单曲重复（repeat: track） | 点歌后 | 关掉，改回不重复 |
| 列表重复（repeat: context） | 不改 | 播放单曲 URI 时没有可重复的上下文，列表重复对 Folia 播放的这首没有影响，是你自己的设置 |
| 随机（shuffle） | 点歌后 | 关掉。随机会把 Folia 写进队列的顺序打乱，所以这里是真有影响、必须关 |
| 音量 | 只在你在 Folia 里拖音量滑块、按音量快捷键时 | 跟随滑块；接管期间与暂停、跳转、状态轮询都不写 |
| 播放 / 暂停 / 进度 | 你的操作 | 只在 Folia 里操作时下发，状态轮询只读 |

几点补充：

- **单曲重复只在它是单曲重复时改**：列表重复对单个 track URI 的播放没有影响，不动它；只有单曲重复会让 Spotify 在这一首上来回放，卡住 Folia 写进队列的衔接，所以只关这一种。
- **接管期间什么都不改**：重开 Folia 接管你正在放的歌时，Spotify 队列里后面的歌和它当下的音量都是你自己的——这一轮运行并没有被要求接管它们。接管之后、你在 Folia 里点歌之前，写队列、收歌、设音量都不做；你点歌之后才进入正常播放方式。
- **接管期间你自己调音量照常生效**：要挡住的只是"Folia 把上次留下的滑块值推给 Spotify"，所以两条路径分开——自动同步（启动、接管、每首歌起播后按存下来的音量对齐）在接管期间不写；你在 Folia 里拖滑块或按音量快捷键是**你的操作**，接管期间也照常写给 Spotify。滑块与快捷键都走 `previewExternalPlaybackVolume`，自动那条走 `setExternalPlaybackVolume(level, 'sync')`。
- 改过的单曲重复和随机按**这一轮第一次改动之前**的原值记录，之后的点歌不会把 Folia 自己设的值当成你的原值。

### 何时恢复

| 时机 | 恢复什么 |
| --- | --- |
| 切换离开官方客户端播放方式（改成标准或 Soloist） | 单曲重复、随机放回原值；Folia 写进队列的歌收回 |
| 登出 Spotify | 同上 |
| 退出 Folia | 同上；开着"退出时关闭 Spotify"时，在关掉它之前先把状态放回 |
| 停止外部播放（切回本地歌、其他平台、Stage 等） | Folia 写进队列的歌收回；单曲重复与随机在离开这种方式时放回 |

恢复的实现和失败时的行为：

- 主进程侧是 `officialClient.cjs` 的 `restoreUserState()`：把记下的原值写回页面，成功一项就清掉那一项的记录。`spotifyApiBridge.cjs` 在切换播放方式、登出与退出三处调用它。
- **连不上 Spotify 时不为了恢复去启动它**：谁把它关了，它的状态就跟着这个应用一起没了，为了两个开关把 Spotify 重新拉起来是更大的打扰。这时记录留着，下一次恢复（或退出）再试。
- 某一项被页面拒绝时只清掉成功的那些，失败的那项留到下次；这些都只写日志，不弹提示。
- 队列的收回在单曲循环修复里已经做过（收回 Folia 写过的歌、把你自排的歌原位放回），这里沿用同一套做法。

## 功能

进度、播放/暂停、切歌、循环、随机、打乱、歌单播放与编辑、音量（含静音）、插队、喜欢，都由 Folia 的队列和控件完成。另外：

- **真实频谱**：Windows 桌面版采集整机正在发出的声音（Chromium 的 loopback），只在内存里分析出频谱交给可视化，所以跟着音频跳动的效果照实际声音动，不是只跟着进度模拟。
  - 不录制、不保存任何音频；为满足系统接口另外保留一路 1fps、16x16 的窗口画面，从不读取。
  - 采的是整机声音：浏览器和其他播放器的声音也会混进来，免费账号的广告也会照实跳动。
  - 暂停或无声时停在最后一帧，不跳变。
  - 采集不到时（非 Windows、网页版、系统不允许、从开播起就静音）回退到按播放进度模拟，有声音后自动回到真实频谱。
  - 没有开关，Windows 桌面版一直尝试。
- **媒体键**：这种方式开着、Folia 在运行时，媒体键一直由 Folia 接管。
  - 上一首、播放暂停、下一首都走 Folia 的队列，不会让 Spotify 在它自己的队列里往下走；只在换回标准或 Soloist 方式、或者退出 Folia 时还给系统。
  - 接管范围只限这种方式：Soloist 和 Apple Music 的媒体键还是上游本来的行为（走 `useMediaSessionBridge` 的媒体会话）。
  - 按键在各种状态下都由 Folia 处理：
    - **外部播放停了**（手动停、失败中止）：按播放算用户主动操作，重新唤起 Spotify 并从停下时的歌曲与进度继续（沿用"拉起、最多强杀 1 次、拉起时进托盘"的规则）；上一首、下一首照常走 Folia 的队列。
    - **队列放完**（最后一首结束、没有下一首）：按播放或下一首从当前队列第一首重新开始（随机是队列本身的顺序，循环在队尾结束的情形已经不存在）；上一首重放刚放完的最后一首。
    - **离开外部路由**（在放本地歌、Navidrome 或其他平台的歌，Folia 自己出声）：按键照常控制 Folia，播放暂停当前歌，上一首、下一首走 Folia 的队列。
- **一直不放手是实测的结论**：Spotify 客户端自己注册了一个系统媒体会话，而且这个会话常驻。
  - 暂停时 Windows 的当前会话仍是 Spotify：`GlobalSystemMediaTransportControlsSessionManager.GetCurrentSession()` 是 `SpotifyAB.SpotifyMusic…!Spotify`，状态 Paused。
  - 队列放完、Folia 自己出声、Spotify 停下时，这个会话也都还在。
  - 只要 Folia 一释放，系统就把按键交给这个会话，Spotify 会自己恢复，并在它自己的队列里往下走，绕过 Folia。
- **在 Spotify 里手动切歌**：在 Spotify 窗口里点上一首、下一首，Folia 会拉回自己的队列——往前走就是 Folia 的下一首，往回走就是 Folia 的上一首，队首时从头重放当前这首。
- **手动关了 Spotify**：之后点播放，Folia 重新拉起它，并从原来的进度继续。自动续播和暂停永远不会拉起 Spotify。
- **重新打开 Folia**：退出 Folia 时没关 Spotify、它还在放的时候，重开 Folia 按它现在的样子处理：
  - **能连上它的调试端口，而且它正在放记住的那首**：直接接管——路由变成本方式、界面显示正在播放、进度跟着 Spotify 的时钟走，媒体键和后面几首照常按上面的规则来。
  - **能连上调试端口，但它在放别的歌**：按端口给出的 track id 把这首查出来，换成当前歌曲，再按上一条的方式接管。队列里它排在原来记住的那首之前，记住的那首和它后面的照旧留在它后面，所以这首放完接着放原来记着的队列。主题、封面、歌词、时长按正常切歌加载，不额外按播放、不跳转。
  - **它在放别的歌，但暂停着**：同样换成当前歌曲，显示它的位置（仍是暂停），不接管；按播放从那里接着放。
  - **连不上它的调试端口**（比如 Spotify 是你自己开的、没带调试端口）：就只剩系统媒体会话可问，那里没有 track id，只有标题和一个歌手名——多歌手的歌只报主歌手，所以按"标题相同、至少一个歌手名整体对得上"认——歌手名不做子串比对，"DJ" 不算 "DJ Snake"，"Earth, Wind & Fire" 也不算 "Fire"；标题只去掉 (feat. …)、(ft. …)、(featuring …) 括注，(with …) 属于标题本身：认得出记住的那首，就同步它的进度（仍是暂停，精度到秒级）；认不出就什么都不动，并记一行日志说明两边各是什么。这时**跟随不了别的歌**，要靠调试端口拿到 track id 才行。
  - **放着广告、查不到这首、接管失败**：保持原样，不按播放、不暂停、不跳转，也不动 Spotify；广告期间既不写进度也不接管。
  - 接管本身不按播放、不跳转、不暂停，也**不动 Spotify 的队列和音量**：接管后到你在 Folia 里点歌之前，Spotify 队列里后面的歌和它当下的音量都是你自己的（见下面"会改动 Spotify 的哪些状态"）。你在 Folia 里点一首歌之后才进入正常播放方式：音量跟随 Folia 的音量滑块，后面的歌写进 Spotify 自己的队列（能清空时排三首、替换它自己排的队列；清不掉时只补一首，App 里原有的尾巴留着不重写，同一首不会写两次）。
  - 接管前会为这次运行搜端口（只读：读 Spotify 写下的端口文件、探本机监听端口），一次运行最多搜 2 次、两次至少隔 3 秒，找到和没找到都写一行日志；找到就记住，之后不再搜。没装 Spotify 时不搜。搜不到就只同步进度，**不会为了这个重启 Spotify**。
  - 接管之后 Spotify 就是这次运行正在用的播放器：如果开着"退出 Folia 时关闭 Spotify"，退出时它也会被关掉（规则同上一条）。
- **自动续播失败时**：
  - 只有"连不上 Spotify"（客户端被关掉、调试端口没有回应、请求没送到）才停在这首、提示"连不上 Spotify"。
  - **Spotify 自己说这首下架（再放也是这个结果）**：立刻跳下一首，只留一句"歌曲已下架，已跳过"，不查替代版本、不倒计时；免费账号只被会员限制放不了的，同样立刻跳，提示"需要 Spotify 会员，已跳过"。
    - 认它要有两次：页面的播放错误是它最后一次起播留下来的记录，上一首的歌可能还写着，所以第一次读到不可用信号先按住，隔一次轮询（约 100ms）再读到同一个判定才算数；错误自己写明了曲目 uri 而跟这次要放的不一致时，当它没说。
      - 只认错误里的 `uri`、`item.uri`、`track.uri` 三处曲目标识；`contextTrack` 是它播放的那份列表（上下文容器），不算这次点名的歌，不读。
      - 屏上是广告、点的那首还没出现时，一律不认不可用信号，广告开始前按住的那次判定也一起作废；广告结束后重新按上面的两次确认算。
  - 这首歌**其他**放不了的情况（放不了、但 Spotify 没说是下架也没说是会员限制），或者电脑上没装客户端，还是走原来的失败流程：说出真正的原因，并按"无法播放时自动跳过"的设置在倒数后跳过。
- **每次运行最多强杀 1 次**：Spotify 已在运行但没带调试端口时，Folia 要关掉再带端口启动，这一次只允许一次；用完后只走媒体会话，直到下次启动 Folia。
- **拉起时不出现窗口**：Folia 启动 Spotify 之前先起一个隐藏的监视进程，窗口一被显示就在同一帧用 `ShowWindow` 隐藏。
  - 监视进程靠 `SetWinEventHook` 抓 `EVENT_OBJECT_SHOW`，再加 20ms 轮询兜住创建即可见的窗口。
  - 实测（5ms 采样，三次冷启动）窗口一次都没被采样到，最差一次 ≤15ms；旧做法是页面就绪时才隐藏，同一次实测里可见约 1.5s。
  - 同时仍带 `--minimized`、仍对 STARTUPINFO 要 SW_HIDE：商店版两者都忽略（实测），所以真正起作用的是监视进程。
  - 只对这次启动出来的进程生效，启动前已存在的 PID 一律跳过，你自己开着的 Spotify 窗口不会被隐藏。
  - 监视进程随这次启动结束一起退出，之后从托盘点开一切照常。
  - 万一监视进程没起来，页面就绪时还会再扫一次同样的 SW_HIDE 兜底。
- **三个开关**（设置里的集成页"连接与集成"，也在命令面板里；都和这种方式一样只在 Windows 上出现）：
  - 打开 Folia 时唤起外部播放器（只在官方客户端播放开着时生效，默认关）；
  - Folia 退出时关闭 Spotify（默认关）：本次运行由 Folia 拉起、退出时还开着的 Spotify，或者带着 Folia 打开的调试端口在运行的 Spotify，都会关掉。
    关的动作是 `taskkill /IM Spotify.exe /F`，按进程名结束，所以同一台电脑上你自己另外开着的那份 Spotify 也会被一起关掉；
  - **使用官方客户端时始终接管媒体键**（默认开）：按上面那条规则一直占着；关掉时只在 Spotify 正放着 Folia 的歌（含暂停）时占着，队列放完、离开外部路由、外部播放停下就还给系统。占着期间浏览器等其他程序收不到媒体键。

## 找不到 Spotify 桌面版时

这种方式开着、而电脑上没装 Spotify 桌面版时，播放会失败，并打开"播放设置"清单：清单里写明没找到，也给"改回标准播放"和"改用 Soloist 播放"。

**不会**悄悄退回 Folia 自己播放：免费账号用它必然失败，悄悄退回只会换来一条看不懂的错误。装好 Spotify 桌面版后再点播放即可，不用重启 Folia。

## 风险

- **非官方方式，账号风险自负**：
  - 这种方式控制的是 Spotify 自己的客户端，走它的调试端口和页面内部的播放器，不在 Spotify 的公开 API 里。Spotify 改版会让它失效。
  - 用它是否违反 Spotify 的使用条款、会不会影响账号，由用的人自己判断和承担。Folia 不做任何绕过付费、屏蔽广告或改动账号数据的事。
- **调试端口对本机程序开放，对网页不开放**：
  - 端口只绑 `127.0.0.1`，而且只有 Folia 自己指定端口时，才会把那个端口的来源写进 `--remote-allow-origins`。
  - 现在的调用从不指定端口，所以实际一律不写：端口是 Spotify 自己挑的，没有能写进去的来源。
  - Folia 自己的调试客户端不发 `Origin` 头，所以正常可用；浏览器里的网页一定会带 `Origin`，Chromium 会直接拒绝这种连接，网页扫到端口也连不上。
  - 但**本机上不带 `Origin` 的普通进程仍然可以连上这个端口，进而控制当前已登录的 Spotify**，这一点没有鉴权。端口每次启动随机（见上面"它怎么工作"）只是让这类程序没法事先写好端口号。
  - 不用这种方式播放时不会开这个端口。

## 限制

- **只验证了 Windows**：Windows 11、微软商店版 Spotify 1.3.6、免费账号。其他版本和安装方式没有测。
- **调试端口的发现依赖 Spotify 自己的行为**：
  - 随机端口靠 Spotify 的 CEF 写出的 `DevToolsActivePort`，或者它在本机回环地址上开的监听端口。
  - 两者都读不到时会退到固定端口 9283；如果哪个版本连这两样都不给，这种方式就连不上 Spotify 页面，只能靠系统媒体会话粗放地暂停和继续。
  - 这一条要在真机上确认，见下面的"真机复测"。
- **声音不经过 Folia**：均衡器、音效、ReplayGain 和 Automix 都不处理它，视频导出也不可用。
  - 跟着音频跳动的效果在 Windows 桌面版用上面"真实频谱"那条的整机声音采集，拿到的不是这首歌的音频流。
  - 采不到时退回按播放进度模拟，混进来的别的声音也会带着它动。
- **广告照常播放**：免费账号在歌与歌之间会有广告。Folia 不做任何屏蔽或静音（Spotify 的条款禁止屏蔽广告），音量也不动。Folia 只是认得出它是广告，所以它既不会被当成当前这首的结束，也不会被当成你在 Spotify 窗口里切了歌，队列和进度都停在这首上。
- **起播时的片头广告**：
  - 免费账号点歌时常常先放一段广告，再放点的那首。
  - 等起播时广告的时间不算在 5 秒的等待里（整段等待最多 60 秒），广告结束后点的那首出现就算起播成功。
  - 广告长到 60 秒还没结束时，这次起播按"已接受、广告中"交给状态轮询接着跟，既不报成这首放不了，也不会触发"无法播放时自动跳过"。
- **Spotify 的页面结构会变**：播放器是在页面的 React 树里找到的，Spotify 改版后可能找不到，这时会退到媒体会话，精度降低。

## 实现

- 主进程：`electron/spotify/officialClient.cjs`（启动、调试端口与端口发现、播放器调用、媒体会话）、`spotifyApiBridge.cjs`（`playback_mode`、`client_*` 操作、退出时关闭）、`../quitShutdown.cjs`（哪一次退出去问各个 bridge 关闭）。
- **媒体键是通用的**，不在这个目录里：`electron/mediaKeys.cjs`（与 `quitShutdown.cjs` 同级）只管在 `globalShortcut` 上占住三个键并把手势交给渲染进程；要不要占、按键做什么由下面这条通用 bridge 决定。
- 页面：`src/services/onlineMusic/spotify/spotifyClientPlayback.ts`（外部播放路由的实现）、`spotifyExternalPlayback.ts`（按当前方式在 Soloist 和官方客户端之间分派，并声明这种方式要一直占着媒体键）、`spotifySetup.ts`（配置清单）。
- 公共部分：`src/components/app/playback/bridges/useMediaKeyTakeoverBridge.ts`（通用的媒体键接管：问 omni 要不要占、按一次键跑播放暂停和上一首下一首、队列放完时重新开始、外部停了之后重新唤起都在这里，与路由无关）。
  - `externalPlayback.ts` 里的 `skipped`：播放器被它自己的控件换了歌；同一处还有降级状态。
  - `externalPlayerWake.ts`：启动时唤起。
- 真实频谱（跟着音频跳动的效果）：
  - `src/components/app/playback/externalSpectrumCapture.ts`：整机声音的采集与分析。
  - `spectrumBands.ts`：频谱折成本机播放用的同一套频段。
  - `electron/displayMediaRoute.cjs` 与 `main.cjs` 的 `setupDisplayMediaRequestHandler`：一个 session 只有一个 display-media handler，视频导出和频谱在这里分派。
  - 采集只在外部路由上起，离开就停；采集期间主窗口不进入后台节流，即使后台节流开关开着也一样。
- 平台只声明、通用层不认平台：`OnlineExternalPlaybackProvider` 的 `holdsMediaKeys`（它的会话在放时占着）和 `holdsMediaKeysWhileRunning`（它的程序在跑就一直占着）由 `spotifyExternalPlayback.ts` 按当前方式回答，omni 汇总成 `wantsMediaKeyTakeoverWhileRunning()`。
