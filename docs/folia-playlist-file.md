# Folia 歌单文件（JSON）

Folia 聚合歌单可以导出成一个 JSON 文件，再在别处（或这台设备上）读回来。和 M3U8 不同，它装得下各个来源的歌。

规则都在 `src/services/foliaPlaylist/foliaPlaylistFile.ts`（纯函数，不碰存储与界面）；接曲库、音源状态、Navidrome 配置与下载的在 `foliaPlaylistFileIo.ts`；窗口在 `src/components/folia-playlists/FoliaPlaylistFileDialogs.tsx`。

## 文件长什么样

一张歌单一个文件，扩展名 `.folia-playlist.json`，UTF-8。

```jsonc
{
  "format": "folia-playlist",   // 格式标识，认文件靠它
  "version": 1,                 // 格式版本，整数
  "exportedAt": 1795000000000,  // 导出时刻（毫秒），只作记录
  "playlist": {
    "name": "歌单名",
    "favorite": true,           // 只有「我喜欢的音乐」带
    "createdAt": 1790000000000,
    "origin": {                 // 转存来的歌单才有：它原来是哪家的哪张歌单
      "sourceId": "netease", "collectionId": "123", "name": "原歌单名",
      "savedAt": 0, "playVia": "lxmusic", "refreshedAt": 0,
      "collectionType": "album",  // 原来那张是专辑才写
      "collectionData": { }       // 原歌单在音源那边的附带数据，有才写；和歌的附带数据过同一道筛
    },
    "entries": [
      { "source": "online", "addedAt": 0, "originalKey": "online:netease:2", "fromOrigin": true, "song": { /* 歌的快照 */ } },
      { "source": "navidrome", "addedAt": 0, "song": { /* 歌名、歌手、专辑、时长 */ }, "navidrome": { "id": "…", "coverArtId": "…" } },
      { "source": "local", "addedAt": 0, "song": { /* 歌名、歌手、专辑、时长 */ }, "local": { "path": "Music/A/one.mp3", "fileName": "one.mp3", "fileSize": 5000000, "durationMs": 180000 } }
    ]
  }
}
```

- `originalKey`：这一条换过来源时，它原来那首歌的 key。`fromOrigin`：这一条是跟着原歌单来的（「从原歌单更新」靠它）。
- 文件里不写条目的 key：读入时从歌重新算，文件里写了也不认。

### 三种条目

| `source` | 写了什么 | 读入时 |
| --- | --- | --- |
| `online` | 歌的快照：id、歌名、别名、歌手、专辑（含封面地址）、时长、`sourceRef`（音源 id、媒体 id、变体、音源自己的数据） | 照着白名单重建；音源在这台设备上没装或停用的照样导入，只是暂时播不了 |
| `navidrome` | 歌名、歌手、专辑、时长，加上 Navidrome 的歌 id、专辑 / 歌手 id、路径、后缀、码率、封面 id | 封面地址用这台设备上配的 Navidrome 账号在读入那一刻拼（读入时没配的，之后配了也不会补上封面；播放地址是播放时现拼的，不受影响）。默认是同一个服务器——文件里不记服务器地址 |
| `local` | 歌名、歌手、专辑、时长，加上认回文件用的线索：相对路径、文件名、文件大小、时长 | 在这台设备的曲库里重新认（见下） |

### 本地歌怎么重新认

本地歌的 id 是这台设备导入时生成的，换一台设备就不是它了，所以文件里不写 id，只写线索。读入时在曲库里按顺序找，**只认唯一的一首**：

1. 整条相对路径一样（不分大小写，`\` 与 `/` 一样看）。
2. 去掉最前面那一层（导入的文件夹名，各人起的不一样）以后路径一样。去掉以后只剩文件名的（文件就在导入的文件夹底下）等于只比了文件名，照第 3 步要证据。
3. 文件名一样，并且文件大小相同，或时长相差不超过 1.5 秒。

第 1、2 步路径对上了，但线索里大小和时长都有、而那首歌两样都对不上：不认（同一个位置上放的是另一个文件）。

不按歌名歌手认：同名的歌太多，认错比认不出更糟。认不出来的不导入，预览里写明有几首、列出前几首的歌名。导出时曲库里已经找不到的本地歌没有线索可写，不写进文件，导出窗口里写明有几首。

## 不写进文件的东西

- 凭据与带凭据的地址：Navidrome 的播放地址、封面地址（带着账号的令牌）一概不写，只写 id。
- 音源自己的数据（`sourceRef.providerData`，以及出处的 `collectionData`）里：带查询串或片段的地址（相对地址带查询串的也算）、`blob:` / `data:` / `file:` 地址删掉；键名像凭据的（token、cookie、secret、password、session、api key、authorization、sign……）整项删掉；其余留着（音源靠它找回这首歌）。整份超过 16384 个字符的不带。音源契约本来就要求这份数据里不放凭据，这里是第二道。
- 歌的封面地址只带公开的：不是 http(s) 的、主机是本机或内网的、带用户名密码的、查询串里有像凭据的键的（自建服务器的封面常带 `api_key`）都不带。所以内网自建服务器上的歌读回来没有封面。
- 播放地址、本地文件的 blob 地址、歌的本机 id。
- 快照里会过期或只对导出者有意义的字段：收费与权限标记、响度数据等。读回来以后播放时会重新取。
- 自定义封面的图片。理由：它是二进制的，放进 JSON 要转成 base64，文件会大一个量级；封面在别的设备上可以重新设；文件保持成一份人能读、能比对的清单更有用。歌曲自己的封面地址（公开的 http(s) 地址）照带。

## 读入：文件是不可信的数据

- 上限：文件 32 MB，条目 20000 条（M3U 的路径数也按这个算）。超了整份不读。
- 先看 `format`，再看 `version`：不是这个格式、版本比这一版新、结构不对，各有各的提示，什么都不写。
- 每一条照白名单重建，只留认识的字段、认识的类型，字符串有长度上限；不成形的条目略过并计数。
- 封面地址过和导出时同一道筛（只收公开的 http(s) 地址）。文件里没有任何字段会变成界面上能点的链接；封面地址是唯一会被界面自动请求的东西（一次不带凭据的取图）。
- 时间戳超出 Date 的范围当 0，时长超过七天当 0；数字 id 只收非负的安全整数；歌名、歌手名、歌单名里的控制字符和改变显示方向的字符去掉。
- 出处（`origin`）是文件说的，不验证：用户之后点「从原歌单更新」时，会向那个已安装的音源读文件指定的那张歌单并把新歌加进来。更新不会删歌。文件没有出处时，条目上「跟着原歌单」「换过来源」的记号不带。
- 音源 id 只收合法的 id；歌手、专辑的 `catalogRef` 只收这首歌自己那个音源的。
- 条目的 key 从歌重新算。同一首歌在文件里出现多次只留一条。
- `__proto__`、`constructor`、`prototype` 这些键不收。

预览（歌单名、共几首、各来源几首、哪些来源在这台设备上不可用、本地歌认出几首、认不出几首）出来之前不写任何东西；用户点了导入才写。

## 导出与导入的窗口

- 导出：歌单的「导出歌单…」打开窗口，选保存格式。歌单里有 M3U8 装不下的歌（不是本地文件的）时默认选 JSON，并写明 M3U8 会丢掉几首；全是本地歌时默认 M3U8（别的播放器也能开）。
- 导入：同一个入口，两种格式都认——按内容认，不看扩展名。有 M3U 的标记行、或每一行都像一条带扩展名的路径的是 M3U；不是 M3U 而以 `{` 开头的当 JSON。
- 同名歌单已经存在时让用户选：新建一张（默认，两张同名），或并入已有的那张（已在里面的不重复加；并进去的算用户自己加的，不带出处与「跟着原歌单」的记号）。导出的「我喜欢的音乐」默认并入这台设备的「我喜欢的音乐」。

## 改格式的时候

- 加可选字段不用升版本：旧版读入时不认识的字段会被丢掉。
- 改了已有字段的意思，或旧版读了会出错的改动，把 `FOLIA_PLAYLIST_FILE_VERSION` 加一，并在解析里保留对旧版本的读法。旧版的 Folia 见到更新的版本会提示更新，不会硬读。
