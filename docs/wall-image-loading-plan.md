## 结论

1. **能单独做，而且和歌词舞台的重构互不依赖**。两面墙都是 DOM，Lattice 打开时歌词舞台是卸载的。
   这件事比舞台小一个量级，可以先做。
2. **合成这一侧已经调得很细，没有看到明显的漏洞**：按视口裁剪、世界层整层平移、不加 `will-change` 以免按 1 倍光栅化
   （`wall.css:81-91`）、相机平移吸附到设备像素、封面按 256 / 512 / 1024 三档取、升档前先解码。
3. **缺口集中在「图从哪来」**：三档阶梯只对一部分平台生效，其余平台的小磁贴拿到的是 512 到 1200 像素的图；
   本地封面的缩略图在主进程的线程上同步生成；同一张封面会以不同地址被取两次。
4. 建议按下面 A → B → C 的顺序做，D、E 先量再定。

墙上一张普通磁贴的尺寸：格子 128，相机缩放 0.52–0.76（`bravaisConstants.ts`），2 倍屏上边长不超过约 195 设备像素，
落在 256 那一档。聚焦卡和大格才用到 512 和 1024。

## 现在的取图路径

两面墙共用 `src/components/wall/useWallPosterArtwork.ts`：

- 磁贴按自己的边长（设备像素）取 `COVER_SIZE_STEPS = [256, 512, 1024]` 里够用的最小一档，地址由 `getSizedCoverUrl` 改写。
- 一张冷的磁贴直接把这一档的地址写进 `background-image`，由浏览器自己取、自己解码。
- 换档（磁贴展开）时先 `new Image().decode()`，解码完才换地址；在那之前继续画手里已有的低一档。
- 解码过的地址记 600 条，失败的地址记 600 条。

`test/manual/lattice-cover-memory.mjs` 是这条路径的测量工具，它的文件头写了结论：图比磁贴大时，
代价主要不是常驻内存（Chromium 会丢掉解码结果再重解），而是平移时每次重画的解码，表现为帧间隔变差。

## A. 让尺寸阶梯对所有平台生效

`getSizedCoverUrl`（`src/utils/coverUrl.ts`）认得的平台才能拿到小图：

| 封面来源 | 256 档实际拿到 | 依据 |
|---|---|---|
| 网易云、酷狗、Navidrome | 256 | 地址里写多少给多少 |
| QQ | 300 | 只有 300 / 800 / 原图三档 |
| 酷我（波点） | 240 | 只有 240 / 800 |
| **本地** | **512** | 缩略图只有 512 和 1024（`LOCAL_COVER_THUMBNAIL_SIZES`，`electron/localCoverAssets.cjs:10`） |
| **Apple Music** | **512** | 归一化时把模板里的 `{w}`、`{h}` 写死成 512（`appleMusicNormalize.ts:14-16`），没有改写规则；聚焦卡要 1024 时也只有 512 |
| **Spotify** | **最大的一档** | `pictureOf` 只留 `sources` 里最宽的那张（`spotifyNormalize.ts:62-66`），没有改写规则 |
| **YouTube Music** | **最宽到 1200** | `thumbnailUrl(…, maxWidth = 1200)`（`electron/ytm/catalog.cjs:16-22`），没有改写规则 |
| **汽水** | 原样 | `qishuiImage` 拼出带模板前缀的地址，没有改写规则 |
| **飞牛** | **600** | `fnMusicCoverUrl(coverId, size = 600)`，地址里有 `size` 参数但没有改写规则 |

对下半张表的平台，现在的墙就是探针里的 `original` 模式。

做法：

- 每个平台补一条「这张封面的 N 像素版本」的规则。Spotify 和 YouTube Music 的响应里本来就有多档，归一化时不要只留一张；
  Apple Music 保留模板或按 `512x512` 改写；飞牛改 `size` 参数；汽水先按真实响应确认模板怎么写再定。
- 规则放哪：`coverUrl.ts` 里已经有四个平台的规则，但 AGENTS.md 要求一个平台的规则留在那个平台的目录里，
  平台目录外提到平台名的次数还有测试核对（`platformNamePlaces.ts`）。建议做成各平台登记的一项能力，
  `coverUrl.ts` 只负责分发；已有的四条规则是否一起挪过去另议。
- 本地封面加 256 这一档（见 B）。

怎么量：`CoverSizeAuditPanel`（对照请求的尺寸和 CDN 实际返回的尺寸）确认规则生效；
`npm run manual:lattice-cover-memory` 的 `original` 对 `stepped`，看平移时的帧间隔。

## B. 本地封面的缩略图挪出主进程的线程

现状（`electron/main.cjs:3134-3146`、`electron/localCoverAssets.cjs`）：

- 缩略图在 `folia-cover:` 的协议处理器里按需生成：`nativeImage.createFromBuffer` → `resize` → `toJPEG`。
  这三步都是同步的，跑在主进程的线程上。外面那层「最多 2 个并发」只限制了排队，挡不住每一张都卡住主进程一次。
- 第一次打开一面本地歌曲的墙时，视口加外扩范围内的几百张磁贴各触发一次；平移时继续触发。主进程卡住期间，
  所有 IPC（播放控制、窗口操作）都在等。生成一次后落盘，之后不再有这笔开销。
- 每个请求另有读描述文件、`JSON.parse`、两次 `stat`、一次 `net.fetch(file://)`，缩略图已经在盘上时也一样。

做法：

- 导入时就把 256 / 512 / 1024 三张缩略图做好：封面字节本来就是渲染进程写进来的，在渲染进程的 Worker 里用
  `createImageBitmap`（带缩放）加 `OffscreenCanvas.convertToBlob` 生成，和原图一起交给主进程落盘。
- 老资料库在空闲时补做，一次几张。
- 协议处理器保留按需生成作为兜底，另加一份内存里的描述缓存，省掉每个请求的读文件和 `stat`。

怎么量：导入一批带大封面的本地歌曲后第一次打开墙，用 `dev/perf/app` 或主进程的事件循环延迟看卡顿；
改完后同一操作再量一次。

## C. 同一张封面只取一次

`getCoverIdentity` 已经知道哪些地址是同一张图：网易云的 `p1`、`p2` 主机可以互换，`http` 和 `https` 是同一张。
但 `getSizedCoverUrl` 改写时保留了原来的主机和协议，所以同一张专辑封面从两首歌的数据里来、主机不同，
浏览器就当成两个资源，各取一次、各解码一次。

做法：改写时把主机和协议也规范成一个。先量再做：开发日志里数一面墙上「不同的地址数」和「不同的封面数」，差得多才值得改。

## D. 取图的先后（先量）

冷磁贴的图由浏览器按自己的队列取。视口内的和外扩范围（Bravais 420、Lattice 500 世界单位）里的磁贴同一个优先级，
快速平移扫过的磁贴也照样发请求。缓存热的时候这没有影响；网络慢、缓存冷、平移快的时候，视口里的图可能排在看不见的图后面。

先在 `bravaisPerf` 探针里加一个读数：磁贴挂上到封面画出来的时间，按平台分。数字难看再做：
把冷加载也收进 `useWallPosterArtwork` 现有的解码队列，视口内优先、外扩其次，磁贴卸载时撤掉还没发出的请求。

## E. 图片之外的两处（先量）

- **专辑墙和歌手磁贴的逐磁贴混合**。专辑墙的碎片磁贴每张有一个 `filter` 加三层 `mix-blend-mode`
  （`bravaisAlbumPoster.css:438-463`），歌手人像磁贴有一个 `filter` 加两层混合（`bravaisTileKinds.css:106-123`）。
  每张这样的磁贴都要单独合成一次。`bravaisPerf` 探针的场景里没有专辑墙，也没有歌手页签，这两种墙没被量过。
  先加场景；如果确实重，把双色调加网点在 Worker 里按封面烘成一张位图，磁贴只画这张图，悬停时换回原图。
- **#843**（未关闭）：Bravais 的世界层 transform 在 `pointermove` 里同步写，高刷新率屏上拖拽有节奏抖动，
  issue 里建议改成 rAF 目标插值。

另有一处小的不一致：专辑墙找切点时取 128 像素的封面（`bravaisAlbumWall.ts:30`），歌手取色取 256
（`bravaisArtistTone.ts:14`，注释写明是为了和墙上最小的一档同一份缓存）。切点也改成 256，少一个只用一次的尺寸。

## 不建议做的

**把墙搬进 GPU 舞台**（封面做成纹理图集，磁贴画成实例）。平移可以完全不经主线程，但磁贴上有文字、点击、键盘走位、
翻牌和无障碍语义，这些都要重做；而且两面墙现在的问题不在合成。等上面几条做完、量过仍然不够再考虑。
