# Omni 在线音乐层

`src/services/onlineMusic/omni.ts` 是普通在线歌曲数据的唯一公开入口。组件、hook、store 和普通 app service 不得直接调用具体 provider、registry、transport 或 raw API；只有明确的跨 provider 编排，或 provider adapter/transport 自身，才可以使用 provider-explicit 层。

## Layer map

```text
UI / hooks / stores / app services
  -> omni.ts
       -> providerRegistry.ts
            -> neteaseProvider.ts
            -> kugouProvider.ts
                 -> kugouTransport.ts（酷狗请求/IPC 边界）
            -> qqProvider.ts
                 -> qqTransport.ts（QQ 音乐请求边界）
            -> bodianProvider.ts
                 -> bodianTransport.ts（波点音乐的受限 IPC 边界，仅桌面端）
            -> ytmProvider.ts
                 -> ytmTransport.ts（YouTube Music 的受限 IPC 边界，仅桌面端）
            -> spotifyProvider.ts
                 -> spotifyTransport.ts（Spotify 的受限 IPC 边界，仅桌面端）
       -> account/（各平台账号共用的逻辑，只从 omni 进入）
       -> login/（登录失败的分类和请求时限，不认识任何平台）
       -> providerAccountCache.ts / providerStorage.ts
  -> src/types/onlineMusic.ts（共享合同）
```

图里的 `<id>Provider.ts` 和 `<id>Transport.ts` 都在各平台自己的目录 `<id>/` 里（例如 `qq/qqProvider.ts`）。网易云没有单独的 transport，请求在 `netease/netease.ts`。

当前 registry 注册 `netease`、`kugou`、`qq`，以及桌面端的 `bodian`、`ytm`（YouTube Music）和 `spotify`。波点接入状态、接口与剩余验收见
[`docs/bodian.md`](../../../docs/bodian.md)；支持喜欢与自建歌单歌曲增删，收藏写入尚未实现。Navidrome 是独立的 Subsonic 服务，入口是 `src/services/navidromeService.ts`，不属于 Omni provider。

登录的分工：provider 把后端的回答翻成 `LoginState`。失败带着平台的原话（`message`）和事实（`failure`：码、原话、HTTP 状态、要等多久，或者直接点名的情况，比如 QQ 的登录设备超限 `device-limit`）；这一次检查在网络这一层没拿到回答、码在平台那边还有效时标 `transient`，登录接着检查。要码与生成二维码拿不到 key / 图片时直接抛错，不交出空值。情况怎么分在 `login/loginFailureCase.ts`，平台自己的码是什么意思由它的 `describeLoginFailure` 说。登录失败后由登录调用一次 `omni.runLoginSelfCheck` 主动自检（`loginSelfCheck.ts`），结果进诊断报告；`omni.getLoginDiagnostics` 的 provider 段每一行都由 `login/loginDiagnosticReport.ts` 的 `diagnosticLine` 写，放进去的文字先洗过：登录凭据、IP 和账号不进报告。

网易扫码轮询（`/login/qr/check`）在桌面端由本地服务换掉的 `login_qr_check` 处理（`electron/netease/neteaseApiStartup.cjs` 的 `createLoginQrCheck`）：上游原版请求被拒时只回 `404 Not Found`，换掉以后页面拿到网易云真正回的 `{ code, msg }`。扫码的要码与轮询遇到网络层失败时重发一次（同一文件的 `withQrNetworkRetry`）。识别网络层失败用 `shared/networkErrorText`（`.mjs` 给渲染进程，`.cjs` 给主进程，内容一致）。

要地址、读集合没有成功时，失败分成有名字的情况（`failure/onlineFailureCase.ts`，不认识任何平台；平台自己的码是什么意思由它的 `describeFailure` 说），提示条按情况说发生了什么、该做什么，再引平台的原话（`failure/onlineFailureTexts.ts`）。要地址连不上时先自己再要两次（到了时限的请求只再要一次），并提示正在重试；平台要求稍后再试而说了等多久时，到点之前这个平台的地址点歌和预取都不再去要；没说多久、或平台的服务出了错（5xx）时只让预取先停 30 秒（`failure/onlineRequestCooldown.ts`）。播放时失败只按情况说，从不回写歌曲的可用性、预取或缓存。

每个平台靠哪个库或哪个服务拿数据、版本钉在哪、上游变了怎么跟，见同目录 [`UPSTREAMS.md`](UPSTREAMS.md)。

## 接入一个新平台

下面用 `foo` 代表新平台的 id。`OnlineProviderId` 是开放的字符串，不用改类型。

一个平台的代码放在名字正好是 `foo` 的目录里：`src/services/onlineMusic/foo/`，桌面端的 `electron/foo/`，测试 `test/unit/foo/`。目录名要和 id 相同：`test/unit/onlineMusic/platformNameCount.ts` 按目录名认平台自己的文件，别处每一行提到平台名都要登记。上一次完整接入一个平台的记录在 [`docs/bodian.md`](../../../docs/bodian.md)，可以对照着看。

### 必须做的

1. `foo/fooTransport.ts`：平台的原始请求全在这里发出，别的文件不碰平台接口。平台答的错误换成 `OnlineProviderError`，带上 `'foo'`。
2. `foo/fooProvider.ts`：导出一个 `OnlineMusicProvider`（定义和契约注释在 `src/types/onlineMusic.ts`）。必填 `id`、`displayName`、`capabilities`、`normalizeSong`。其余成员按平台有的能力加（`search`、`playback`、`lyrics`、`auth`、`library`、`catalog`、`recommendations`、`explore`、`mutations` 等）。`capabilities` 的开关要和实现了的成员一致：界面很多地方只看开关（例如探索页签）。短的例子是 `bodian/bodianProvider.ts`；归一化、集合、用户库可以像波点那样分成同目录的几个文件（`bodianNormalize.ts`、`bodianCatalog.ts`、`bodianLibrary.ts`）。
3. 每首歌都带 `sourceRef: { kind: 'online', providerId: 'foo', mediaId }`，每个集合都带 `providerId: 'foo'`。原因：没有 `sourceRef` 也没有 `providerId` 的歌会被当成网易云的（`src/utils/appPlaybackGuards.ts` 的 `getPlaybackSourceRef`）。
4. 在 `providerRegistry.ts` 里 import `fooProvider`，再 `registerOnlineMusicProvider(fooProvider)`。这是唯一的平台清单。
5. 有登录的：`auth` 实现 `startLogin`、`checkLogin`，再加 `createQr`（扫码）或 `openLoginPage`（在浏览器里确认）其中一个。`getLoginTexts` 回登录标题和说明的文案键（现有的叫 `home.loginTitle<平台>`、`home.loginNote<平台>`），三份语言文件 `src/i18n/locales/en.ts`、`zh-CN.ts`、`in.ts` 都要写。
6. 两个架构测试要认得新平台，否则它们不管它：
   - `test/unit/onlineMusic/omniArchitecture.test.ts` 的 `forbiddenImport` 加上 `fooTransport`，界面、hook、store 就不能直接 import 它。
   - `test/unit/onlineMusic/platformNameCount.ts` 的 `PLATFORM_NAMES` 加上平台的名字（id 和中文名）。平台目录之外提到它的文件（`providerRegistry.ts`、桌面端的 `main.cjs`、`preload.cjs`、`vite-env.d.ts` 等）在 `platformNamePlaces.ts` 里登记行数和原因；`node test/unit/onlineMusic/platformNameCount.ts --files` 列出这些文件和数字。
7. 逻辑测试放 `test/unit/foo/`：归一化、翻页、错误答复这些用的人看不出来的逻辑，用量到的最小答复做数据。

### 只在桌面端跑的平台

平台要在主进程里请求（凭据加密、跨域、本地服务）时，照波点和 YouTube Music 做：

1. `electron/foo/fooApiBridge.cjs`：导出 `createFooApiBridge({ store, safeStorage, ... })`，对外一个 `request(operation, params)`，回 `{ ok: true, data }` 或 `{ ok: false, error: { code, message } }`。凭据在主进程里用 `safeStorage` 加密保存，不交给渲染进程。
2. `electron/main.cjs`：require 并创建这个桥；加 `ipcMain.handle('foo-api-request', ...)`，先用 `isTrustedMainWindowContents(event.sender)` 挡掉别的窗口（照 `bodian-api-request` 那一段）。
3. `electron/preload.cjs`：加 `fooRequest`。
4. `src/vite-env.d.ts`：给 `window.electron` 加 `fooRequest` 的类型。
5. `fooTransport.ts` 用 `window.electron?.fooRequest` 判断能不能请求；provider 的 `getAvailability` 在网页版回 `{ configured: false, reason: 'runtime-unavailable' }`（照 `bodian/bodianTransport.ts`）。
6. 音频地址要特殊的请求头或会重定向的：在 `main.cjs` 的媒体请求规则里登记（波点用 `electron/bodian/mediaCors.cjs`）。

### 按需要做的

- 探索页：见同目录 `EXPLORE_ADAPTER.md`。
- 电台页签和音质档位：见 `EXPLORE_ADAPTER.md` 最后一节。
- 应用开着时要盯着的东西（比如本地服务起不来）：provider 的 `watch` 成员。提示由 `src/components/app/useProviderNotices.ts` 统一显示，不用改它。
- 登录要靠的本地服务：`auth.localService`，登录窗口会显示它的错误和重启按钮。
- 多种登录方式和图标：`auth.getLoginMethods` 回 `iconKey`，图标放 `src/assets/providers/<iconKey>.svg`。
- 跨源歌词匹配的来源：`src/utils/lyrics/lyricSources.ts` 的 `ENTRIES` 加一行，三份语言文件加 `lyricProvider.foo`。`platform: true` 的来源经它的 provider 去搜，`lyricMatchSources.ts` 不用改。
- 本地歌匹配在线信息：`src/components/modal/LocalSongMetadataMatchDialog.tsx` 的平台按钮和 `src/services/onlineMetadataSearchService.ts` 的自动匹配顺序都只写了网易云、QQ、酷狗；要让新平台参加，改这两处。
- 命令面板的“搜某平台的歌”：`src/components/command-palette/commands/searchCommands.ts` 现在只有网易云一条。
- 封面按尺寸取图：`src/utils/coverUrl.ts` 的 `CoverProvider` 和 `describeCoverUrl` 按地址的主机认平台；认不出的封面按原图用。
- 新的缓存键：用 `providerStorage.ts` 的 `online_provider_<id>_...` 前缀就不用改；新的前缀要登记到 `src/services/repositories/cacheRepository.ts` 的 `getCacheTableName` 和 `matchesCategory`。

### 不用改的

- 登录界面 `src/components/login/`：平台的记号（`mark`）、标题、说明、失败说明都由 provider 声明，界面经 omni 去问。
- 登录失败的分类和请求时限（`login/`）。
- 账号状态：`src/stores/useOnlineProviderAccountStore.ts`、`providerAccountCache.ts`、`account/accountRead.ts`。
- 平台切换：`omni.ts` 的 `getProviderSummaries` 按注册表列出。
- 设置页。
- 探索页的界面和页面数据（`src/components/app/home/explore/`、`src/stores/useExploreFeedStore.ts`）。

### 由 mod 提供平台

不改内建代码、由 mod 加一个平台的做法，见 [`docs/folium/api.md`](../../../docs/folium/api.md) 和 [`docs/folium/contributing.md`](../../../docs/folium/contributing.md)。这条路还是实验接口，能力比内建平台少，动手前先读 `contributing.md` 开头说的接口边界。

## Public contract

调用前先看 `omni.ts` 的方法和 `src/types/onlineMusic.ts` 的类型。常用入口按能力分组：

| 能力 | Omni 方法/区域 | 结果/边界 |
| --- | --- | --- |
| provider 状态 | `getProviderSummaries`、`getActiveProviderSummary`、`getProviderCapabilities` | `useOnlineProviderAccountStore` 提供 active provider 与账号快照 |
| 账号/二维码 | `readAccount`、`signOutAccount`、`startLogin`、`checkLogin`、`confirmsLoginInBrowser`、`openLoginPage` | provider auth adapter；不要在 UI 直接保留 raw session。登录有两种样子，轮询、取消、过期是同一套：扫二维码（provider 有 `createQr`）、只在浏览器里确认（provider 有 `openLoginPage`、没有 `createQr`，`startLogin` 回的图片是空串；登录一开始界面就打开那个页面，弹窗里只留一个“重新打开浏览器”的按钮；provider 自己已经打开页面的（`opensLoginPageItself`），界面不再打开，也没有这个按钮）。Spotify 和 YouTube Music 是后一种。平台自己的记号（`mark`）、登录标题和说明、只在它身上才说得通的失败说明（`getLoginTexts`）、可以在登录窗口里重启的本地服务（`localService`）都由 adapter 声明，界面经 `getProviderMark`、`getLoginTexts`、`getLoginLocalService` 来问；`src/components/login/` 里不出现任何平台的名字。登录为什么没成功：某一步抛了错时 facade 问 provider 的 `describeLoginFailure`，`checkLogin` 回 error 状态时 provider 自己带上 `failure`；provider 把自己的错误说成共用的事实或者点名是哪一种情况，`login/loginFailureCase.ts` 再分成有名字的情况（它不认识任何平台），登录会话（`library/core/account/providerLoginSession.service.ts`）把它放进账户快照的 `login.failure`，交给登录窗口。登录等着的请求里自己没有时限的（网易云、QQ、酷狗的取 key、取二维码、检查这三个），由各自的 transport 套上 `login/loginRequestLimit.ts` 的 20 秒时限，到点算作「没有回应」；要一首歌的地址、读集合歌曲的请求（网易云的 song/url/v1、playlist/track/all、album，QQ 的 music_play、song_list_detail、user_playlist_detail、user_liked_songs、album_info；QQ 要地址时一档超时就不再试下一档），套上 `failure/onlineRequestLimit.ts` 的时限，到点算作「连不上」；时限比那个平台的后端最慢的正常回答还长，由各自的 transport 定（网易云 60 秒，QQ 70 秒，原因写在那里）；别的请求不加 |
| 搜索 | `searchSongs`、`searchProviderSongs` | 普通搜索按 active provider；显式 provider 或跨 provider 用第二个方法。可选的 `context` 参数（`ProviderSearchContext`；`searchSongs` 的第三个、`searchProviderSongs` 的第四个参数）里的 `session` 把翻页互不干扰的调用方分开，不给就是宿主自己的界面：在两页之间留着读到哪儿的 adapter 按会话分开存，别的 adapter 不看它 |
| 用户库 | `getUserPlaylists`、`getUserAlbums`、`getLikedSongIds`、`getProviderLikedSongIds`、`accountMoment`、`getCloudCollection` | 统一 `OmniCollection` / page 类型，账号快照可先展示再静默刷新。喜欢的歌读回来是 `{ ids, whole }`：adapter 在自己的上限处停下、或者说不准读没读到底时 `whole` 是 `false`；读不出来的一页必须抛错，不能当成更短的或空的列表交回。读账号的地方不自己写 `likedSongIds`：`account/accountRead.ts` 把读到的结果交给 `applyLikedRead`，由“修改”一行说的那条规则决定账号里留下什么；读失败就不交，账号里的保持原样；快照随后按 store 里此刻的 `likedSongIds` 存。回到 Folia 的窗口、进入主页这两个时机（`accountMoment`）不直接读整份：先向当前平台要“喜欢的歌”的数目（adapter 的 `getLikedSongCount`，一次请求，没有便宜办法的 adapter 不实现它），和手上的数目不一样才把喜欢的 id 整份读一遍；什么时候读只在 `account/readMoments.ts` 一处决定（见下面 `account/` 一条） |
| 推荐 | `getHomeFeed`、`getPersonalFm`、`supportsDailySongs`、`getDailySongs`、`getRecommendationHistory*`、`dislikeSong` | 首页推荐与历史推荐仍由 Omni 路由；日推入口按能力显示，空结果不隐藏入口；私人 FM 一首歌都没交回时不出这张卡片（点了也没有可播的歌） |
| 播放/歌词 | `getSongDetail`、`getSongDetails`、`canPlaySong`、`getAudioSource`、`getAudioQualityLevels`、`resolveAudioQuality`、`getLyrics`、`getChorusRanges`、`getAlternateArtistName` | 输出 `OmniAudioSource` / `OmniLyricsResult`；Navidrome 歌词走独立 service。`getSongDetail` / `getSongDetails` 收这首歌的 `UnifiedSong.id`，也收它的 `sourceRef.mediaId`，两者不同的平台在自己的目录里两种都接受。`getSongDetails(providerId, ids, { run? })` 按 id 查多首，每个 id 按入参顺序回一项 `OmniSongDetail`：`found`、`missing`（provider 答了、没有这首）、`failed`（为它发的那次请求失败，带 provider 的错；逐首问时一首失败不影响后面的）、`skipped`（调用方的 `run` 拒绝了这次或之前的请求、或不再等它，带 `run` 的拒绝；后面的都不再问）。adapter 有 `playback.getSongDetails` 就成批问：一批最多 `playback.songDetailsPerRequest` 个（不写就是全部一批），一批接一批，每批经 `run` 一次、一批失败不影响别的批（它拒绝的回答要抛错，不能回一串 null），没有就逐首问 `getSongDetail`，不并发；`run`（可选，`OmniRequestRunner`）包住 omni 对 adapter 的每一次调用（一次批量、或一首），由调用方计数和限流（`folium.omni` 的闸门）；`capabilities.songDetail` 为 false 的 provider 不能按 id 查歌（不写按能查）。`getLyrics` 的 `extensionHooks: false` 交出 provider 的歌词（副歌已标），不经扩展层改写。音质档位：档位从低到高是 `standard`、`high`、`ultra`、`lossless`、`hires`。`OnlinePlaybackProvider.audioQualityLevels`（可选）列出这个 provider 真正分得开的档位，不写就是 `standard`、`high`、`lossless`、`hires` 四档；`ultra` 只属于把它列出来的 provider（现在只有 YouTube Music，而且只对会员列出），列表可以随账号变，所以每次用到时现读。控制面板的音质选项只显示当前 provider 列出的档位（`getAudioQualityLevels`）。存的偏好仍是一个与 provider 无关的值，不迁移；它不在某个 provider 的列表里时，亮起的按钮和实际去要的档位都是不高于它的最近一档（`resolveAudioQuality`；`getAudioSource` 按歌曲所属的 provider 统一换算后再交给 adapter），所以存着 `ultra` 时，没列它的 provider 都按 `high` 去要。`getAudioSource` 交出地址时记下这个地址是按哪一档去要的、provider 有没有把它标成试听片段（`ProviderAudioSource.preview`；内存里，最近 200 个），`levelOfAudioSource(url)` 和 `isPreviewAudioSource(url)` 按地址查；扩展换进来的地址档位不明，也不算试听。片段还可能从歌中间开始：provider 在 `ProviderAudioSource.clipStartMs` 里写起点（毫秒，只在 `preview` 时有意义，不写就是从歌头开始），omni 按同一个地址记下（`previewClipStartMsOfAudioSource`），播放的歌词时钟加上这个偏移（`usePlaybackVisualizerBridge.ts`），进度和时长仍是片段自己的。有一个例外（2026-10-09）：列出了档位的 provider 在交回的 `quality` 里写的是它列出的另一档时，记的是它写的那一档（YouTube Music 的歌在 `ultra` 取不到、按 `high` 给的时候）；不这样的话，那份文件会顶着去要的那一档的名字存进媒体缓存，以后一直当那一档播。没列档位的 provider 不变，仍记去要的那一档。媒体缓存存一首歌时用它记下档位，播放只用和选项同一档的那一份，见下面 `resourceCache.ts` 一条 |
| 听歌上报 | `canReportPlayback`、`reportPlayback` | 只有声明 `playbackReports` 的 provider 支持（当前仅网易云）；时长必须是真实累计播放秒数，频控在 `playbackReportGate.ts` |
| 可用性 | `getSongAvailability`、`getSongReplacement` | 静态可用性只由 provider 的显式信号给出，`state: 'unavailable'` 只表示下架（taken-down），权限 / 付费 / 地区限制是 `unknown` + `reason: 'restricted'`；一次播放失败按 `failure/onlineFailureCase.ts` 分成有名字的情况，永不回写可用性、预取或缓存 |
| 集合详情 | `getCollectionTracks`、`getCollectionDetail`、`getAlbumDetail`、`getArtistDetail`、`getArtistSongs`、`getArtistAlbums` | 按 collection 的 `providerId` 路由 |

## Provider and cache files

- `providerRegistry.ts`：注册、查找、按歌曲 `sourceRef` 选择 provider、能力检查。
- `bodian/bodianProvider.ts`：波点 adapter；`bodian/bodianTransport.ts` 通过受限 IPC 连接 `electron/bodian/bodianApiBridge.cjs`。
  桥接调用固定版本的 `bodian-music-api`，协议实现在独立仓库维护；Folia 负责加密存储与媒体策略。没有系统加密时存着的登录和 YouTube Music 一样处理（`electron/bodian/session.cjs`）；请求被拒时这次读不出的那份留着，用户退出登录时也删。
  `bodian/bodianCatalog.ts` / `bodian/bodianLibrary.ts` 处理集合与用户库，`bodian/bodianNormalize.ts` 统一数据，凭据不返回 renderer。
- `ytm/ytmProvider.ts`：YouTube Music adapter，仅桌面端；`ytm/ytmTransport.ts` 通过受限 IPC 连接 `electron/ytm/ytmApiBridge.cjs`。
  YouTube Music 的文件各层都收在自己的 `ytm/` 目录里：这里的 `ytm/`、`electron/ytm/`、`test/unit/ytm/`。
  登录在用户自己的浏览器里做（2026-10-09；只跑过单元测试，没有在应用里试过）：主进程打开电脑上装的 Chrome、Edge、Chromium、Brave，或者 Chrome 的 Beta、Dev、Canary 版、Helium 的一个单独窗口（按这个顺序找，四种稳定版在前；先找装给整台电脑的位置，这几种都找过才找装在用户自己目录下的，Windows 上 Chrome Canary 只装给一个人，只在用户自己目录下找；Linux 上按命令名在 PATH 的绝对路径里找，新加的几种是 `google-chrome-beta`、`google-chrome-unstable`（Dev 版）、`google-chrome-canary`、`helium`（Helium 官方的 deb / rpm）和 `helium-browser`（AUR 的 helium-browser-bin）。各个位置的出处写在 `electron/ytm/browserSignIn.cjs` 的 `BROWSERS` 上面；2026-10-22 加的这几种只跑过单元测试，没有用真的浏览器试过；日志 `[Ytm] Sign-in can use <浏览器名> (<可执行文件名>)` 写出用了哪一种），用户在里面登录 Google，看到 YouTube Music 显示自己的账号后关掉那个窗口，应用再读出这次登录（桥接操作 `web_login_start` / `web_login_check` / `web_login_open` / `web_login_cancel`；同一时间只有一个，没有 key，窗口关了却没登录、或过了 10 分钟，都算过期）。这些浏览器一个都没装时（`web_login_start` 报 `unsupported`），这一次登录失败，没有别的登录方式：弹窗显示“登录 YouTube Music 需要安装 Chrome（Beta、Dev、Canary 版也可以）、Edge、Chromium、Brave 或 Helium。”（`ytmProvider.ts` 的 `getLoginTexts().caseNotes['no-browser']`，文案键 `home.loginNoBrowserYtm`）。登录的凭据由主进程用 `safeStorage` 加密保存，不进 renderer。
  旧版本存下的设备登录（`electron/ytm/session.cjs`，键 `YTM_SESSION_V1`）不再使用：每次运行的第一个请求里这个键有值就删掉；能解开而且里面有 `refresh_token` 时同时向 Google 撤销授权（不等答复，15 秒没有答复就放弃，失败不重试），解不开的只删不撤销；两种情况各记一行日志。存储读写抛错时记一行警告（`[Ytm] The device sign-in of an earlier version could not be removed: …`），这次请求照常进行，这次运行里不再试。存着的浏览器登录不动。浏览器登录存下的是这几项（`electron/ytm/webSignIn.cjs`，`YTM_WEB_SESSION_V1`，整份加密）：`version`、发往 youtube.com 的 Cookie 请求头 `cookie`、发请求用的浏览器名 `userAgent`、存入时间 `storedAt`，和账号 `user`（Google 账号 id 的摘要 `id`、昵称 `nickname`、头像地址 `avatarUrl`、是否会员 `premium`）。这次运行没有系统加密（没有可用的加密，或是 Linux 的 `basic_text`）时：存着的登录读不出，留着不删，`login_status` 报 `unavailable`；这次的新登录只在这次运行里有效，存着的旧登录照样删掉，下次启动不会回到旧账号。加密能用、只是这一次写不进去（文件一时被锁住）时，存着的留着；是另一个账号的就删掉（波点、Spotify 也一样）。加密能用却解不开的（别的系统账号封的、内容坏了），当作没存。从浏览器读到的 cookie 拼成请求头后，先看它能不能当请求头的值（只能有可见 ASCII 字符和空格），不能就算这次登录失败（`web_login_check` 答 `error`），不拿去发请求，也不保存。账号的请求头（`Cookie`、`Authorization`、`X-Goog-AuthUser`、`X-Goog-PageId`）只随发往 `www.youtube.com` 和 `music.youtube.com` 的请求走（`guardAccountHeaders`）；带着这些请求头的请求不跟随重定向（`redirect: 'error'`），对方答重定向时这次请求失败。在 Electron 43.7.5 里用两个本机服务器量过（2026-10-09）：跟随重定向时，另一个源收到了 `Authorization`、`X-Goog-AuthUser`、`X-Goog-PageId`（没有收到 `Cookie`）；设成 `'error'` 后请求失败，另一个源什么都没收到。请求进行中用户登出或换了账号的，这次请求报 `unavailable`，答复不交给渲染端。日志和错误里没有 cookie、账号名和资料夹路径。登出只删掉本机存的这一份，不会结束 Google 那边的这次登录（那些 cookie 到期前仍然有效）；要结束它，到 Google 账号的“安全性”→“您的设备”里把这一次登录退出。登录用的浏览器资料夹（`userData/ytm-sign-in`，登录后里面是用户整个 Google 会话）在一次登录结束时删掉，不管怎么结束。启动浏览器之前应用先在里面放一个自己的标记文件（`folia-sign-in-folder`）；删除时认这个标记（没有标记的旧版本留下的认 `Local State`，空的和不存在的也算），先删别的，最后删标记和资料夹，所以删到一半失败后下次还认得它。一次删除总共最多 4 秒（失败就隔 250 毫秒再删一遍），到时间答“没删掉”，之后不再继续删。应用退出时先结束那个浏览器（`shutdown`），并把退出最多推迟 3 秒，等资料夹删掉；没有浏览器要结束、也没有登录的资料夹正在删时不推迟。上一次运行留下的资料夹，在本次运行的第一个请求时删；删不掉的（包括本次运行里登录结束时没删掉的）随后面的请求再删，直到删掉（`webSignIn.cjs` 的 `sweepIfLeft`）：这样随请求的删除，两次开始之间至少隔一分钟，上一次还没结束时不开始下一次；这一分钟不从登录结束时那次失败的删除算起，所以那之后的第一个请求可能马上再删。登出和 `web_login_start` 各自另删一次，不受这一分钟限制。删之前先结束上一次运行留在这个资料夹上的浏览器（应用没有正常退出时会留下）：看一遍所有进程的命令行（Windows 用系统自带 PowerShell 的 `Get-CimInstance Win32_Process`，资料夹路径放在环境变量里传进去；macOS 和 Linux 用 `ps`），只结束命令行里的 `--user-data-dir=` 正好是这个资料夹的进程，不凭进程号。结束不了，或资料夹删不掉时，`web_login_start` 报 `unavailable`，不在这个资料夹上再开一个浏览器。资料夹里有东西、却既没有标记也没有 `Local State` 的，当作不是应用自己的，不删；这时 `web_login_start` 同样报 `unavailable`，要用户自己把 `userData/ytm-sign-in` 删掉。删除和结束浏览器这两段只在 Windows 上用替身进程试过，没有用真的浏览器试过，macOS 和 Linux 上没有运行过。账号、音乐库（`user_playlists` / `user_albums`）、歌单（`playlist`）、探索页（`explore`）、收藏（`list_save` / `list_saved`）、歌单增删（`playlist_edit`）和歌曲的喜欢（`song_like`）都走网页客户端（web 会话，不加载播放器脚本，从不用来取流）；没有人登录时这些操作报 `auth-required`（`login_status` 答空）。YouTube 不再认这份登录有两种答法：状态 401，或状态 200 但按游客答复（看答复里的 `logged_in` 标记）；遇到时再问一次账号，两次都不认才删掉存着的登录，只有一次不认报 `unavailable`。登录窗口由 `web_login_start` 自己打开，关掉就是登录结束，所以界面不在开始时再开一次，也没有“重新打开浏览器”的按钮（`auth.opensLoginPageItself`）；macOS 上关掉窗口浏览器不会退出，说明文字换成让用户退出那个浏览器（没有在 macOS 上试过）。
  主进程用四个 youtubei.js 会话 guest、player、web、member（guest 和 web 按应用的界面语言请求页面，所以歌名、歌手名和界面是同一种语言，搜索结果和歌单里也一致：简体中文用 zh-CN，英文用 en，印尼文用 id。一个会话只用一种语言，界面语言变了，下一次请求就各自重建。各语言的页面会改写一部分歌手名：英文页把中文歌手名写成拼音，zh-CN 页给少数西方歌手起中文名，20 个里 1 个；音乐库卡片的歌单歌曲数按这三种语言的写法读，只认卡片第二行最后一段里末尾的那个数，`webPages.cjs`）：未登录的 guest 负责搜索、专辑、歌手等公开页面；未登录的 player 以 YouTube Music 网页播放器的身份取流；web 是上一段说的浏览器登录的账号，负责账号、用户库、歌单、探索页和写操作；member 是同一个账号加播放器脚本，在未登录的网页播放器取不到时接手 `standard` 和 `high` 的取流，不要求会员（网页播放器答应了、下载却失败的歌，下一次请求先走 member），`ultra` 只走它（见下面“超高档”一段）。这条后备没有在真实账号上对游客被拒的歌（比如有年龄限制的）量过，只量过游客也取得到的歌它取得到（`high` 的 itag 251）。有没有人登录，在轮到 member 路线时才判断：问网页播放器的那一两秒里听众可能登录或登出；没有人登录时跳过这条路线。两条路都取不到时报未登录的网页播放器给的原因，不报 `auth-required`；member 路线自己不判定登录失效，那由走 web 会话的请求（`withWeb`）判定。四个会话的请求都不用 cookie 罐：Google 下发的 cookie 不保存也不回传。账号放在请求头里：web 和 member 会话是存下的那条 Cookie 请求头和 youtubei.js 用它算出的 `Authorization`（SAPISIDHASH）；guest 和 player 不带账号（youtubei.js 在每个会话的第一个请求里自带一条自己生成的 cookie，内容是随机访客 id 和时区）。一次请求最多等会话 45 秒；会话继续建，建好后给之后的请求用。建了 3 分钟还没好的当作卡死，下一次请求重建。
  网页播放器的音频要带一枚 proof-of-origin 令牌才放行，令牌由 Google 的 BotGuard 脚本在隐藏的沙箱页里生成（`electron/ytm/poToken.cjs`，依赖 `bgutils-js`）。
  音频地址是应用自己的 `folia-ytm://audio/<id>/<档位>?k=<key>`，每次 `getAudioSource` 都换一把 key；主进程把整首歌下进内存缓冲，再按 Range 应答。网页播放器的文件按 10 MiB 一段依次请求：一次要整个大文件时，音频服务器只按播放速度发（52 MB 的文件实测 40 KB/s）。下载 30 秒没有新数据就判失败，下一次请求重新取流。一个地址只代表一个文件：换路线后文件不同（长度或类型变了）时，旧地址答 503，渲染端换新地址后按时间续播。下载中途失败后，音频元素会对同一个地址重问，约 30 次失败才报错（每次立刻失败时是半分钟）；这些请求距离这首歌上一次取流尝试不足 3 秒时不再问 YouTube（答网络错误，元素继续播已有的部分并稍后再问），所以短暂断网能自己恢复。重问持续 30 秒仍没取到流，之后的重问直接答 503，交给渲染端换地址或跳过。重问停下超过 10 秒（听众切走了，或元素已经报错）就不再算进这 30 秒：之后再用这个地址，会重新问 YouTube。登出、一次浏览器登录被另一次换掉、或被 YouTube 拒绝而删掉时，只作废以账号身份（member 路线）取的缓冲和地址，旧地址答 503：`ultra` 的全部，和 `standard` / `high` 里由 member 路线取的；未登录的网页播放器取的照旧能用。第一次登录不作废任何地址。同一首歌的失败下载 5 分钟内最多换 4 次新的取流答复，之后答 503（元素约一秒内报错，渲染端跳到下一首）；没问成的尝试不计数。取流请求 60 秒没有答复按网络错误处理。某首歌在当前地区不可播时报 `not-playable`（跳过这一首），不报 `region-restricted`（那个错误码会停掉整个队列）。
  音质（2026-10-08）：账号不是会员、或者没有人登录的时候，adapter 只列两档（`playback.audioQualityLevels` 回 `['standard', 'high']`）：音质选项在 YouTube Music 下只有 `standard` 和 `high` 两个按钮，存着的偏好是 `ultra`、`lossless` 或 `hires` 时亮的是 `high`，交给主进程的也是 `high`。会员多出来的一档在下一段。档位随 `audio` 操作交给主进程（参数 `quality`），由 `ytmApiBridge.cjs` 的 `pickAudioFormat` 选格式：`high` 取原声轨里码率最高的一种，itag 774 和 141 除外：这两种是 `ultra` 的，会员账号不论按哪一档去要都会被给到，除掉它们，`high` 不论由哪条路线取都是同一份文件（一首歌只给了这两种时照取）；`standard` 取 itag 250（Opus，约 64 kbit/s），没有它时取 40 kbit/s 以上的 Opus 格式里离 64 kbit/s 最近的一种（一种 Opus 都没有时在全部格式里取），只给了一种格式时两档都是它。“先取原声轨（不要配音、不要响度压缩的那一种）”对两档都成立。实测（未登录，一个公开视频）给的是四种纯音频格式：itag 249 Opus 约 48 kbit/s、250 Opus 约 64、251 Opus 约 130、140 AAC 约 130。主进程的内存缓冲按“歌曲 id + 档位”存，地址里带档位，所以在一档缓冲过的歌换另一档去要时会重新取流、重新下载。日志 `[Ytm] Plan for <id> at <档位>: the <路线> route, itag <n> at <码率> kbit/s` 写出每次选中的格式，渲染端的 `[Ytm] Audio for …` 一行也带档位和格式。2026-10-08 用应用自己的桥、未登录、同一个公开视频各要一次：`standard` 选中 itag 250（61 kbit/s），地址交出的文件 1,628,559 字节；`high` 选中 itag 251（129 kbit/s），3,433,755 字节；两个文件不同。两档的差别还没有在应用里听过。媒体缓存（共享代码，所有不自己存文件的平台都一样；2026-10-08 改，只跑过单元测试，还没有在应用里试过）：整首播完的歌、和自动混音分析时整首读下来的歌（都要开着“缓存歌曲”）存进媒体缓存时，旁边记下这份文件取自哪一档（键 `audioLevel_<歌曲键>`，档位是交出那个地址时去要的那一档，不是存的那一刻选项停在哪）。播放只用和当前选项同一档的那一份：存着的是另一档时不播它（日志 `[Cache] Copy of <歌曲键> passed over: fetched at <档位>, asked for <档位>`），照没有缓存的歌那样取地址播放，这首歌播完后用这一档的文件盖掉原来那一份（新文件得是整首歌才盖，规则在下面 `resourceCache.ts` / `resourceKeys.ts` 一条）。记档位之前存下的文件没有档位，选哪一档都照旧播它。自动混音分析和人声分离不看档位，存着哪一份就读哪一份。
  超高档 `ultra`（2026-10-09；只跑过类型检查和单元测试，没有在应用里试过，写这部分代码时没有向 YouTube 发过请求）：YouTube Music 给会员多两种约 256 kbit/s 的格式，itag 774（Opus）和 itag 141（AAC），都标着 `AUDIO_QUALITY_HIGH`（实测 2026-10-09，一个账号的一首歌；同一个请求在这个账号成为会员之前没有这两种）。这一档只在登录的账号是会员时列出（`ytmProvider.ts` 的 `audioQualityLevels` 是一个 getter，读 `ytmAccount.ts` 记下的“是不是会员”），顺序排在 `high` 和 `lossless` 之间，界面上叫“超高”；列出时，存着的偏好是 `lossless` 或 `hires` 亮的也是它。`pickAudioFormat` 在这一档只取标着 `AUDIO_QUALITY_HIGH` 的 itag 774，没有时取 itag 141，都没有就算这一档没有，不拿别的格式顶替。取流走 member 会话：浏览器登录的同一份 Cookie、同一个浏览器名、同一个 `guardAccountHeaders`，另外加载播放器脚本；它以 YouTube Music 网页播放器的身份问 `/player`，带一枚和未登录时一样生成的令牌。member 会话的请求是唯一带着账号 Cookie 的取流请求：按 `ultra` 去要时只对存着的会员账号发；按 `standard` / `high` 去要时，未登录的网页播放器没取到而且有人登录才发，不看是不是会员（日志 `[Ytm] Plan for <id> at <档位>: the member route, itag <n> at <码率> kbit/s, <毫秒>ms (web: <原因>)`）。给 `standard` / `high` 当后备这件事，没有在真实账号上对游客被拒的歌量过。音频文件本身和未登录的网页播放器一样下载：用应用自己的 fetch 请求格式自带的地址，请求头只有 Range，账号的请求头到不了 googlevideo.com（这个会话自己发往别的域名的请求，`guardAccountHeaders` 也会把账号的四个请求头摘掉）。不向 YouTube 上报播放。成功时的日志是 `[Ytm] Plan for <id> at ultra: the member route, itag 774 at <码率> kbit/s`。
  取不到这一档就照实按 `high` 给：没有人登录、存着的账号不是会员、member 路线被拒绝或出错、答复里没有这一档的格式，这首歌都改按 `high` 取（先问未登录的网页播放器，取不到再问 member 路线；日志 `[Ytm] No plan for <id> at ultra after <毫秒>ms (member: <原因>)` 和 `[Ytm] <id> is served at high in place of ultra`），并且处处当作 `high` 的那一首：内存缓冲存在“id + `high`”下（和直接按 `high` 去要的是同一份，不重新取流），地址里写的是 `high`，`audio` 的答复多一个 `level: 'high'`（给的档位和要的不一样时才有这个字段），`getAudioSource` 交回的 `quality` 是 `high`，渲染端日志写 `at ultra (served at high)`，媒体缓存也按 `high` 记（omni 的例外，见上面 facade 表“播放/歌词”一行）。代价：这样一首歌在选项停在“超高”时每次播放都重新去要，存着的那一份档位不对、不拿来播（取不到地址时仍然播它）。
  账号是不是会员：网页客户端的账号列表不说，读的是 `/account/account_menu` 里的图标（`webPages.cjs` 的 `premiumFromMenu`）。有 `UNLIMITED`（升级会员的入口）就不是会员；没有它而有 `MONETIZATION_ON`（付费会员一项）就是会员；两个都没有、或者答复没有标成是给登录账号的，算没说，存着的不动。这条规则是从一个账号成为会员前后各读一次推出来的，别的账号、别的国家、家庭方案都没有验证过。读的时机：一次浏览器登录确认之后、主进程把它告诉渲染端之前（`web_login_check` 答 `confirmed` 时读，最多等 10 秒，超过就先答、读到后再存）；之后每次取流（`audio` 操作，不管哪一档）时，这次运行里还没读到答案就在后台读一次，不耽误那首歌。读到答案（是或不是）后这次运行不再读；没读到（请求失败、菜单没说、答复不是给登录账号的）就等之后的取流再读，两次读至少隔 5 分钟。读到的写进存着的登录（`user.premium`）。`login_status` 仍然只读存着的、不上网，所以后台读到的变化要到下一次 `login_status`（重启，或者界面再读一次账号）才显示出来。member 路线拿到一首可播的歌的答复、里面却没有这一档的格式时，不改存着的会员标记：这首歌按 `high` 给，同时再读一次账号菜单（同样至少隔 5 分钟），是不是会员只由菜单决定（只有读菜单这一处写 `user.premium`）。这首歌在它那份 `high` 的取流答复还有效期间（没开始下载的 30 分钟内，或缓冲还在）记作没有这一档，再按 `ultra` 去要时不带 Cookie 去问，直接按 `high` 给，日志只有 `served at high in place of ultra` 一行。没有测过会员账号下是不是有歌本来就不给这两种格式（比如用户自己上传的视频）。
  重启之后：渲染端把“登录的账号是不是会员”存在 localStorage（键 `folia_ytm_account`，内容 `{ premium }`；旧版本存的还带 `signIn`，是 `'tv'` 的按不是会员算），模块加载时读回，所以会员在读到 `login_status` 之前要的第一首歌就按 `ultra` 去要；读到 `login_status` 之后以它为准；浏览器登录确认时按 `web_login_check` 答复里的账号记，不另发请求；没有人登录、账号因登录失效离开（adapter 的 `auth.signInRanOut`，由 `account/accountRead.ts` 调）、登出时（请求发出之前删一次，答复之后再删一次），都删掉。主进程走不走 member 路线只看它自己存着的登录，不看渲染端怎么说。
  `ytmCatalog.ts` / `ytmLibrary.ts` 处理集合与用户库，`ytmNormalize.ts` 统一数据并把 YouTube 的翻页 token 换成 offset。
  歌单的歌有两种读法（`ytmCatalog.ts` 的 `ytmPlaylistTracks`），读的都是 YouTube Music 网页客户端的歌单页（`VL<id>`），一次都给 100 首：以账号身份读（桥接操作 `playlist`，2026-10-09）；以 guest 身份读（桥接操作 `public_playlist`，实测 2026-10-07，只测了一份 182 首的公开歌单和一张 12 首的专辑；那份歌单 2 次请求约 0.47 秒）。guest 读到的歌和顺序，只和应用已不再使用的 TV 客户端的登录读法比过（2026-10-07，相同），没有和现在的登录读法比过。先用 guest 读，第一页没有内容（私密歌单约 40 毫秒就答空）或第一页读失败时改用登录读法，后面的页读失败就是失败；翻页的 token 属于哪种读法由 token 自己的前缀决定。账号自己建的歌单（卡片带 `isOwned`）和“喜欢的音乐”直接用登录读法：前者刚改完就要看到结果，guest 读法多快反映改动没有测过；后者永远不公开。 歌一页一页到达时歌单页不挪动视图：`GridView` 只在第一次出现卡片、筛选变化、卡片间距变化时居中（原来每到一页都把视图拉回第一张卡片，这里一页 100 首，滚到哪儿都会被拽回去）。
  日志按 `docs/client-logging.md` 的约定都以 `[Ytm]` 开头。两个进程的行都进应用内日志面板（设置 → 开发者）。渲染进程记：每首歌取流走的路线和耗时、自带歌词有没有、另一种语言页面上的歌手名、音乐库刷新结果（歌单数和其中属于账号自己的个数）、探索页每次读到的栏数和条目数、失败的请求及其错误码。主进程记：每次取流方案（含前一条路线被拒时 YouTube 的原话）、下载完成或中断在第几个字节、会话建立耗时、登录状态的变化、每次专辑收藏和歌单增删、被问到的专辑是否已收藏、合辑读到几首、歌单改动被拒时 YouTube 给的状态词、旧版本设备登录的清理。界面拿到的错误句子里也带着 YouTube 的状态词（如 `LOGIN_REQUIRED`）。写进日志的值只有歌曲 id、合辑和专辑的列表 id、路线名、字节数、耗时和固定句子（渲染进程的行另有歌名和歌手名）；异常自己的文字先经 `errors.cjs` 的 `describeError` 抹掉 http(s) 地址（含 JSON 转义的）、文件路径（盘符或 `\\服务器` 开头的，以及 `/Users/`、`/home/` 下的）和 32 位以上的长串，再截到 160 字符。
  自带歌词只有逐行时间（取自手机 App 的歌词页，网页版只有纯文本），逐字和翻译靠跨源匹配。各语言的页面对歌手名的写法不同（zh-CN 页的 Oasis 是“绿洲合唱团”，英文页的陈奕迅是 “Eason Chan”），歌词源只认其中一个；所以跨源匹配落空时，`lyrics.getAlternateArtistName` 向另一种写法的页面问一次这首歌的歌手名：歌手名里有非拉丁字母就问英文页（`song_detail_en`），否则问中文页（`song_detail_zh`），都是不经过会话的单条请求，自动匹配用问到的名字再搜一遍；问到的名字只是写法不同（歌单里的 “A & B”，歌曲页分开列成两位）时不算另一个名字，不再搜。问哪一页由名字本身决定，不看界面语言：队列和歌单里的歌可能是界面还是另一种语言时读到的。列表里显示的仍是界面语言那一页的名字。渲染端缓存的页面在界面语言变化时清空。
  探索页的图（`electron/ytm/webExplore.cjs`）：视频条目给的是它自己的 16:9 截图（卡片 800×450，行 400×225），其余条目给方图。图宽大于高的条目带 `wideCoverUrl`，就是条目自己的那张图，供版式按原比例放。
  探索页（`ytm/ytmExplore.ts`，桥接操作 `explore`）读的是网页客户端的页面（见下一段），只在登录后读：未登录的首页人人相同。YouTube 的栏整栏到达，没有栏内续页，只有页尾的续页（`explore` 的 `continuation`）；栏内还有后续条目的只有应用自己做的“与某首歌相似”的栏（`getSectionItems`，给的是已经读到的歌，不向 YouTube 要）。条目有四种：歌曲、歌手、歌单/专辑、合辑。合辑（mix）没有歌单页，它是 YouTube 按一个列表 id 临时排出的播放队列，用桥接操作 `mix` 以 guest 身份读（约 50 首），集合上带 `providerData.mix`，`getPlaylistTracks` 据此分流；只有列表 id 以 `RD` 开头的才算合辑，其他“点了就播”的列表按普通歌单读。同一个合辑的答复留 5 分钟，过期后只有从头读才换新的一份，翻页始终是同一份列表。一页里没有能显示的条目却还有续页时（第一页也一样：它的栏可能全是 `ytmExplore.ts` 去掉的那几栏），接着读下一页，最多连读 3 页，仍是空的就当作到底（`useExploreFeedStore.ts` 的 `readPageWithSections`）。

客户端的“音乐”页上做的，网页客户端的页面没有重新量过；网页客户端的栏没有栏内续页，有栏内续页的只有应用自己做的“与某首歌相似”的栏。YouTube 的这一页每次读几乎是同一批（实测 2026-10-07：同一账号隔几秒连读三次，第一页 12 个条目有 11 或 12 个相同），但多数栏后面还有（实测有续页的栏共 8 到 30 多个条目，续页一次给 6 个；20 栏里有 7 栏没有续页；整页不止 20 栏），所以只重读一遍是换不出东西的。还有一条更要紧的限制：YouTube 的续页 token 不认栏目，只认位置——一栏的续页是“页面上第 11 栏、从第 7 个条目起”，整页的下一页是“从第 8 栏起”；而页面每从头读一次，YouTube 就重新排一次栏目的位置。实测 2026-10-07：从头重读页面之后，拿重读前“专辑”一栏的 token 去取，回来的是 6 首单曲（那个位置上现在是另一栏），旁边单曲那一栏取回 6 张专辑；不重读页面时，同一个 token 在三分多钟里反复取，每次都是同样的条目。所以契约规定（`OnlineExploreProvider`）：游标只在页面下一次从头读之前有效。YouTube 的适配层（`ytmExplore.ts`）给每个发出去的游标带上“第几次从头读”的编号，拿旧编号的游标来问一律答“没有了”，不发请求。做法因此是：“换一批”平时不重读页面。每一栏显示自己排在当前这批后面的那些（已经读到的直接用，不够一批时用这一栏自己的游标再读一次），排到最后一个之后从头再来；续页读失败的栏这次不变，下次再试。同时最多三栏在读续页。只有当这一次换不出任何“从上次读页面以来没显示过”的条目时（每一栏都排到过头了），才把页面从头重读一遍，读到原来读到的那一页为止（一页一次请求，遇到没有可显示内容的页最多连读三页）：旧游标全部作废（重读失败时页面还留着旧游标，YouTube 的适配层对它们一律答“没有了”，再按一次“换一批”重读成功后恢复），每一栏换成平台现在在这个标题下给的条目和新游标，重读到的页面里没有的栏继续轮换自己已经读到的条目。栏目按标题对应；同一个标题有好几栏时，各自对应和自己已读条目重合最多的那一栏。没有别的可换的栏保持原样，不翻：只有一批条目、平台给回来的还是这一批的。用“更多”全部展开的栏，“换一批”时收回成一批、从头排起。续页读到的都是已经有的条目、但又给了下一个 token 时，这次不变，下次从那个 token 接着读。往下滚时读到的后面几页的栏目不会因为“换一批”被拿掉，所有栏目也都不换位置（即使应用记住的标题先后和现在站的顺序不一样）；所以列表不会变短，停在原来滚到的位置。重读时平台给的、页面上还没有的栏目加在最后（标题每次都换一种说法的栏目因此会每重读一次多一栏，这次会话里不会减少）；往下读到的某一栏如果页面上已经有了（标题相同、条目多半相同），不再放第二份。每一栏的条目是有限的（TV 客户端的页面上实测有续页的栏 8 到 30 多个）：换一到五次就全部显示过，之后只能轮换，直到 YouTube 自己更新推荐。第一栏换到条目较少的一批时高度不变（窗口宽 1024 以上；更窄时这一栏会变矮）。一批有几个，按这一栏第一次给了几个算（其中有被取消收藏而不显示的也算在内）。“换一批”读取期间如果切换了平台或页面被清掉，还没发出的续页请求不再发。同一页读失败后重试，列表留在原来滚到的位置（这时屏幕上是应用自己的两栏）；换账号或语言才回到顶部。读取期间旧的一页留在屏幕上变淡；读失败时旧页原样留着，按钮上多一个点，再按是重试。“换一批”是一个只有图标的按钮，不在列表里面：它叠在列表右上角，第一栏的标题行在那里给它留了位置（`data-explore-controls-room`），列表往下滚时它留在原处，滚上去的内容在列表上沿 56 像素内渐隐（列表的 `mask-image`，渐隐的长度随滚动从 0 长到 56），所以别的栏标题行右端的按钮经过它下面时是变淡的（没有完全消失：只有最上沿才全透明）。替换时栏目本身不动：界面按标题认栏目（每次读到的栏目 id 都是新的，页面上的栏目沿用第一次读到时的 id），标题留在原地，只换它下面的内容，旧卡片原地翻走、新卡片翻进来，从上到下一栏接一栏；多出来的栏目排在列表中间时在原位展开，排在列表末尾时直接出现（滚到底读到下一页也是这样：末尾的“正在读取”和“重试”一样高，新栏目来的那一刻列表只会变长，停在末尾的人不会被带着上下动）。三，合辑的卡片写“动态歌单”（`ProviderExploreItem.isMix`），和能收藏的歌单区分开。四，在应用里取消收藏的专辑或歌单，七天内不在探索页显示：YouTube 的“来自你的媒体库”一栏在专辑取消收藏之后仍然把它发过来（实测 2026-10-07，在应用已不再使用的 TV 客户端的页面上：现读的页面上有一张专辑卡片，它自己的页面说未收藏；持续多久没有测到），而栏目里没有任何东西能把这张卡片和推荐区分开。重新收藏就恢复显示。
  界面怎么动都写在 `src/components/app/home/explore/exploreMotion.ts`（用 framer-motion）：第一次看到的页面一栏接一栏升起，栏里的条目从右依次进入；“更多”按下后先在原位留出占位（横排 4 个；第一栏在列表末尾留一列 5 个）并把占位滚到开头（已经滚到头就不动），读到的条目再填进去（第一栏只为占位滚动：刚在这里播放的歌是不请自来加进列表的，那时不滚）；应用设置里关掉界面微动效（`uiMicroMotion`）时全部改为原地淡入。横排里移动的是卡片，不是它占的格子：横排停靠在格子边上，格子自己一动，横排会跟着滚。页面第一栏（`ExploreLead.tsx`）的高度不随条目数变：第一个条目放大，其余的在它右边按一列 5 行排成多列。列表够宽（704 像素起，也就是窗口 1200 像素宽起；窄于 1024 时列表在大条目下方，768 起）时一屏两列，否则一屏一列，每列正好占满，所以列表停在哪儿看到的都是整列，滚到尽头也是；只有一列时它占满整个宽度。看不见的列横向滚动去看，和别的栏一样用标题旁的左右箭头，但两端不做渐隐（没有露出半截的条目）（原来“更多”要来的条目排在下方，按一次多一块，条目多了这一栏越来越长）。这个列表停靠在每一列的列头上，列头是按位置放的空元素（`data-explore-post`），不是歌：停靠点如果是某一行歌，刚播放的歌把它往后挤一格，列表就跟着它滚走（实测：连着记 30 首，列表自己滚到了末尾）。所有条目都画出来，不在视野里的也画：开发版实测（2026-10-07，无头 Chromium），主页回到屏幕上到这一栏画完，8 首 43 毫秒、60 首 78 毫秒、300 首 384 毫秒；300 首时记一首新歌有一帧 144 毫秒。只画看得见的几列能省掉这些，没有做。
  应用自己的两栏（`src/components/app/home/explore/` 的 `ownSections.ts`，读 `recentPlays.ts`，由 `useRecentPlaysRecorder.ts` 写）：探索页最前面是“最近播放”和“再听一次”，都只来自在本应用里播放过的这个平台的歌，和账号在平台官方应用里听过什么无关，各平台一样。播放记录按平台、按账号分开，同一首歌只有一条 `{ song, at, heardAt, days }`：`at` 是最后一次播放的时间，`days` 是每天听过几次（`[第几天, 次数]`；一天从凌晨 4 点算起，按本机时区，所以听到后半夜的一晚算一天），`heardAt` 是最后一次算作“听过”的时间；最后一次播放之后留 30 天，每个账号最多 300 首（localStorage 键 `folia_recent_plays`，只存在本机）。“播放过”和“听过”是两回事，由 `useRecentPlaysRecorder.ts` 分别上报：一首在线平台的歌真正响够 5 秒算播放过（暂停和拖动进度不算），进“最近播放”；响够它的一半（最长按 4 分钟）才算听过一次，之后每再响够一整首再算一次，所以单曲循环、拖回开头重听都会接着算（单曲循环用的是音频元素自带的循环，歌没有换，应用不会重新开始跟踪它，只能靠累计响了多久来数）。歌的长度先看正在播的音频自己的长度，没有时看歌曲信息里的，都没有按 4 分钟；不到 10 秒的按 10 秒算。“最近播放”是其中最近 7 天内播放的，最新的在前。“再听一次”是最近 30 天里听过不止一次的，最多 30 首，按分量排：一天里听 n 次的分量是 log2(1+n)（1 次 1，2 次约 1.6，3 次 2，30 次约 5），每过 7 天减半，各天相加；分量一样时后播放的在前。这样算是为了两件事。一，只听几秒就切走的歌不算数：原来响 5 秒就算一次，切走两次的歌也会进这一栏。二，某一晚循环很多遍的歌不会一直排在最前：一晚听 30 遍的歌，和从那天起每天听一遍的歌相比，第 4 天起排到后面。同一次收听只算一次。同一次收听里一首歌可能被重新跟踪不止一次（播放器把它换到另一个播放槽、自动混音的过渡被取消、窗口在歌放到一半时重建，都会从零再数），而记录收到的东西分不出这些和“又放了一遍”，所以按时间算：距离上一次算它听过还不到这首歌的长度（上报这次收听时用的那个长度，随上报一起交给记录），它不可能已经放完一遍，算同一次收听，不加次数。同一次跟踪里接着响满一整首的那些（循环、拖回去重听）由上报的一方标明，不受这条时间规则限制。代价有三个。一首歌听过一半后切走、不到一首歌的时间又切回来再听一半，只算一次。长歌更明显：超过 8 分钟的歌听够 4 分钟就算一次，而这条规则看的是整首歌的长度，一小时的合辑一晚上分三次听，只算一次。单曲循环中途被重新跟踪（窗口重建、换播放槽）时，之后少算一次。歌的长度是每次检查时现问的：一开始不知道、后来音频报出更短的长度时，之前少算的收听在接下来几次检查里补上，每次检查最多上报一次。超过 300 首时去掉的是最久没播放的，不看听过几次。过了 30 天没播放的歌在读取时、下一次记录时去掉；30 天以前的收听不再算数（存着的在这首歌下一次被算作听过时去掉）；过了 7 天的在应用开着的时候下一次显示“最近播放”时从这一栏里去掉。早先的记录不带时间（存的是歌本身），第一次读到时按那一刻播放的算，并立刻带着时间存回去，免得每次启动都重新算；不带 `days` 的记录（当时数的是响够 5 秒的次数）按没有听过算。这两栏不属于平台的页面：“换一批”不动它们；歌全部在栏里，没有“更多”；平台的页面正在读、读不到、是空的时候它们都照样显示，平台页面的状态（转圈、重试）在它们下面。平台不一定知道这里放了什么（应用不向 YouTube Music 上报播放），它自己的收听记录也不进这两栏。YouTube Music 的页面上有它自己的这类栏，`ytmExplore.ts` 把它们去掉；它们除了标题没有别的标识（这一句里的实测都是 2026-10-07 在应用已不再使用的 TV 客户端的“音乐”页上做的，网页客户端的首页用不用同样的标题没有量过：和别的栏结构完全一样，翻页 token 里也只有栏的位置不同），所以靠标题认（`LISTENING_RECORD_HEADINGS`；实测 2026-10-07 - `spotify/spotifyProvider.ts`：Spotify adapter，仅桌面端；`spotify/spotifyTransport.ts` 通过受限 IPC 连接 `electron/spotify/spotifyApiBridge.cjs`。
  Spotify 的文件各层都收在自己的 `spotify/` 目录里：这里的 `spotify/`、`electron/spotify/`、`test/unit/spotify/`。
  登录在用户自己的浏览器里完成（`electron/spotify/signIn.cjs`）：应用打开 Spotify 的授权页，用户点“同意”，Spotify 把浏览器送回本机的 `http://127.0.0.1:5588/login`，主进程在一次登录期间（10 分钟）监听这个地址，拿到授权码后换成令牌（authorization code + PKCE，没有密钥）。用户不用输入、不用粘贴、不用自己注册开发者应用。应用对 Spotify 用的是它官方桌面客户端的身份（开源播放器共用的那个 client id）：自己注册的应用最多 5 个用户，还要在 Spotify 后台逐个登记。授权页上显示的应用名因此是 Spotify 自己的。端口固定为 5588（实测 2026-10-08 可用；别的端口 Spotify 认不认没有测到，它在用户登录之后才检查回跳地址），被占用时登录报 `unavailable`。令牌由主进程用 `safeStorage` 加密保存（`electron/spotify/session.cjs`），不进 renderer；renderer 拿到的账号 id 是 Spotify 账号名的摘要。没有系统加密时和 YouTube Music 一样：存着的读不出就留着、`login_status` 报 `unavailable`，这次的新登录只在这次运行里有效并删掉存着的。访问令牌一小时过期，到期前一分钟内的请求先续期（同时到来的请求只续一次）；请求得到 401 时续期后再试一次；向 Spotify 发的每个请求 30 秒没有答复算失败；Spotify 已经批准、读账号时网络出错的，登录不作废，下一次轮询再读；只有续期被 Spotify 以 `invalid_grant` 拒绝才清掉登录并报 `auth-required`（Spotify 的续期令牌从第一次授权起六个月失效，到时要重新登录），网络错误和别的拒绝都保留登录。登出只是忘掉令牌：Spotify 没有收回授权的接口。
  数据不走 Spotify 的公开 Web API：它对这种登录从第一个请求起一律答 429（实测 2026-10-08）。读的是 Spotify 自己的应用用的两个服务：查询服务（`api-partner.spotify.com/pathfinder`，一组有名字的查询，每个查询靠一个哈希值认，名字和哈希的清单是桥接层的 `QUERIES`，renderer 只能发清单里的，其中读账号名的那一个只有主进程自己用）和 `spclient`（一首歌的电台、歌词、账号套餐）。这两个服务没有公开文档，Spotify 改了就要跟着改；查询被换掉时 Spotify 的回答里带着 `PersistedQueryNotFound`，主进程把它记进日志（`[Spotify] query <名字> failed`）。请求带应用的界面语言（`Accept-Language`：zh-CN / en / id），栏目标题和歌单名跟着变。查询的回答原样交给 renderer，由 `spotify/spotifyNormalize.ts` 转成应用自己的歌曲和集合：Spotify 的每样东西都有 `spotify:<种类>:<id>` 形式的 uri，应用里的 id 是最后一段；同一首歌在不同查询里缺的字段不同（喜欢的歌 uri 在歌的旁边，专辑里的歌不带专辑，歌手热门歌的专辑没有名字），都在 `spotifySongOf` 里处理；歌单里不是歌的行（播客单集、读不出的条目、uri 不是所要种类的）去掉，翻页仍按 Spotify 自己的行数走；一整页都不是歌时接着读下一页，一次调用最多连读 5 页（应用把没有歌的一页当作列表到头）。
  音乐库（`spotify/spotifyLibrary.ts`）：歌单一栏是账号自己建的和收藏的歌单，最前面多一项“已点赞的歌曲”（id `liked`，带 `isLiked`，封面用最近点赞那首的封面）；歌单卡片带 `isOwned` 当且仅当 Spotify 说这个账号能改它的歌（自己的和受邀协作的）。歌单和专辑按 offset 翻页，要多少给多少（实测要 343 行，50 首的歌单整份返回），一次最多要 100 行。歌手页的歌是 Spotify 给的十首热门歌，没有下一页。
  搜索：Spotify 的搜索翻页不干净（实测 2026-10-08：每页都给足要的行数，其中约五分之一是前面给过的；它报的总数是“页大小加五分之一”；第二页起一律说没有下一页）。所以一次搜索从头往下走并留着，每页只交出没给过的歌（`spotifyProvider.ts` 的 `searchWalks`，按搜索词留最近 8 个；放不下时先丢只读过第一页的，给歌词找歌的搜索只读一页、不会回来，翻过页的是听的人正在看的），最多往下读 300 行；回到之前搜过的词接着原来读到的地方走，已经不留着的从头重走到要的那一页；同一个搜索的调用排队，不会两次要同一段。
  探索页（`spotify/spotifyExplore.ts`）全是 Spotify 自己按账号给的内容，分四段，读到哪段才向 Spotify 要哪段（下面的数字是实测 2026-10-08，一个很少使用的免费账号）：（1）Spotify 官方应用的首页（查询 `home`）：6 栏，每栏一个标题加歌单、专辑、歌手卡片，每栏给 10 个，各栏共有 6 到 50 个；账号自己的收听记录栏（类型 `HomeRecentlyPlayedSectionData`、`HomeShortsSectionData`）去掉，理由同上文“应用自己的两栏”；一栏的“更多”用查询 `homeSection`，它不管要哪个 offset 都给这一栏的前 20 个（换成网页播放器现在用的哈希也一样），所以每栏只有一批“更多”，内容是这 20 个里首页没给的那些。（2）关注歌手的新发行（查询 `queryWhatsNewFeed`，只要专辑类：2 张），标题是应用自己的（`home.spotifyNewReleases`）；读不到时这一栏不出现，页面照常往下。（3）Spotify 为这个账号生成的歌单（查询 `browsePage`，页面 uri `spotify:page:0JQ5DAt0tbjZptfcdMSKl3`，对所有账号相同）：9 栏共 138 个歌单，每个都带“为该账号生成”的标记（每日合辑、每周新发现、反复聆听、按歌手和按风格的合辑），没有一个出现在首页上，都能用 `fetchPlaylist` 打开（27 到 50 首）；这一页的翻页是真的（`sectionPagination` 的 offset 对页面上所有栏同时生效，100 个的一栏要第 51 到 100 个，给的是另外 50 个），每栏一批 20 个，“更多”的游标记着栏的 uri 和读到第几个；和首页同 uri 的栏不再出一次（一页里一个 id 只有一栏）；这个查询被 Spotify 拒绝或换掉时这一段不出现，页面照常往下到第（4）段，网络错误时这一页报失败、可以重试。（4）应用自己做的“与《某首歌》相似”的歌曲栏（那首歌的电台：桥接操作 `radio` 给出歌单 uri，再读它的歌；50 首，第一首是那首歌自己，再问一次是同一份；3 个电台共 150 首里 137 首不同）。种子依次是 `listened`（听者在应用里听过的 Spotify 歌）和账号在 Spotify 点赞的歌（最近的 50 首，读到这一段时才要一次；读不到时先用 `listened` 的种子，下一页再要，一个种子都没有才报失败）。一页 3 栏，一次从头读最多 9 栏（每栏向 Spotify 发两个请求）；一栏只收别的栏没有的歌，去掉种子自己和电台里重复的行，不足 12 首不成栏，只留整批（12 首一批，一般 4 批）；这些栏带 `changesWithRead`，栏的 id 和“更多”的游标每次读都是新的，上一次读的游标在这一次读里什么也拿不到。点赞不到 10 首的账号每次从头读用的是同一批种子，栏还是那几栏，只是栏里的歌换了先后。下一次从头读先用之前没用过的种子，全用过了先用最久以前用过的；一栏里先排之前各栏没交出过的歌，再排最久以前交出过的（用过的种子和交出过的歌记在各平台共用的 `exploreReads.ts` 里，见 `EXPLORE_ADAPTER.md` 规则 10；实测：第二次读到的 9 栏，首批 108 首没有一首在第一次的首批里）。Spotify 的栏各有一个各次读取都不变的 uri，用作栏目 id；隔几秒连读两次，首页和账号歌单页的栏目、条目和顺序都相同，所以每次从头读真正不同的是第（4）段。批的大小是配合“换一批”定的：探索页逐批走完每一栏、所有栏都没有新的一批了才把页面从头重读，20 个一批的最长一栏（5 批）和 12 首一批的相似栏（4 批）差一次就同时走完。Spotify 的首页和账号歌单页上没有单曲，全是集合。整页读到底是 22 个请求。
  电台页（2026-10-08 接上，`spotify/spotifyRecommendations.ts`，能力 `recommendations: true`；2026-10-08 在一个真实的 Premium 账号上跑过一遍读取，7 个请求：每日合辑认出来了、50 首，推荐歌单 35 个，FM 连要 4 次各 2 首、没有重复，丢弃一首后它所在电台剩下的歌一并丢掉并换了种子；页面本身还没有人看过）：三样东西都是 Spotify 自己按账号给的。私人 FM：一个接一个的“歌曲电台”（桥接操作 `radio`；种子和读电台的函数在 `spotify/spotifyRadio.ts`，和探索页“与某首歌相似”的栏共用）。种子是账号最近点赞的 50 首歌，加上探索页最近一次从头读时交来的 `listened`（`getPersonalFm` 拿不到 `listened`，所以本次运行里没打开过探索页时只有点赞的歌）。每次从还没用过的种子里随机取一首：同一首歌的电台每次都是同一份歌单，按固定顺序取的话每次启动都从同样的歌开始。`getPersonalFm()` 每次交出接下来的 2 首（队列因此总知道下一首是什么），一次运行里一首歌只交出一次，种子本身不交出；一个电台用完换下一个种子，种子和最后一个电台都用完时重读一次点赞的歌（期间新点赞的歌成为新种子）。`dislikeSong`（FM 的垃圾桶）不通知 Spotify：这首歌本次运行不再交出，它所属电台剩下的歌整个丢掉；已经交进播放队列的歌（最多两首）收不回来。红心走通用的 `likeSong`，就是 Spotify 的点赞。一个种子都没有（没有点赞，也没有听过）时 `getPersonalFm` 交回空表，首页不出私人 FM 卡片，不编造歌曲。不设 `personalFmModes`。每日推荐：Spotify 的第一个 Daily Mix。它每天按账号的收听重新生成，对得上卡片上“每天更新”的说法；Discover Weekly 一周才换一次，所以没有用它；其余的 Daily Mix 留在推荐歌单里。Daily Mix 是从“为你打造”那一页（`spotifyExplore.ts` 的 `spotifyMadeForAccount`）里按歌单 id 的前缀 `37i9dQZF1E3` 认出来的，这个前缀 2026-10-08 在一个真实账号上核对过（57 个歌单里认出了每日合辑）；认不出时日志写明读到多少个歌单、其中没有 Daily Mix，卡片是 0 首。推荐歌单：那一页上其余的歌单，按 Spotify 自己的顺序，最多取调用方要的数量。那一页的读取结果留一分钟，供同时来的两个请求和随后打开卡片用。Spotify 换掉查询（非网络错误）时这两样留空，FM 照常（FM 自己读“点赞歌曲”被拒时也一样：用在应用里听过的歌做种子，一首都没有就不出 FM 卡片，页签其余部分照常）；断网时整页读取失败，回到这一页时重读。登出、或一次登录成功后，FM 的记录和读到的歌单都清掉。日推页面上的“管理推荐”和历史日期只在平台有 `historyRecommendations` 能力时出现（`GridView.tsx`）：Spotify 的日推页只有歌单、数量和刷新。
  歌词：Spotify 自带的歌词只有逐行时间（`spclient` 的 `color-lyrics`，请求必须带 `app-platform: WebPlayer`，否则答 400），不带时间的当作没有，交给跨源匹配。
  Spotify 也是跨源匹配的一个歌词来源（`LyricProviderSource` 的 `spotify`，排在默认顺序的最后；歌词来源都登记在 `src/utils/lyrics/lyricSources.ts` 这一张表里，一个来源一行，怎么搜、怎么取在 `lyricMatchSources.ts`），别的平台、本地和 Navidrome 的歌都能用它。它只用账号自己的登录来答，所以只在 Spotify 登录着的时候出现在“匹配歌词”对话框的标签和设置的“歌词匹配优先级”里（`useLyricMatchSources`），自动匹配在没登录时不向它发请求（`isLyricMatchSourceOffered`）。自动匹配里它只可能当逐行的备选：别的来源已经给出逐行歌词后不再问它，每试一个歌手名最多一次搜索加一次取词（所有来源都落空、换另一种歌手写法重试时再来一遍）；正在放的就是 Spotify 的歌时直接用手上那份歌词，不发请求。把它选成首选来源时，Spotify 的歌保留自己的逐行歌词，只有别处找到逐字歌词才换。搜索用的是和其他来源一样的“歌名 - 歌手 - 专辑”（实测 2026-10-08：英文、日文、中文各取知名歌曲共 4 首，都搜到并取到带时间的歌词）。本地歌曲从 Spotify 匹配到歌词时，歌名、歌手、专辑和封面也照其他来源的规矩取自 Spotify（`onlineMetadata.source` 为 `spotify`）；“匹配元数据”对话框不搜 Spotify。设置里选了 Spotify 之后登出，这一项不再显示，自动匹配和设置页都当作没有选过，按默认的首选（QQ）走；存着的选择不动，再登录就恢复。两处留着没改：对话框开着 Spotify 标签时账号登出，标签消失但对话框还停在 Spotify 上（搜不到东西）；每次自动向 Spotify 搜歌词都会占掉搜索页留着的 8 个搜索词里的一个，被挤掉的搜索词翻下一页时从头重走。
  播放（2026-10-08 接上，`electron/spotify/audio.cjs`）：Spotify 自己的音频只给付费账号（它对所有第三方播放器的限制）。账号是否付费在登录时读出并存下（`vipType`），之后每次读登录状态时最多十分钟重读一次；存下的是免费账号时，要一首歌之前先重读一次套餐（最多 30 秒一次），所以账号开通会员后不用重新登录，第一次点播放就能听。读套餐的请求还在路上时，这期间要的歌都等同一个答复。只有 Spotify 这次运行里亲口答过“免费”才报 `subscription-required`（队列停下并提示“Spotify 需要会员才能播放，当前账号不是会员”；这个原因和“只能试听”分开：平台给试听片段时照放片段并提示（见下面 `resourceCache.ts` 一条），免费账号却一段也不播；日志里带它答的 `catalogue` 和 `product`）；套餐读不到时不算免费，照常去取歌，由播放组件决定成不成；重读时发现登录已失效报 `auth-required`。套餐读失败时沿用已存的，不把付费账号记成免费。
  Spotify 把每首歌存成 CDN 上的一个加密文件。主进程用 `@lox-audioserver/node-librespot`（librespot 的 Node 绑定，原生模块，可选依赖）以账号的 token 连上 Spotify，问到文件的 CDN 地址和 AES-128 密钥（`resolveAudioFileAsync`，实测一次 0.1 到 0.4 秒，第一次连同建立连接约 1.3 秒）。音频地址是应用自己的 `folia-spotify://audio/<trackId>?k=<key>`，每次 `getAudioSource` 都换一把 key；音频元素要哪一段，主进程就按 Range 向 CDN 要哪一段，边读边解密（计数器模式，可以从任意字节开始），解密后的音频不落盘，也不在内存里留整首歌（加密文件本身可以存盘，见下一段）。Ogg 文件开头有 167 字节是 Spotify 自己的页，不交给播放器（应用看到的文件从它之后算起）。CDN 地址有时效：10 分钟后或被 CDN 拒绝（401/403/404/410）时重新问一次；重新问到的文件长度或类型变了，旧地址答 503，渲染端换新地址。连接放久了可能被 Spotify 关掉：在留着的连接上问失败时新建一次连接再问；Spotify 明说这首歌没有（`track is unavailable`、`no audio files available`）时报 `not-playable`，不新建。登录、登出会关掉连接并作废所有已发出的地址。音质：`standard` 要 160 kbit/s，其余档位要 320 kbit/s（Ogg Vorbis；Spotify 的无损没有接）。所以 adapter 只列两档（`playback.audioQualityLevels: ['standard', 'high']`）：音质选项在 Spotify 下只有 `standard` 和 `high` 两个按钮，存着的偏好是 `lossless` 或 `hires` 时亮的是 `high`，交给主进程的也是 `high`。
  **Spotify 的音频存盘时保持 Spotify 自己的加密**（2026-10-08，`electron/spotify/audioFiles.cjs`）：Spotify 给的文件本来就是加密的，歌曲缓存开着时主进程把它原样写进缓存目录下的 `spotify/`（`<歌曲 id>-<码率>.bin`，先写 `.part`，字节数对上才改名），**密钥不写盘**，每次运行向 Spotify 重新要，所以盘上的文件离开登录着的会员账号打不开，也不能离线播放。解密后的音频不写盘，也不进渲染端的歌曲缓存。这些文件算进歌曲缓存的容量上限（和原始音频、转码一起按最久没用的先删）、大小统计和“清除缓存”；缓存目录可能是用户自己选的文件夹，所以列出、统计、删除都只认自己命名的文件，“清除缓存”不动 `spotify/` 里别的东西。只存能核对密钥的文件（Ogg；用这次拿到的密钥解开头，对不上就删掉重新走 CDN）。读：`folia-spotify://` 的每个请求先看盘上有没有整份（长度要和这个地址对应的文件一致），有就读盘，没有照旧读 CDN；盘上有时定位歌曲也不再向 CDN 要开头字节。写：provider 的 `playback.keepAudio(url)` / `hasKeptAudio(url)`（`providerRegistry.ts` 的 `keepsOwnSongAudio`、`keepProviderSongAudio`、`hasProviderKeptSongAudio`）。两处会要求存：automix 提前分析（`profileService.ts`，先存再读，所以分析读的就是盘上那份）和整首播完（`playedTrackCache.ts`）；存好后按歌曲缓存写入同样的方式通知（`notifyAudioCached`），并带上读这份文件用的地址，等着的人声分离被唤醒：“下一首”的分离请求常常在这首歌还没有地址时就排上了，没有这个地址它醒来也无从读。分析那边每次经过这首歌都会问一遍（`profileService.ts` 的 `keepWithProvider`），包括以前测量过、这次不再读的歌：这样的歌文件可能不在盘上（功能上线前测的，或被容量上限删了），歌曲缓存开着就补存。“盘上有没有”只看硬盘，不问 Spotify。**人声分离现在有**：`stems.ts` 仍然不下载，但盘上已有的文件它通过这首歌的地址读（读的是盘，不是网络）。注意分离本身对所有歌都会把要分离的那 30 秒解码后的采样临时写到系统临时目录（`electron/analysis/sidecar.cjs` 的 `folia-htd-*`），跑完就删；Spotify 的歌进了分离也一样，这一小段是解密后的。流量：一首歌第一次播放时，如果它之前没被当作“下一首”提前分析过，播放那一路仍从 CDN 读，另有一次整份下载写盘；之后的播放、拖进度、分析、分离都读盘。
  等待都有时限（30 秒）：建立连接、问文件位置、文件的头几个字节、CDN 的应答、读流中途没有数据。CDN 答的 `Content-Range` 起点和要的不一样时按网络错误处理（别处的字节用这里的计数器解出来是噪音）。
  原生模块只有部分系统的现成构建（0.5.1：win32-x64、darwin-arm64、linux-x64/arm64 glibc；**没有 darwin-x64**）。没有构建的系统上模块加载失败，`getAudioSource` 报 `unavailable`，其余功能不受影响；所以它是 `optionalDependencies`（安装脚本在没有现成构建时会尝试用 Rust 从源码编译，失败不应让整个安装失败）。打包时 `build/afterPack.cjs` 只留目标系统的那一份。原生模块自己直连 Spotify（接入点的 TCP 连接和几个 HTTPS 请求），不走应用的系统代理设置；CDN 的请求走。
  喜欢与收藏（2026-10-08 接上，`spotify/spotifyMutations.ts`；三种改动都在真实账号上各做一次、读回、再撤回）：渲染端只说“哪个 uri、留还是不留”（桥接操作 `library`，只收 `spotify:track|album|playlist:<22 位 id>`），改动的名字和哈希留在主进程（`CHANGES`），渲染端不能通过 `query` 发改动。歌和专辑用 `addToLibrary` / `removeFromLibrary`（变量是 `libraryItemUris`；这对改动拒收歌单），歌单用 `addItemsToRootlist` / `removeItemsFromRootlist`（变量是 `uris`）。Spotify 拒绝一个改动时答的是状态 200 加 `errors`，所以带 `errors` 的答复、或者没有带回改动结果的答复，一律算没改成。能收藏的是专辑和别人的歌单；账号自己的歌单和“已点赞的歌曲”不能（`canSubscribe`）。**把账号自己的歌单移出音乐库等于删掉它**，而卡片不一定知道歌单是谁的（首页和“为你打造”的卡片不带这个信息，音乐库里的卡片带），所以主进程在改歌单之前先向 Spotify 读一次这个歌单（`fetchPlaylist`）：歌单的主人是当前账号、账号能管理它、或者 Spotify 没说主人是谁，都拒绝（`unsupported`）。

  歌单里歌曲的增删和新建歌单（2026-10-08 接上；在为试验建的歌单上做过并撤回，试验歌单随后移出音乐库）：`updatePlaylistTracks` 走桥接操作 `playlist_edit {id, action: add|remove, tracks}`（一次最多 100 首），`createPlaylist` 走 `playlist_create {name}`（名字最长 100 字）。主进程每次改之前先把歌单整份读一遍（`fetchPlaylist`，一次要 500 行，按实际给的行数往下读，最多 40 次请求），一是确认 Spotify 说这个账号能改它的歌（`currentUserCapabilities.canEditItems`，否则 `unsupported`），二是因为两种改动都要用到歌单里现有的行：Spotify 的 `addToPlaylist` 会把已经在里面的歌再加一次（实测加两次得两行），所以只加歌单里没有的；`removeFromPlaylist` 按行的 `uid` 删，不按歌的 uri，所以把这首歌的每一行都删掉。只有整份读到才改：Spotify 说答复不完整（数据旁边带 `errors`）、答复里没有行、或者歌单比读取上限还长，都拒绝改动，否则会把已有的歌再加一次，或者把没删掉的歌报成已删。没有自己 `uid` 的行也算“歌单里有这首歌”。两次改动同时发给同一个歌单时不排队，各读各的（选择框自己挡住了连点）。新建分两步：`POST spclient /playlist/v2/playlist`（答 `uri`），再用 `addItemsToRootlist` 放进音乐库；第二步失败时歌单存在但不在任何人的音乐库里。新建的歌单是否公开没有量。能加歌的是带 `isOwned` 的歌单，“已点赞的歌曲”除外（`canAddToPlaylist`）。播放面板的“加入歌单”在 provider 有 `createPlaylist` 时带“新建歌单”（`omni.canCreatePlaylistForSong` / `createPlaylistWithSong`，`src/components/app/AddToPlaylistHost.tsx`），目前只有 Spotify 有。加进去的是面板上显示的那首歌，由 `AddToPlaylistHost` 交给回调（过渡期间播放状态里的当前歌已经是下一首）。新建成功但加歌失败时刷新一次歌单列表，让新歌单出现在选择框里，再试时不会建出第二个。歌已经在歌单里时没有东西发给 Spotify，界面照样提示“歌单已更新”。应用里没有删除歌单的操作。

的读取被采用了，这个答复丢掉、不对账，不管两者哪个先开始（那次读取可能显示这首歌是喜欢的，更早问的答复却说不喜欢，照收会把红心灭掉）；那次读取没读全的，歌重新问，读全了的不再问。每首歌在两次读取喜欢的 id 之间只问一次（读取跟在“可能在别处改过”的时机、同步按钮、登录之后）；请求失败就停，到下一次读取喜欢的 id 之前什么都不再问（失败过的请求多半还会失败，不能每次歌变了都再发一遍）；平台对某首什么都没说的不再问。日志：对账一行 `[Like] <平台>: hearts of <n> songs in play checked (<m> liked) applied: …`，失败一行警告。代价：问到的红心让手上的 id 个数变了，下一个时机数目对不上，会整份再读一次。
- `providerAccountCache.ts`：按 provider 保存用户、集合、点赞 ID、hydration/freshness 快照；刷新失败保留旧快照。
- `providerStorage.ts`：renderer 的 provider session/account 持久化边界。QQ 这里只保存 opaque `qqmusic_session`；真实 credential 始终由 QQ API 后端持有。Electron 通过主进程的 `safeStorage` 加密仓库跨重启恢复，独立 Node / Docker 后端可用 `QQ_AUTH_SESSION_PATH` 与 `QQ_SESSION_SECRET` 启用加密文件仓库；serverless 形态下 credential 加密在 token 里，服务端不存。Electron 这次没有系统加密、读不出仓库时（`electron/qq/qqAuthSessionRepository.cjs`），存着的 session 这次不带（按游客请求）也不删，读账号报 `unavailable`；只有登录才有的栏目、推荐、收藏状态、试听按游客走（`hasUsableQqSession`）。这次运行里一扫码登录，仓库就把读不出的那份删掉（和别的平台一样，新登录替掉旧登录，下次启动不会回到它），主进程从此答「读得出」（`get-qq-api-status` 的 `sessionStoreUnreadable` 每次现问），新 session 照常带，页面重新载入以后也带。过期的会话只在到期 30 天以内多给一小时去试续期：这一小时不写盘、每次启动重给，到期更久的照包的规则删掉。别的路由回 401 时 transport 先问一次 `login_status`（同一时间只问一次），后端不再认出这个用户、存着的又还是那个 session 才删（`qq/qqTransport.ts`）；这样删掉时账号层不知道，界面上的账号到下一次读账号（进首页、同步、重启）才离开。送出方式按部署形态分岔：同源 base 用 `X-QQ-Session` header 送裸 token，外部 URL 与 Electron 维持 `?cookie=` 送整串 cookie，两者语义不同不可互换。酷狗 Web transport 仍在这里保存远端 API 请求所需的 session；Electron transport 只保留非敏感 `userid` 提示，`token`、cookie 与 `dfid` 由主进程加密持有，不得复制到 renderer。主进程这次没有系统加密、读不出存着的会话时，它留着不被覆盖，这次也还没有新登录时登录检查报 `unavailable`；退出登录（登录失效也走这里）时连同旧版本的明文会话一起从磁盘删掉（`electron/kugou/kugouApiBridge.cjs`）。旧版本的明文会话写成 V2 之后才删；这次运行没有系统加密时，读进内存后马上从磁盘删掉（旁边留着读不出的 V2 时也删），只在这次运行有效，磁盘上不留不加密的登录。没有系统加密时的新登录同样只在这次运行有效，并删掉存着的 V2，下次启动不会回到旧账号；这个删除一次运行只做一次（每次删除都要重写整份配置文件），删不掉只记一行警告，请求照常。加密能用、只是这一次写不进去时，存着的留着等下一次存；是另一个账号的就删掉。
- `resourceCache.ts` / `resourceKeys.ts`：在线资源缓存键和缓存层。当前 kind：`audio`、`lyric`、`cover`、`theme`、`replayGain`。**新增 kind 必须同时在 `src/services/repositories/cacheRepository.ts` 的 `getCacheTableName` 与 `matchesCategory` 里登记前缀**，否则条目会静默落进 `api_cache` 兜底表、不属于任何一个「清除缓存」分类，变成清不掉的孤儿；若该 kind 是按歌曲存一份，还要确认它没有被计进 `mediaCount`（那个数字的语义是「已缓存歌曲数」，会翻倍）。`audio` 旁边另有一个键 `audioLevel_<歌曲键>`（不是 `SongResourceKind`，键在 `resourceCache.ts` 里拼，`saveSongAudioLevel` 写）：这份音频取自哪一档。`getCachedSongAudioBlob(song, level?)` 和 `hasCachedSongAudio(song, level?)` 带着档位问时，记着别的档位的那一份算没有；没记档位的（记档位之前存下的、网易云旧键的）问哪一档都算有；不带档位和以前一样。带档位的是播放、预取和播完写入，不带的是自动混音分析和人声分离。试听片段（2026-10-17，只跑过单元测试）：平台可能拿比整首短的文件应答一首歌，账号只能试听时给的就是试听片段。adapter 照交地址，在 `ProviderAudioSource.preview` 上标出来，omni 按地址记下（`isPreviewAudioSource`）；播放照放，放完接着放下一首。提示 `status.songPreviewOnly`（info；provider 写了 `playback.previewNoticeKey` 时换成它自己的那一句，经 `omni.previewNoticeKey` 取）只从一处来：活动播放器开始放一个标成试听的地址时（App.tsx 的 `playing` → `previewNotice.ts` 的 `notePreviewPlaying`），同一首歌每开始一次只提示一次（按 `currentSong.ts` 的 `startOfAskedSong` 分）：暂停再放、卡顿后接着放、播放中换地址（recovery）、过渡被暂停或拖动取消而回到上一首、一次放歌中途放弃而回到原来那首（后两种是 `askForSong(…, { putBack: true })`，那首歌拿回自己原来的那次开始）都不再提示，再放一次这首歌才再提示；只认播放器放的是当前那首歌、当前那个地址的时候，换歌途中上一首的地址报的 playing 不算，不会把新歌的那次提示用掉；启动时恢复上一首而不自动播放时不提示，按下播放才提示。自动混音的下一首放的是预取的地址，也从这里提示。旧窗口交给新窗口的地址（`useElectronWindowPlaybackHandoff.ts` 的退路）新窗口的 omni 不认识，不提示。长度的规则（`wholeSongCheck.ts`）有两个数，放在一处：文件头里的播放时长不到歌曲 `durationMs` 的一半，算“不是这首歌”（试听片段大约是 3 到 5 分钟歌里的 30 秒）；到 90%，算“证明是整首”。分开是因为 `durationMs` 可能是另一个版本的：拿 90% 去拒收、删除、跳过分析，会把一首整歌当成片段丢掉，离线时它的副本被删就放不了。只有“不是这首歌”拿来对付文件；“证明是整首”只用来决定能不能盖掉磁盘上已有的那份。存音频的两处（播完写入 `playedTrackCache.ts`、自动混音分析整首读下来那一次 `profileService.ts`）存之前过同一个检查（`mayStoreSongAudio`）：标成试听的地址一律不存，两处都在下载之前就停（`whyPreviewClip`），片段不白下；用一个不出声的 `Audio` 元素读文件头里的播放时长（5 秒为限），不到一半的也不存，磁盘上没有文件时也一样；别的文件（一半到 90% 之间，或读不出时长、没有 `Audio`、元素报错、5 秒没有结果、时长不是有限的数，或歌曲没有 `durationMs`），磁盘上没有文件就照旧存，要盖掉一份已经在磁盘上的文件（不论它是哪一档）就不盖，原来那份留着，只有证明是整首的文件才盖（日志 `[Cache] Copy of <歌曲键> kept, … play length <秒数或 unknown>, stated length <秒数或 unknown>`；没有旧文件而不存时是 `[Cache] <歌曲键> not stored, …`）。播放拿缓存副本时（`loadOnlineSongAudioSource`：同一档的那份，和拿不到地址时别的档位的那份）也读一次文件头，300 毫秒为限：不到一半的连同 `audioLevel_` 一起删掉（旧键下的也删），照没有缓存那样向平台要地址，以前版本存下的试听片段就这样清掉；别的副本照播，读不出或超时也照播。只删量过的那份：渲染端把读到的大小交给主进程（`remove-audio-cache`，`electron/audioCacheRemove.cjs`），磁盘上的文件大小变了（这期间播完写入写进了整首）就不删，档位也不删；IndexedDB 里的副本同样按大小比。文件删不掉时（Windows 上文件被占用，EBUSY、EPERM）主进程报错，副本和它的元数据、档位都留着，下次从缓存开始播时再查。日志在删完之后打，带结果（`[Cache] Copy of "<歌名>" deleted: …`、`left, a newer file is there: …`，删不掉是 `not deleted (…)`）。自动混音从音频量出来、按歌留下的东西用同一条规则（`whyNotTheSong`、`whyNotTheSongPlayed`）：分析结果（`profileService.ts` 存的 `automix_profile_<键>`，节拍网格、响度、开头结尾都在里面）对标成试听的地址不下载、不分析，对不到一半的文件（整首读下来的，或媒体缓存里的副本）不分析；存着的整首分析量的那个文件不到这首歌的一半时（以前版本从片段量的）不用，重新量；播完一首用播放器听到的响度补上只有开头的分析时，播的是片段就不补；问自己存文件的 provider 存不存时（`keepWithProvider`），试听地址不问。这些跳过在这次运行里记住（下载按歌和地址，缓存副本按歌），每次预取不再重新下载、重新读同一个文件；缓存副本在这首歌的音频写入、或副本不在了时忘掉；别的跳过（还没有地址、下载失败）照旧下次再试。人声分离的窗口（`stems.ts`，只在内存里）不从不到一半的缓存副本切，请求等这首歌自己的文件存进来再做。正在放的片段也不用内存里的分析：内存里有了分析，这次运行就不再量这首歌，开会员以后整首也会用片段的；没有分析时过渡照没有分析的歌那样做（读播放器的现场响度）。实测读文件头的代价（2026-10-17，在一个空的 Electron 窗口里读本机媒体缓存的 324 个文件，不是在应用里）：中位 6 毫秒，90% 在 20 毫秒内，5 MB 以下的文件（试听片段都在这里）最多 7 毫秒，每次运行第一次 126 毫秒；只用 E 核时中位 9 毫秒、第一次 282 毫秒，偶有和文件大小无关的停顿到 1.6 秒（超过 300 毫秒就照播，下次再查）。盖的时候先删 `audioLevel_`、再写音频、最后写新档位：中途失败留下的是一份没有档位的文件（哪一档都播它），不是新文件挂着旧档位。播完写入和自动混音分析这两处，写入音频后都跟一次 `saveSongAudioLevel`：地址的档位查不到时不记，并删掉这首歌以前记的（网易云旧键搬到新键那一处不跟，那份文件本来就没有档位）。前缀已在上面两处登记：和歌曲一起清、一起计大小，不计进 `mediaCount`。拿不到地址时（断网、登录失效、歌曲下架）例外：`loadOnlineSongAudioSource` 改播那份别的档位的副本，日志 `[Cache] No URL for "<歌名>": its copy of another level plays`。
- `watch`（adapter 的可选成员）：应用开着时这个平台自己要盯着的东西。应用起来之后由 `omni.watchProviders` 一起开始（只管当时注册了的平台），平台要告诉用的人的话（i18n key）由 `src/components/app/useProviderNotices.ts` 显示成底部消息。现在只有网易云声明：`netease/neteaseLocalService.ts` 的 `watchNeteaseLocalService` 把桌面端本地后端的状态抄进 `netease/useNeteaseApiStatusStore.ts`（登录窗口经 provider 声明的 `localService` 读它），起不来时说一句；因为断网起不来的不说（状态里带 `offline`）：要用它的请求说连不上，并且叫主进程再启动它一次（至多每 10 秒一次，规则在 `electron/netease/neteaseApiStartup.cjs` 的 `startsAgainWhenNeeded`），网通了就不用重启应用。

- `songMetadata.ts` / `songAvailability.ts`：歌曲元数据、可播放性和替代歌曲相关共享逻辑。
- `catalogRefs.ts`：歌曲、歌单、专辑、歌手的 provider-aware catalog 引用。
- 应用自己的播放记录不在这个目录：`recentPlays.ts`、写它的 `useRecentPlaysRecorder.ts` 和用它做出探索页两栏的 `ownSections.ts` 都在探索页自己的目录 `src/components/app/home/explore/`（见上文“应用自己的两栏”）。

- `exploreReads.ts`：各平台的探索页 adapter 共用的两样，不认平台（规则见 `EXPLORE_ADAPTER.md` 规则 3 和规则 10）。一，`createHandedOut()`：记前几次读取用过什么（一栏交过的条目、拿来问过的歌），按 adapter 自己定的范围记；`inTurn` 把候选排成“没用过的在前，其余最久以前用过的在前”，`note` 把这一次用的按先后记下（后记的算后用的，所以长短不一的列表都轮得匀）；每个范围最多 5000 个，超出时忘掉最久以前用过的；只在内存里。二，`stampCursor` / `cursorWords`：在游标前面写上、读出读取的序号，用来认出上一次读取的游标。用它的是 `netease/neteaseExplore.ts`、`ytm/ytmExplore.ts`、`spotify/spotifyExplore.ts`（Spotify 只用第一样：它的游标不带序号）；YouTube Music 只记问过的歌，它的栏不记交过的条目。

`omni.ts` 的 active-provider 调用带 request generation 检查：`withActiveProvider` 会丢弃 provider 切换后返回的旧响应，切换事务需要 `invalidateActiveRequests()`。不要在调用方重新实现一套取消/晚到响应防护。

## Routing rules

### Ordinary single-provider flow

```ts
import { omni } from '@/services/onlineMusic/omni';

const page = await omni.searchSongs(query, { limit: 30, offset: 0 });
const song = page.items[0];
if (song) {
    const lyrics = await omni.getLyrics(song);
    const audio = await omni.getAudioSource(song, 'high');
}
```

歌曲已经带有 provider identity 时，使用 song-aware 方法：

```ts
await omni.toggleSongLike(song);
await omni.getCollectionTracks(collection, { limit: 50, offset: 0 });
```

### Explicit cross-provider flow

歌词匹配、本地元数据匹配、联邦搜索、fallback、比较和迁移才是跨 provider。使用 `searchProviderSongs(providerId, ...)` 等显式方法，并保留每条结果的 `sourceRef.providerId`。不要为了“当前有两个 provider”就直接并发调用 raw adapter。

### Identity

在线歌曲身份是 `(sourceRef.kind='online', sourceRef.providerId, sourceRef.mediaId)`，不是 `song.id` 单值。比较、去重、替代、入队前优先使用：

- `src/utils/appPlaybackGuards.ts`：`getPlaybackSourceRef`、`getPlaybackSongKey`、`isSamePlaybackSong`
- `src/utils/appPlaybackHelpers.ts`：播放结构和来源相关派生

跨 provider 的 numeric id 不可直接去重；`online:netease:123` 与 `online:kugou:123` 默认是两个播放身份。
