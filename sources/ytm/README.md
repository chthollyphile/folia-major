# YouTube Music（`ytm`，仅桌面端）

Folia 内置的 YouTube Music 音源模组（Folium 2.0）。原来是 `src/services/onlineMusic/UPSTREAMS.md` 里的一节和
`src/services/onlineMusic/README.md` 的 `ytm/ytmProvider.ts` 一条，随平台搬到这里（路径改成本目录的，其余照旧，
日期是当时写的）。构建、布局和依赖的规矩见 `dev/sources/README.md`。

## 迁成模组后变了什么

- **请求通道**：client 经 `folium.rpc` 的 `request` 发操作给 main 入口（`main/index.ts`），宿主只放主窗口的调用进来，
  和以前 `ytm-api-request` 的来源校验一样。main 入口里的 `.cjs` 除了下面几处都是原样搬来的。
- **网络**：认领的内存分区 `folia-ytm`（`api.net.session`），第一次用时设成系统代理，请求一律 `credentials: 'omit'`。
- **沙箱**：认领的内存分区 `folia-ytm-sandbox` 的隐藏窗口（`api.windows.hidden`，`backgroundThrottling: false`）；
  分区的 http(s) 由 `intercept` 本地应答，权限由 `refusePermissions` 一律拒绝，其余走不存在的代理；主窗口走了
  窗口跟着关（`api.windows.onMainWindowChanged`）。`main/sandbox.cjs` 改成收这几样。
- **音频地址**：`folia-ytm://audio/<id>/<档位>?k=<key>` 换成 `folia-mod://ytm/_media/audio/<id>/<档位>?once=<key>`
  （`api.media.serve('audio')`）；宿主比较两个地址时不看 `once`。`main/audio.cjs` 收 `urlOf`，多了 `serve`（拆开的一次读取），
  Range 的解析搬进它自己（不再 require 宿主的 `electron/transcode/protocol.cjs`）。key 只在一次运行内有效，旧地址不用认。
- **存储**：登录仍在主进程存储的 `YTM_WEB_SESSION_V1`（旧设备登录 `YTM_SESSION_V1` 照旧在第一个请求时删掉），经
  `api.legacy.store` 读写、`api.seal` 加密；网页登录的浏览器目录是认领的 `ytm-sign-in`（`api.paths.legacy`）。
- **退出与停用**：进行中的网页登录在退出（`api.onBeforeQuit`）和停用（`api.onBeforeUnload`）前收尾，最多 3 秒。
- **渲染端的记忆**：会员与否存在音源的页面存储（键 `account`，localStorage 里是 `online_provider:ytm:account`），
  翻转时 `handle.changed()` 让宿主重读音质档位；账号自己建的歌单存在键 `ownedPlaylists`（`{ userId, ids }`，最多
  1000 个），代替宿主的账号快照。旧键 `folia_ytm_account` 模组读不到：升级后第一次运行在读到登录状态之前按非会员列档位。
- **语言**：模组收不到换语言的事件。语言表的 `pageLanguage` 每种语言一个词，每次调进音源前比一下，变了就丢掉按
  旧语言读的页（以前是 `i18n.on('languageChanged')`）。
- **文字**：短名、登录窗口的标题与说明（macOS 另一句）、两种失败情况的说明、「与某首歌相似」都在 `locales/`；
  全名 `YouTube Music` 写在定义里，各语言相同。下文提到的 `home.loginNoBrowserYtm` 现在是模组语言表的 `login.noBrowser`。
- **歌词**：交原始 LRC 行轨（有带时间的行才交），由宿主解析；不是别的歌的歌词来源（没有 `crossSource`）。

## 上游

- **上游**：
  - `youtubei.js`（仓库 LuanRT/YouTube.js）：向 YouTube 自己的 InnerTube 接口发请求，解析答复。
  - `googlevideo`：按 SABR 读音频流（`main/ytmApiBridge.cjs` 里和 youtubei.js 一起按需加载）。
  - `bgutils-js`（仓库 LuanRT/BgUtils）：跑 Google 的 BotGuard 脚本，做出音频服务器要的 proof-of-origin 令牌（`main/poToken.cjs`）。
  - YouTube 自己的播放器脚本和 BotGuard 脚本：第三方代码，随时会变，放在没有 Node、没有网络的隐藏页面里跑（`main/sandbox.cjs`）。
- **版本**：`youtubei.js` 18.1.0、`googlevideo` 4.1.1、`bgutils-js` 4.0.3，钉死在本目录的 `package.json`（构建核对装着的版本）和根目录 `package.json`（包从仓库根的 `node_modules` 找）。升级时两处一起改。三个包都是 ESM-only，声明成 `vendor`：打成 main 入口旁的 `vendor.<指纹>.mjs`，入口经 Node 的 require(esm) 载入（不能有顶层 await）。
- **我们包了什么**（都在本目录的 `main/`）：
  - 把 youtubei.js 的 `Platform.shim.eval` 换成在沙箱页面里执行（`ytmApiBridge.cjs`）。
  - 取逐行时间的歌词时冒充手机 App：`MOBILE_CLIENT` 写死 `ANDROID_MUSIC` 7.21.50（同一文件），网页客户端只给纯文本歌词。
  - 网页登录、收藏、列表页、探索页由我们自己的文件读网页客户端的答复（`webSignIn.cjs`、`webSaves.cjs`、`webPages.cjs`、`webExplore.cjs`），目录节点由 `tiles.cjs`、`catalog.cjs` 读。
- **上游变了怎么跟**：
  - 先看 youtubei.js 和 BgUtils 的发布说明，再在应用里用访客和登录的账号各放一首歌。
  - `test/unit/ytm/` 下的测试都用替身或裁剪过的样本（例如 `ytmTiles.test.ts` 直接把样本交给 `tiles.cjs`、`catalog.cjs`，不跑 youtubei.js），上游改了解析结果它们抓不到。
  - YouTube 改了播放器或 BotGuard，表现是音频请求 403 或歌放不出来；日志都以 `[Ytm]` 开头。
  - 更多实测（音质档位、会员判断、登录方式）在下面「平台说明」。

## 平台说明

- `client/ytmProvider.ts`：YouTube Music 音源，仅桌面端；`client/ytmTransport.ts` 经 `folium.rpc` 的 `request` 连接 main 入口里的 `main/ytmApiBridge.cjs`（迁之前是受限 IPC `ytm-api-request`）。
  YouTube Music 的文件各层都收在自己的 `ytm/` 目录里：这里的 `ytm/`、`main/`、`test/unit/ytm/`。
  登录在用户自己的浏览器里做（2026-10-09；只跑过单元测试，没有在应用里试过）：主进程打开电脑上装的 Chrome、Edge、Chromium、Brave，或者 Chrome 的 Beta、Dev、Canary 版、Helium 的一个单独窗口（按这个顺序找，四种稳定版在前；先找装给整台电脑的位置，这几种都找过才找装在用户自己目录下的，Windows 上 Chrome Canary 只装给一个人，只在用户自己目录下找；Windows 上这些位置都没有时，再读注册表：先是打开 https 链接的默认浏览器（`UserChoiceLatest`、`UserChoice`），再是 `StartMenuInternet` 里登记的浏览器（用户自己的在前），只认绝对路径的 `chrome.exe`、`msedge.exe`、`brave.exe`，这样设成默认浏览器的便携版也找得到（#1227，2026-11-15，只在本机读过注册表、跑过单元测试，没有用便携版浏览器登录过；注册表用系统自带 PowerShell 读，读不了就当没有）。Windows 上两次启动浏览器都多带一个 `--portable`：chrome++（Bush2021/chrome_plus）做的便携包在命令行里没有它时会让浏览器重开一次自己、第一个进程马上退出，调试管道也不交给新进程，有它时原样运行、用我们给的 `--user-data-dir`；这一条只读过 chrome++ 的源码，没有运行过；Linux 上按命令名在 PATH 的绝对路径里找，新加的几种是 `google-chrome-beta`、`google-chrome-unstable`（Dev 版）、`google-chrome-canary`、`helium`（Helium 官方的 deb / rpm）和 `helium-browser`（AUR 的 helium-browser-bin）。各个位置的出处写在 `main/browserSignIn.cjs` 的 `BROWSERS` 上面；2026-10-22 加的这几种只跑过单元测试，没有用真的浏览器试过；日志 `[Ytm] Sign-in can use <浏览器名> (<可执行文件名>)` 写出用了哪一种），用户在里面登录 Google，看到 YouTube Music 显示自己的账号后关掉那个窗口，应用再读出这次登录（桥接操作 `web_login_start` / `web_login_check` / `web_login_open` / `web_login_cancel`；同一时间只有一个，没有 key，窗口关了却没登录、或过了 10 分钟，都算过期）。这些浏览器一个都没装、注册表里也没有时（`web_login_start` 报 `unsupported`），这一次登录失败，没有别的登录方式：弹窗显示“登录 YouTube Music 需要安装 Chrome（Beta、Dev、Canary 版也可以）、Edge、Chromium、Brave 或 Helium。Windows 上也可以把便携版 Chrome、Edge、Brave 设为默认浏览器（需是 chrome.exe、msedge.exe、brave.exe 本身，不是启动器）。”（`ytmProvider.ts` 的 `getLoginTexts().caseNotes['no-browser']`，文案键 `home.loginNoBrowserYtm`）。登录的凭据由主进程用 `safeStorage` 加密保存，不进 renderer。
  旧版本存下的设备登录（`main/session.cjs`，键 `YTM_SESSION_V1`）不再使用：每次运行的第一个请求里这个键有值就删掉；能解开而且里面有 `refresh_token` 时同时向 Google 撤销授权（不等答复，15 秒没有答复就放弃，失败不重试），解不开的只删不撤销；两种情况各记一行日志。存储读写抛错时记一行警告（`[Ytm] The device sign-in of an earlier version could not be removed: …`），这次请求照常进行，这次运行里不再试。存着的浏览器登录不动。浏览器登录存下的是这几项（`main/webSignIn.cjs`，`YTM_WEB_SESSION_V1`，整份加密）：`version`、发往 youtube.com 的 Cookie 请求头 `cookie`、发请求用的浏览器名 `userAgent`、存入时间 `storedAt`，和账号 `user`（Google 账号 id 的摘要 `id`、昵称 `nickname`、头像地址 `avatarUrl`、是否会员 `premium`）。这次运行没有系统加密（没有可用的加密，或是 Linux 的 `basic_text`）时：存着的登录读不出，留着不删，`login_status` 报 `unavailable`；这次的新登录只在这次运行里有效，存着的旧登录照样删掉，下次启动不会回到旧账号。加密能用、只是这一次写不进去（文件一时被锁住）时，存着的留着；是另一个账号的就删掉（波点、Spotify 也一样）。加密能用却解不开的（别的系统账号封的、内容坏了），当作没存。从浏览器读到的 cookie 拼成请求头后，先看它能不能当请求头的值（只能有可见 ASCII 字符和空格），不能就算这次登录失败（`web_login_check` 答 `error`），不拿去发请求，也不保存。账号的请求头（`Cookie`、`Authorization`、`X-Goog-AuthUser`、`X-Goog-PageId`）只随发往 `www.youtube.com` 和 `music.youtube.com` 的请求走（`guardAccountHeaders`）；带着这些请求头的请求不跟随重定向（`redirect: 'error'`），对方答重定向时这次请求失败。在 Electron 43.7.5 里用两个本机服务器量过（2026-10-09）：跟随重定向时，另一个源收到了 `Authorization`、`X-Goog-AuthUser`、`X-Goog-PageId`（没有收到 `Cookie`）；设成 `'error'` 后请求失败，另一个源什么都没收到。请求进行中用户登出或换了账号的，这次请求报 `unavailable`，答复不交给渲染端。日志和错误里没有 cookie、账号名和资料夹路径。登出只删掉本机存的这一份，不会结束 Google 那边的这次登录（那些 cookie 到期前仍然有效）；要结束它，到 Google 账号的“安全性”→“您的设备”里把这一次登录退出。登录用的浏览器资料夹（`userData/ytm-sign-in`，登录后里面是用户整个 Google 会话）在一次登录结束时删掉，不管怎么结束。启动浏览器之前应用先在里面放一个自己的标记文件（`folia-sign-in-folder`）；删除时认这个标记（没有标记的旧版本留下的认 `Local State`，空的和不存在的也算），先删别的，最后删标记和资料夹，所以删到一半失败后下次还认得它。一次删除总共最多 4 秒（失败就隔 250 毫秒再删一遍），到时间答“没删掉”，之后不再继续删。应用退出时先结束那个浏览器（`shutdown`），并把退出最多推迟 3 秒，等资料夹删掉；没有浏览器要结束、也没有登录的资料夹正在删时不推迟。上一次运行留下的资料夹，在本次运行的第一个请求时删；删不掉的（包括本次运行里登录结束时没删掉的）随后面的请求再删，直到删掉（`webSignIn.cjs` 的 `sweepIfLeft`）：这样随请求的删除，两次开始之间至少隔一分钟，上一次还没结束时不开始下一次；这一分钟不从登录结束时那次失败的删除算起，所以那之后的第一个请求可能马上再删。登出和 `web_login_start` 各自另删一次，不受这一分钟限制。删之前先结束上一次运行留在这个资料夹上的浏览器（应用没有正常退出时会留下）：看一遍所有进程的命令行（Windows 用系统自带 PowerShell 的 `Get-CimInstance Win32_Process`，资料夹路径放在环境变量里传进去；macOS 和 Linux 用 `ps`），只结束命令行里的 `--user-data-dir=` 正好是这个资料夹的进程，不凭进程号。结束不了，或资料夹删不掉时，`web_login_start` 报 `unavailable`，不在这个资料夹上再开一个浏览器。资料夹里有东西、却既没有标记也没有 `Local State` 的，当作不是应用自己的，不删；这时 `web_login_start` 同样报 `unavailable`，要用户自己把 `userData/ytm-sign-in` 删掉。删除和结束浏览器这两段只在 Windows 上用替身进程试过，没有用真的浏览器试过，macOS 和 Linux 上没有运行过。账号、音乐库（`user_playlists` / `user_albums`）、歌单（`playlist`）、探索页（`explore`）、收藏（`list_save` / `list_saved`）、歌单增删（`playlist_edit`）和歌曲的喜欢（`song_like`）都走网页客户端（web 会话，不加载播放器脚本，从不用来取流）；没有人登录时这些操作报 `auth-required`（`login_status` 答空）。YouTube 不再认这份登录有两种答法：状态 401，或状态 200 但按游客答复（看答复里的 `logged_in` 标记）；遇到时再问一次账号，两次都不认才删掉存着的登录，只有一次不认报 `unavailable`。登录窗口由 `web_login_start` 自己打开，关掉就是登录结束，所以界面不在开始时再开一次，也没有“重新打开浏览器”的按钮（`auth.opensLoginPageItself`）；macOS 上关掉窗口浏览器不会退出，说明文字换成让用户退出那个浏览器（没有在 macOS 上试过）。
  主进程用四个 youtubei.js 会话 guest、player、web、member（guest 和 web 按应用的界面语言请求页面，所以歌名、歌手名和界面是同一种语言，搜索结果和歌单里也一致：简体中文用 zh-CN，英文用 en，印尼文用 id。一个会话只用一种语言，界面语言变了，下一次请求就各自重建。各语言的页面会改写一部分歌手名：英文页把中文歌手名写成拼音，zh-CN 页给少数西方歌手起中文名，20 个里 1 个；音乐库卡片的歌单歌曲数按这三种语言的写法读，只认卡片第二行最后一段里末尾的那个数，`webPages.cjs`）：未登录的 guest 负责搜索、专辑、歌手等公开页面；未登录的 player 以 YouTube Music 网页播放器的身份取流；web 是上一段说的浏览器登录的账号，负责账号、用户库、歌单、探索页和写操作；member 是同一个账号加播放器脚本，在未登录的网页播放器取不到时接手 `standard` 和 `high` 的取流，不要求会员（网页播放器答应了、下载却失败的歌，下一次请求先走 member），`ultra` 只走它（见下面“超高档”一段）。这条后备没有在真实账号上对游客被拒的歌（比如有年龄限制的）量过，只量过游客也取得到的歌它取得到（`high` 的 itag 251）。有没有人登录，在轮到 member 路线时才判断：问网页播放器的那一两秒里听众可能登录或登出；没有人登录时跳过这条路线。两条路都取不到时报未登录的网页播放器给的原因，不报 `auth-required`；member 路线自己不判定登录失效，那由走 web 会话的请求（`withWeb`）判定。四个会话的请求都不用 cookie 罐：Google 下发的 cookie 不保存也不回传。账号放在请求头里：web 和 member 会话是存下的那条 Cookie 请求头和 youtubei.js 用它算出的 `Authorization`（SAPISIDHASH）；guest 和 player 不带账号（youtubei.js 在每个会话的第一个请求里自带一条自己生成的 cookie，内容是随机访客 id 和时区）。一次请求最多等会话 45 秒；会话继续建，建好后给之后的请求用。建了 3 分钟还没好的当作卡死，下一次请求重建。
  网页播放器的音频要带一枚 proof-of-origin 令牌才放行，令牌由 Google 的 BotGuard 脚本在隐藏的沙箱页里生成（`main/poToken.cjs`，依赖 `bgutils-js`）。
  音频地址是应用自己的 `folia-mod://ytm/_media/audio/<id>/<档位>?once=<key>`，每次 `getAudioSource` 都换一把 key；主进程把整首歌下进内存缓冲，再按 Range 应答。网页播放器的文件按 10 MiB 一段依次请求：一次要整个大文件时，音频服务器只按播放速度发（52 MB 的文件实测 40 KB/s）。下载 30 秒没有新数据就判失败，下一次请求重新取流。一个地址只代表一个文件：换路线后文件不同（长度或类型变了）时，旧地址答 503，渲染端换新地址后按时间续播。下载中途失败后，音频元素会对同一个地址重问，约 30 次失败才报错（每次立刻失败时是半分钟）；这些请求距离这首歌上一次取流尝试不足 3 秒时不再问 YouTube（答网络错误，元素继续播已有的部分并稍后再问），所以短暂断网能自己恢复。重问持续 30 秒仍没取到流，之后的重问直接答 503，交给渲染端换地址或跳过。重问停下超过 10 秒（听众切走了，或元素已经报错）就不再算进这 30 秒：之后再用这个地址，会重新问 YouTube。登出、一次浏览器登录被另一次换掉、或被 YouTube 拒绝而删掉时，只作废以账号身份（member 路线）取的缓冲和地址，旧地址答 503：`ultra` 的全部，和 `standard` / `high` 里由 member 路线取的；未登录的网页播放器取的照旧能用。第一次登录不作废任何地址。同一首歌的失败下载 5 分钟内最多换 4 次新的取流答复，之后答 503（元素约一秒内报错，渲染端跳到下一首）；没问成的尝试不计数。取流请求 60 秒没有答复按网络错误处理。某首歌在当前地区不可播时报 `not-playable`（跳过这一首），不报 `region-restricted`（那个错误码会停掉整个队列）。
  音质（2026-10-08）：账号不是会员、或者没有人登录的时候，adapter 只列两档（`playback.audioQualityLevels` 回 `['standard', 'high']`）：音质选项在 YouTube Music 下只有 `standard` 和 `high` 两个按钮，存着的偏好是 `ultra`、`lossless` 或 `hires` 时亮的是 `high`，交给主进程的也是 `high`。会员多出来的一档在下一段。档位随 `audio` 操作交给主进程（参数 `quality`），由 `ytmApiBridge.cjs` 的 `pickAudioFormat` 选格式：`high` 取原声轨里码率最高的一种，itag 774 和 141 除外：这两种是 `ultra` 的，会员账号不论按哪一档去要都会被给到，除掉它们，`high` 不论由哪条路线取都是同一份文件（一首歌只给了这两种时照取）；`standard` 取 itag 250（Opus，约 64 kbit/s），没有它时取 40 kbit/s 以上的 Opus 格式里离 64 kbit/s 最近的一种（一种 Opus 都没有时在全部格式里取），只给了一种格式时两档都是它。“先取原声轨（不要配音、不要响度压缩的那一种）”对两档都成立。实测（未登录，一个公开视频）给的是四种纯音频格式：itag 249 Opus 约 48 kbit/s、250 Opus 约 64、251 Opus 约 130、140 AAC 约 130。主进程的内存缓冲按“歌曲 id + 档位”存，地址里带档位，所以在一档缓冲过的歌换另一档去要时会重新取流、重新下载。日志 `[Ytm] Plan for <id> at <档位>: the <路线> route, itag <n> at <码率> kbit/s` 写出每次选中的格式，渲染端的 `[Ytm] Audio for …` 一行也带档位和格式。2026-10-08 用应用自己的桥、未登录、同一个公开视频各要一次：`standard` 选中 itag 250（61 kbit/s），地址交出的文件 1,628,559 字节；`high` 选中 itag 251（129 kbit/s），3,433,755 字节；两个文件不同。两档的差别还没有在应用里听过。媒体缓存（共享代码，所有不自己存文件的平台都一样；2026-10-08 改，只跑过单元测试，还没有在应用里试过）：整首播完的歌、和自动混音分析时整首读下来的歌（都要开着“缓存歌曲”）存进媒体缓存时，旁边记下这份文件取自哪一档（键 `audioLevel_<歌曲键>`，档位是交出那个地址时去要的那一档，不是存的那一刻选项停在哪）。播放只用和当前选项同一档的那一份：存着的是另一档时不播它（日志 `[Cache] Copy of <歌曲键> passed over: fetched at <档位>, asked for <档位>`），照没有缓存的歌那样取地址播放，这首歌播完后用这一档的文件盖掉原来那一份（新文件得是整首歌才盖，规则在下面 `resourceCache.ts` / `resourceKeys.ts` 一条）。记档位之前存下的文件没有档位，选哪一档都照旧播它。自动混音分析和人声分离不看档位，存着哪一份就读哪一份。
  超高档 `ultra`（2026-10-09；只跑过类型检查和单元测试，没有在应用里试过，写这部分代码时没有向 YouTube 发过请求）：YouTube Music 给会员多两种约 256 kbit/s 的格式，itag 774（Opus）和 itag 141（AAC），都标着 `AUDIO_QUALITY_HIGH`（实测 2026-10-09，一个账号的一首歌；同一个请求在这个账号成为会员之前没有这两种）。这一档只在登录的账号是会员时列出（`ytmProvider.ts` 的 `audioQualityLevels` 是一个 getter，读 `ytmAccount.ts` 记下的“是不是会员”），顺序排在 `high` 和 `lossless` 之间，界面上叫“超高”；列出时，存着的偏好是 `lossless` 或 `hires` 亮的也是它。`pickAudioFormat` 在这一档只取标着 `AUDIO_QUALITY_HIGH` 的 itag 774，没有时取 itag 141，都没有就算这一档没有，不拿别的格式顶替。取流走 member 会话：浏览器登录的同一份 Cookie、同一个浏览器名、同一个 `guardAccountHeaders`，另外加载播放器脚本；它以 YouTube Music 网页播放器的身份问 `/player`，带一枚和未登录时一样生成的令牌。member 会话的请求是唯一带着账号 Cookie 的取流请求：按 `ultra` 去要时只对存着的会员账号发；按 `standard` / `high` 去要时，未登录的网页播放器没取到而且有人登录才发，不看是不是会员（日志 `[Ytm] Plan for <id> at <档位>: the member route, itag <n> at <码率> kbit/s, <毫秒>ms (web: <原因>)`）。给 `standard` / `high` 当后备这件事，没有在真实账号上对游客被拒的歌量过。音频文件本身和未登录的网页播放器一样下载：用应用自己的 fetch 请求格式自带的地址，请求头只有 Range，账号的请求头到不了 googlevideo.com（这个会话自己发往别的域名的请求，`guardAccountHeaders` 也会把账号的四个请求头摘掉）。不向 YouTube 上报播放。成功时的日志是 `[Ytm] Plan for <id> at ultra: the member route, itag 774 at <码率> kbit/s`。
  取不到这一档就照实按 `high` 给：没有人登录、存着的账号不是会员、member 路线被拒绝或出错、答复里没有这一档的格式，这首歌都改按 `high` 取（先问未登录的网页播放器，取不到再问 member 路线；日志 `[Ytm] No plan for <id> at ultra after <毫秒>ms (member: <原因>)` 和 `[Ytm] <id> is served at high in place of ultra`），并且处处当作 `high` 的那一首：内存缓冲存在“id + `high`”下（和直接按 `high` 去要的是同一份，不重新取流），地址里写的是 `high`，`audio` 的答复多一个 `level: 'high'`（给的档位和要的不一样时才有这个字段），`getAudioSource` 交回的 `quality` 是 `high`，渲染端日志写 `at ultra (served at high)`，媒体缓存也按 `high` 记（omni 的例外，见上面 facade 表“播放/歌词”一行）。代价：这样一首歌在选项停在“超高”时每次播放都重新去要，存着的那一份档位不对、不拿来播（取不到地址时仍然播它）。
  账号是不是会员：网页客户端的账号列表不说，读的是 `/account/account_menu` 里的图标（`webPages.cjs` 的 `premiumFromMenu`）。有 `UNLIMITED`（升级会员的入口）就不是会员；没有它而有 `MONETIZATION_ON`（付费会员一项）就是会员；两个都没有、或者答复没有标成是给登录账号的，算没说，存着的不动。这条规则是从一个账号成为会员前后各读一次推出来的，别的账号、别的国家、家庭方案都没有验证过。读的时机：一次浏览器登录确认之后、主进程把它告诉渲染端之前（`web_login_check` 答 `confirmed` 时读，最多等 10 秒，超过就先答、读到后再存）；之后每次取流（`audio` 操作，不管哪一档）时，这次运行里还没读到答案就在后台读一次，不耽误那首歌。读到答案（是或不是）后这次运行不再读；没读到（请求失败、菜单没说、答复不是给登录账号的）就等之后的取流再读，两次读至少隔 5 分钟。读到的写进存着的登录（`user.premium`）。`login_status` 仍然只读存着的、不上网，所以后台读到的变化要到下一次 `login_status`（重启，或者界面再读一次账号）才显示出来。member 路线拿到一首可播的歌的答复、里面却没有这一档的格式时，不改存着的会员标记：这首歌按 `high` 给，同时再读一次账号菜单（同样至少隔 5 分钟），是不是会员只由菜单决定（只有读菜单这一处写 `user.premium`）。这首歌在它那份 `high` 的取流答复还有效期间（没开始下载的 30 分钟内，或缓冲还在）记作没有这一档，再按 `ultra` 去要时不带 Cookie 去问，直接按 `high` 给，日志只有 `served at high in place of ultra` 一行。没有测过会员账号下是不是有歌本来就不给这两种格式（比如用户自己上传的视频）。
  重启之后：渲染端把“登录的账号是不是会员”存在 localStorage（键 `folia_ytm_account`，内容 `{ premium }`；旧版本存的还带 `signIn`，是 `'tv'` 的按不是会员算），模块加载时读回，所以会员在读到 `login_status` 之前要的第一首歌就按 `ultra` 去要；读到 `login_status` 之后以它为准；浏览器登录确认时按 `web_login_check` 答复里的账号记，不另发请求；没有人登录、账号因登录失效离开（adapter 的 `auth.signInRanOut`，由 `account/accountRead.ts` 调）、登出时（请求发出之前删一次，答复之后再删一次），都删掉。主进程走不走 member 路线只看它自己存着的登录，不看渲染端怎么说。

首单曲（那个位置上现在是另一栏），旁边单曲那一栏取回 6 张专辑；不重读页面时，同一个 token 在三分多钟里反复取，每次都是同样的条目。所以契约规定（`OnlineExploreProvider`）：游标只在页面下一次从头读之前有效。YouTube 的适配层（`ytmExplore.ts`）给每个发出去的游标带上“第几次从头读”的编号，拿旧编号的游标来问一律答“没有了”，不发请求。做法因此是：“换一批”平时不重读页面。每一栏显示自己排在当前这批后面的那些（已经读到的直接用，不够一批时用这一栏自己的游标再读一次），排到最后一个之后从头再来；续页读失败的栏这次不变，下次再试。同时最多三栏在读续页。只有当这一次换不出任何“从上次读页面以来没显示过”的条目时（每一栏都排到过头了），才把页面从头重读一遍，读到原来读到的那一页为止（一页一次请求，遇到没有可显示内容的页最多连读三页）：旧游标全部作废（重读失败时页面还留着旧游标，YouTube 的适配层对它们一律答“没有了”，再按一次“换一批”重读成功后恢复），每一栏换成平台现在在这个标题下给的条目和新游标，重读到的页面里没有的栏继续轮换自己已经读到的条目。栏目按标题对应；同一个标题有好几栏时，各自对应和自己已读条目重合最多的那一栏。没有别的可换的栏保持原样，不翻：只有一批条目、平台给回来的还是这一批的。用“更多”全部展开的栏，“换一批”时收回成一批、从头排起。续页读到的都是已经有的条目、但又给了下一个 token 时，这次不变，下次从那个 token 接着读。往下滚时读到的后面几页的栏目不会因为“换一批”被拿掉，所有栏目也都不换位置（即使应用记住的标题先后和现在站的顺序不一样）；所以列表不会变短，停在原来滚到的位置。重读时平台给的、页面上还没有的栏目加在最后（标题每次都换一种说法的栏目因此会每重读一次多一栏，这次会话里不会减少）；往下读到的某一栏如果页面上已经有了（标题相同、条目多半相同），不再放第二份。每一栏的条目是有限的（TV 客户端的页面上实测有续页的栏 8 到 30 多个）：换一到五次就全部显示过，之后只能轮换，直到 YouTube 自己更新推荐。第一栏换到条目较少的一批时高度不变（窗口宽 1024 56 像素内渐隐（列表的 `mask-image`，渐隐的长度随滚动从 0 长到 56），所以别的栏标题行右端的按钮经过它下面时是变淡的（没有完全消失：只有最上沿才全透明）。替换时栏目本身不动：界面按标题认栏目（每次读到的栏目 id 都是新的，页面上的栏目沿用第一次读到时的   界面怎么动都写在 `src/components/app/home/explore/exploreMotion.ts`（用 framer-motion）：第一次看到的页面一栏接一栏升起，栏里的条目从右依次进入；“更多”按下后先在原位留出占位（横排 4 个；第一栏在列表末尾留一列 5 个）并把占位滚到开头（已经滚到头就不动），读到的条目再填进去（第一栏只为占位滚动：刚在这里播放的歌是不请自来加进列表的，那时不滚）；应用设置里关掉界面微动效（`uiMicroMotion`）时全部改为原地淡入。横排里移动的是卡片，不是它占的格子：横排停靠在格子边上，格子自己一动，横排会跟着滚。页面第一栏（`ExploreLead.tsx`）的高度不随条目数变：第一个条目放大，其余的在它右边按一列 5 行排成多列。列表够宽（704 像素起，也就是窗口 1200 像素宽起；窄于 1024 时列表在大条目下方，768 起）时一屏两列，否则一屏一列，每列正好占满，所以列表停在哪儿看到的都是整列，滚到尽头也是；只有一列时它占满整个宽度。看不见的列横向滚动去看，和别的栏一样用标题旁的左右箭头，但两端不做渐隐（没有露出半截的条目）（原来“更多”要来的条目排在下方，按一次多一块，条目多了这一栏越来越长）。这个列表停靠在每一列的列头上，列头是按位置放的空元素（`data-explore-post`），不是歌：停靠点如果是某一行歌，刚播放的歌把它往后挤一格，列表就跟着它滚走（实测：连着记 30 首，列表自己滚到了末尾）。所有条目都画出来，不在视野里的也画：开发版实测（2026-10-07，无头 Chromium），主页回到屏幕上到这一栏画完，8 首 43 毫秒、60 首 78 毫秒、300 首 384 毫秒；300 首时记一首新歌有一帧 144 毫秒。只画看得见的几列能省掉这些，没有做。
  应用自己的两栏（`src/components/app/home/explore/` 的 `ownSections.ts`，读 `recentPlays.ts`，由 `useRecentPlaysRecorder.ts` 写）：探索页最前面是“最近播放”和“再听一次”，都只来自在本应用里播放过的这个平台的歌，和账号在平台官方应用里听过什么无关，各平台一样。播放记录按平台、按账号分开，同一首歌只有一条 `{ song, at, heardAt, days }`：`at` 是最后一次播放的时间，`days` 是每天听过几次（`[第几天, 次数]`；一天从凌晨 4 点算起，按本机时区，所以听到后半夜的一晚算一天），`heardAt` 是最后一次算作“听过”的时间；最后一次播放之后留 30 天，每个账号最多 300 首（localStorage 键 `folia_recent_plays`，只存在本机）。“播放过”和“听过”是两回事，由 `useRecentPlaysRecorder.ts` 分别上报：一首在线平台的歌真正响够 5 秒算播放过（暂停和拖动进度不算），进“最近播放”；响够它的一半（最长按 4 分钟）才算听过一次，之后每再响够一整首再算一次，所以单曲循环、拖回开头重听都会接着算（单曲循环用的是音频元素自带的循环，歌没有换，应用不会重新开始跟踪它，只能靠累计响了多久来数）。歌的长度先看正在播的音频自己的长度，没有时看歌曲信息里的，都没有按 4 分钟；不到 10 秒的按 10 秒算。“最近播放”是其中最近 7 天内播放的，最新的在前。“再听一次”是最近 30 天里听过不止一次的，最多 30 首，按分量排：一天里听 n 次的分量是 log2(1+n)（1 次 1，2 次约 1.6，3 次 2，30 次约 5），每过 7 天减半，各天相加；分量一样时后播放的在前。这样算是为了两件事。一，只听几秒就切走的歌不算数：原来响 5 秒就算一次，切走两次的歌也会进这一栏。二，某一晚循环很多遍的歌不会一直排在最前：一晚听 30 遍的歌，和从那天起每天听一遍的歌相比，第 4 天起排到后面。同一次收听只算一次。同一次收听里一首歌可能被重新跟踪不止一次（播放器把它换到另一个播放槽、自动混音的过渡被取消、窗口在歌放到一半时重建，都会从零再数），而记录收到的东西分不出这些和“又放了一遍”，所以按时间算：距离上一次算它听过还不到这首歌的长度（上报这次收听时用的那个长度，随上报一起交给记录），它不可能已经放完一遍，算同一次收听，不加次数。同一次跟踪里接着响满一整首的那些（循环、拖回去重听）由上报的一方标明，不受这条时间规则限制。代价有三个。一首歌听过一半后切走、不到一首歌的时间又切回来再听一半，只算一次。长歌更明显：超过 8 分钟的歌听够 4 分钟就算一次，而这条规则看的是整首歌的长度，一小时的合辑一晚上分三次听，只算一次。单曲循环中途被重新跟踪（窗口重建、换播放槽）时，之后少算一次。歌的长度是每次检查时现问的：一开始不知道、后来音频报出更短的长度时，之前少算的收听在接下来几次检查里补上，每次检查最多上报一次。超过 300 首时去掉的是最久没播放的，不看听过几次。过了 30 天没播放的歌在读取时、下一次记录时去掉；30 天以前的收听不再算数（存着的在这首歌下一次被算作听过时去掉）；过了 7 天的在应用开着的时候下一次显示“最近播放”时从这一栏里去掉。早先的记录不带时间（存的是歌本身），第一次读到时按那一刻播放的算，并立刻带着时间存回去，免得每次启动都重新算；不带 `days` 的记录（当时数的是响够 5 秒的次数）按没有听过算。这两栏不属于平台的页面：“换一批”不动它们；歌全部在栏里，没有“更多”；平台的页面正在读、读不到、是空的时候它们都照样显示，平台页面的状态（转圈、重试）在它们下面。平台不一定知道这里放了什么（应用不向 YouTube Music 上报播放），它自己的收听记录也不进这两栏。YouTube Music 的页面上有它自己的这类栏，`ytmExplore.ts` 把它们去掉；它们除了标题没有别的标识（这一句里的实测都是 2026-10-07 在应用已不再使用的 TV 客户端的“音乐”页上做的，网页客户端的首页用不用同样的标题没有量过：和别的栏结构完全一样，翻页 token 里也只有栏的位置不同），所以靠标题认（`LISTENING_RECORD_HEADINGS`；实测 2026-10-07 中文页是“最近播放的音乐”“再听一遍”“老歌重温”，英文页是“Recently played”“Listen again”“Forgotten favorites”，按印尼语要的页面给的是英文标题）。“老歌重温”是 YouTube 按账号以前常听、近来不听的歌排的，同样出自它自己的收听记录，所以一并去掉；应用自己没有对应的一栏。YouTube 改了标题就认不出，那一栏会留在页面上。
  电台页（2026-10-08 接上，`client/ytmRecommendations.ts`，能力 `recommendations: true`；**还没有在真实账号上跑过**，下面写的是代码和单元测试保证的行为）。私人 FM：一个接一个的“歌曲电台”（桥接操作 `mix`，列表 id 是 `RDAMVM` + 歌曲 id，以 guest 身份读，约 50 首；种子和读电台的函数在 `client/ytmRadio.ts`，和探索页“与某首歌相似”的栏共用）。种子是账号“喜欢的音乐”列表（`LM`）的第一页（一次请求，100 行，不翻页），加上探索页最近一次从头读时交来的 `listened`（`getPersonalFm` 拿不到 `listened`，所以本次运行里没打开过探索页时只有列表里的歌）。每次从还没用过的种子里随机取一首：同一首歌的电台每次都是同一份歌单，按固定顺序取的话每次启动都从同样的歌开始。`getPersonalFm()` 每次交出接下来的 2 首，一次运行里一首歌只交出一次，种子本身不交出；一个电台用完换下一个种子，种子和最后一个电台都用完时重读一次列表。`dislikeSong`（FM 的垃圾桶）不通知 YouTube：这首歌本次运行不再交出，它所属电台剩下的歌整个丢掉。一个种子都没有时不交歌，首页就不出 FM 卡片；列表读不到（离线除外）按没有它处理，电台页其余部分照常。FM 页有红心：`FmTab` 只对所属平台没有喜欢功能的歌不画红心（按当前歌曲问 `omni.canLikeSong`）。每日推荐：不提供（没有 `getDailySongs`，`omni.supportsDailySongs` 为假，卡片不出现），YouTube Music 没有对应的列表，也不拿别的东西充数。推荐歌单：探索页第一页上的歌单和合辑（去掉 YouTube 自己的收听记录栏，同一个列表只出现一次，专辑和歌手不算），取自探索页最近一次从头读到的第一页，不再向 YouTube 要一次（`ytmExplore.ts` 的 `ytmMusicPagePlaylists`；不管那一页是多久以前读的，因为在这里从头重读会让探索页手里的游标全部作废）；本次运行里还没读过时才在这里读一次，这一次同样算一次“从头读”。登出和开始登录时，FM 的状态、记下的 `listened` 和这一页都清掉；换界面语言时只清这一页。
  喜欢（2026-10-09 接上；只跑过单元测试，没有在应用里试过，`/like/like` 和 `/like/removelike` 也还没有以网页客户端的身份真的发过）。能力 `likes` 是固定的 `true`，和其他有喜欢功能的平台一样；没有人登录时红心照样能点，请求被拒（`auth-required`），状态栏提示“添加失败”。`ytmAccount.ts` 记的“是不是会员”跟着账号走：读登录状态时记；浏览器登录确认时按 `web_login_check` 答复里的账号记，不多发请求；账号离开时（没登录、登录被拒、登出）`account/accountRead.ts` 先让 adapter 清它（`auth.signInRanOut`、`auth.logout`）再清 store；登出请求答复后再清一次。点红心走 `ytmMutations.likeSong`，桥接操作 `song_like`（参数 `id` 是视频 id，`liked` 是 `'true'` 或 `'false'`）：主进程以网页客户端的身份发 `/like/like` 或 `/like/removelike`，内容是 `{ target: { videoId } }`，这是 YouTube Music 自己的喜欢，歌进“喜欢的音乐”。答复里没有成败字段，所以只有带“已登录”标记（`logged_in` 为 `1`，和登录时的要求一样）的答复才算做成，不再读列表确认；标记是 `0` 的由 `withWeb` 再问一次账号，没有标记、是错误内容或没有内容的报 `unavailable`，记 `[Ytm] The answer to <接口> is not marked as given to the account; the change is not taken for made`（`list_save` 和 `playlist_edit` 的写请求同样要求这个标记；写请求的真实答复带不带这个标记还没有测过）；每次记一行 `[Ytm] Song <id> liked` 或 `no longer liked`。`song_like` 没登录报 `auth-required`。哪些歌的红心是满的：`ytmLibrary.getLikedSongIds` 用已有的桥接操作 `playlist` 把“喜欢的音乐”（`LM`）一页一页读到底（网页客户端一页 100 首），最多 50 次请求（5000 首），到 50 次还没读完、或者翻页 token 重复时记一行警告，结果标成没读全（`whole: false`），这次读取只加红心、不灭红心，后面的歌红心保持原样；读到底时记 `[Ytm] Liked songs: <首数> read in <次数> request(s)`。回到窗口、进入主页时要的数目（`ytmLibrary.getLikedSongCount`，2026-10-17，只跑过单元测试，没有用真实账号试过）：用同一个桥接操作 `playlist` 重新要这份列表的第一页（不走 `libraryPager` 的缓存），取页头第二行写的首数（`main/webPages.cjs` 的 `playlistCountOf`，和歌单卡片的首数用同一个解析 `countIn`）；页头没写首数时答 null，这两个时机就不读。每次记一行 `[Ytm] Liked songs count: <首数>`，没写首数时是 `the page names none`。页头的字段是照 ytmusicapi 读的写的，还没在真实页面上看过。`account/accountRead.ts` 每次读账号时读一次，和账号、歌单一起存进快照：读失败时音乐库照常显示，红心保持原样；读到的列表和读的途中点过的红心由 omni 的那条规则对账（上面“修改”一行），hook 自己不写 `likedSongIds`。刚读到的歌单先显示出来，不等这份列表读完（它可能要几十次请求；读一次要多久没有测过）。在“喜欢的音乐”这份歌单里删歌就是取消喜欢（`GridView` 走 `omni.likeSong(track, false)`），所以能从里面删歌；它仍然不在“添加到歌单”的目标里（`canAddToPlaylist`），歌只靠红心进出，和 Spotify 一样。
  收藏专辑和别人的歌单（`client/ytmMutations.ts` 的 `subscribeAlbum` / `subscribePlaylist` / `canSubscribe`、`client/ytmCatalog.ts` 的 `getSubscriptionStatus`，桥接操作 `list_save` / `list_saved`）：收藏就是对列表 id 点赞（专辑是 `OLAK5uy_…`，歌单是它自己的 id），随后它出现在 YouTube Music 音乐库的“专辑”或“歌单”里，取消则消失。是否已收藏读它的页面（专辑带 `albumId` 时读专辑自己的页面 `MPRE…`，否则读 `VL<列表 id>`，见本段后面“读哪一页”）上的收藏按钮。YouTube 应答请求时改动还没生效（实测 2026-10-07，用的是应用已不再使用的 TV 客户端：专辑约 1.5 秒后页面才显示新状态，歌单要 4 到 4.6 秒），所以 `list_save` 发完请求后每 500 毫秒读一次页面，读到新状态才算完成，最多读 20 次，否则报 `unavailable`；某一次读失败算作没读到。界面不等这个过程：星星按下就显示新状态，请求在后台走（`src/library/core/collection/mutations/collectionSaves.service.ts`），失败时星星回到平台最后确认的状态并在状态栏提示（`unavailable` 是 20 次内没读到新状态，或者赞的答复没带“已登录”标记；两种情况改动都可能已经生效，重新打开这一页会读到真实状态，再按一次时页面已经是这个状态就不再发请求）；请求没答复前再按，等这一次答复后，最后想要的状态和刚做成的不同才再发一次，失败的那一次如果已经被按回去就不提示。页面上有不止一个收藏按钮、写的目标又不一样时，不知道哪个是这一页自己的，按没写目标处理。打开页面时读到的“是否已收藏”如果是在一次改动之前或途中问的，改动结束后才答复，就不用它（`collectionSaveReadIsCurrent`）。改动和读取分两次以账号身份执行（两次 `withWeb`）：读取途中登录不被认时，改动不会重发。这样紧接着刷新的音乐库列表读到的就是改动后的。一张专辑有不止一个列表 id：音乐库卡片带的和目录专辑页（`MPRE…`）地址里的不同。读状态和改动用同一个：目录专辑一律用专辑页地址里的那个（实测过用它读和写），卡片自带的不用（只实测过专辑已收藏时用它读到“已收藏”）；专辑本身的 id 就是列表 id 时直接用它。发改动前 `list_save` 先读一次页面，赞发给页面上收藏按钮自己写明的目标（`webSaves.cjs` 的 `saveCommandOf`），不是一律发给页面的 id：TV 客户端探索页上专辑卡片的页面，按钮写的是目录专辑页的那个列表 id，把赞发给卡片自己的 id，YouTube 应答 200 但什么都不变（实测 2026-10-07，用的是应用已不再使用的 TV 客户端：40 秒后页面仍是“未收藏”，音乐库里也没有；改发按钮写的目标后 1 次读取就显示，音乐库多出这张专辑）；歌单页面的按钮还带一段参数（`likeParams` / `removeLikeParams`），一并发出。页面已经显示想要的状态时不发请求，直接算完成，记 `[Ytm] List <id> is already in the library; nothing was sent`（取消时是 `out of`）。按钮没写目标时，读的页面是这个列表自己的页面（`VL<列表 id>`）才用列表 id，并记一行警告；读的是专辑自己的页面（带 `albumId`）时什么都不发，报 `invalid-response`，记 `[Ytm] The save button on the album page of list <id> names no like; nothing is sent`。页面上没有收藏按钮（自己建的歌单就没有）或页面读不到时什么都不发，直接报错；“喜欢的音乐”（id `LM`）按 id 拒绝。界面上出不出现收藏按钮由 `canSubscribe` 按卡片决定：专辑都出现；歌单要不是 `LM`、不是合辑、没有标为自己的。“自己的”这个标记只有音乐库的卡片带，探索页上如果出现自己建的歌单，按钮会出现，点了由上面那一步拒绝。合辑（探索页上 id 以 `RD` 开头的卡片）没有页面（读 `VL<id>` 得 400），对它发收藏请求后音乐库的歌单里也不出现（实测一张 `RDEM` 合辑，4.5 秒后仍没有；这两条都是用应用已不再使用的 TV 客户端测的，网页客户端没有测过），所以不提供。收藏后的歌单在音乐库歌单里的卡片 id 就是收藏时用的 id，不标为自己的。这两个操作走网页客户端（2026-10-09 接上；只跑过单元测试，没有在应用里试过，网页页面的结构是实测的，`/like/like` 和 `/like/removelike` 还没有以网页客户端的身份真的发过），步骤合起来是：先读页面，赞发给收藏按钮写明的目标（带上按钮的参数；没写目标时歌单用列表 id 并记警告，专辑不发、报 `invalid-response`），赞的答复带“已登录”标记才往下走（否则报 `unavailable`），再每 500 毫秒读一次页面，读到新状态才算完成，最多 20 次。请求经 `ytmApiBridge.cjs` 的 `withWeb` / `browseWeb` / `changeWeb` 发，读哪一页由 `listPage` 决定，收藏按钮由 `webSaves.cjs` 找。读哪一页：网页客户端按专辑的列表 id 读（`VL` + `OLAK5uy_…`）只给歌曲行，没有页头，也没有收藏按钮（实测 2026-10-09），专辑的按钮只在专辑自己的页面（`MPRE…`）上。所以专辑有目录页 id 时，渲染端把它和列表 id 一起发来（两个操作的可选参数 `albumId`，`ytmCatalog.ts` 的 `ytmAlbumSaveParams`）：有 `albumId` 读专辑页，没有读 `VL<列表 id>`（歌单都是后者）。只有列表 id 的专辑读不到按钮，两个操作都报 `invalid-response`，句子和没有收藏按钮的页面一样；音乐库和探索页给的专辑都带 `MPRE…` id（`webPages.cjs`、`webExplore.cjs` 只认这种）。怎么找按钮（`main/webSaves.cjs`）：页头（`musicResponsiveHeaderRenderer`）的 `buttons` 里按下去是“对一个列表点赞”的那个开关，它的 `isToggled` 就是是否已收藏（实测 2026-10-08 和 10-09：专辑页和别人的歌单页各有一个，图标是 `BOOKMARK_BORDER` / `BOOKMARK`；别人的歌单页上按钮写的目标就是这份歌单的 id，不带参数）。页头里展开简介的开关、每一行歌自己的喜欢按钮都不算。按钮上的内容怎么读（目标、参数、几个按钮不一致时按没写处理）在 `tiles.cjs` 的 `savedStateOn` / `saveCommandOn`。“喜欢的音乐”的网页页面上没有收藏按钮（实测 2026-10-09），仍然先按 id 拒绝。自己建的歌单的网页页面没有实测过，代码按“没有这样的按钮”处理。确认改动的读取途中，某一次答复是按游客答的：不再往下读，由 `withWeb` 再问一次账号（账号还认就报 `unavailable`，登录留着），改动不会重发。
  歌单增删（桥接操作 `playlist_edit`）只对账号自己建的歌单开放。音乐库卡片的菜单里有“编辑”或“删除”项才标 `isOwned`（`webPages.cjs`），不读账号名。添加带去重选项，已在歌单里的歌不会多出一份；删除按行（2026-10-09）：以账号身份读歌单时（`playlist`），每首歌带着页面给它这一行的编号（原始数据里的 `playlistItemData.playlistSetVideoId`，`webPages.cjs` 的 `playlistRowsOf` 按页面顺序读，只读歌单自己那一栏和续页追加的行，页面上别的列表不算；页面没给编号的行就没有编号，不会拿同一首歌下一行的顶上；答复里是歌曲的 `setVideoId`，渲染端放在歌曲的 `collectionRowId` 上）；删的时候编号连同歌曲 id 一起送回（`playlist_edit` 的参数 `setVideoIds`，和 `videoIds` 一一对应，没有编号的位置是空串），主进程对有编号的发 `ACTION_REMOVE_VIDEO`（`setVideoId` 加 `removedVideoId`），只删这一行，歌单里同一首歌的另一行留着，`GridView` 也只拿掉这一行（后面的页并进列表时，带行编号的歌按“歌曲加行编号”去重，所以同一首歌的两行都显示；没有行编号的仍按歌曲去重）。没有编号的歌（以 guest 身份读到的、更新前存下的列表里的）仍按歌曲 id 删（`ACTION_REMOVE_VIDEO_BY_VIDEO_ID`），会删掉所有副本，`GridView` 也把它们都拿掉。读歌单第一页时记 `[Ytm] Playlist page: <首数> song(s), <个数> with the id of their row`，改动成功时有编号的记在 `[Ytm] Playlist change: remove <首数> song(s), <个数> by the id of their row`。“喜欢的音乐”不在可添加的歌单里；桥接层按 id 拒绝 `LM`、`LL`（赞过的视频）、`WL`（稍后观看），报 `invalid-response`，什么都不发。从歌单里删歌失败时状态栏提示“移除失败”（`home.removeTrackFailed`），任何歌单都一样。每次请求最多改 100 首。请求是 `/browse/edit_playlist`（`playlistId` 和 `actions`），以网页客户端（`YTMUSIC`）的身份、经 `withWeb` 发（2026-10-09 接上；只跑过单元测试，这个请求还没有以网页客户端的身份真的发过）。成功要看答复里的 `status` 是不是 `STATUS_SUCCEEDED`（答复还得带“已登录”标记，没有就报 `unavailable`）；状态词不对时报 `unavailable`，日志记下 YouTube 给的状态词（`[Ytm] Playlist change refused: unavailable (<状态词>)`）；请求本身被拒（比如状态 400）时报 `invalid-response`，日志是 `[Ytm] playlist_edit failed: …`。日志里不写歌单 id。网页客户端认不认按歌曲 id 删除（`ACTION_REMOVE_VIDEO_BY_VIDEO_ID`）和这个去重选项（`DEDUPE_OPTION_DROP_DUPLICATE`），还没有测过，上面“不会多出一份”“删掉所有副本”两句是用应用已不再使用的 TV 客户端实测的。按行删除也没有测过：行编号这个字段没有在真实页面上看过，`ACTION_REMOVE_VIDEO` 没有真的发过；字段是 youtubei.js 和 ytmusicapi 读的那一个，请求是 ytmusicapi 发的那一个。
