# 洛雪音源（`lxmusic`，仅桌面端）

让用户导入洛雪音乐（LX Music）的「自定义源」脚本来取播放地址的音源模组（Folium 2.0）。它是独立的一家音源：自己搜歌、
列歌单与榜单，歌都算 `lxmusic` 自己的；不接管别家平台的歌，也不读别家的登录和数据。
构建、布局和依赖的规矩见 `dev/sources/README.md`。

**不随应用带任何脚本，也不内置脚本的下载地址。** 脚本是第三方代码，来源由用户自己负责；没导入脚本时这家音源答「没配好」，
一个请求都不发。它默认停用（清单 `sources[].offByDefault`），开箱引导里不预先勾选，启用处显示清单 `sources[].enableNotice` 的说明。

最初的接入是 PR #1177（作者 baixiao0919）：脚本接口的行为（回调的几种写法、`lx.utils` 的实现）、四个平台公开接口的
请求与字段都取自那里的实测，这里换了运行方式（沙箱窗口加受控出口）和形态（独立音源，而不是别家歌单加洛雪取流）。

- **上游**：两样，都没有要装的包。
  1. 洛雪桌面版给自定义源的接口（`globalThis.lx`：`on` / `send` / `request` / `utils` / `EVENT_NAMES` / `currentScriptInfo`，
     仓库 lyswhut/lx-music-desktop 的自定义源说明）。我们实现的是其中脚本取地址要用的那部分，见下面「没做的」。
  2. 四个平台的公开网页接口（酷我 `kw`、酷狗 `kg`、QQ `tx`、网易云 `wy`），地址写死在 `main/catalog.ts`。没有官方文档，
     会随平台变动。
- **版本**：`lx.version` 报 `2.0.0`、`lx.env` 报 `desktop`。本目录的 `package.json` 没有依赖。
- **我们改了什么**：不是移植洛雪的代码，是照它的接口重写的运行环境。`lx.utils.zlib` 的 `inflate` / `deflate` 用页面的
  `DecompressionStream` / `CompressionStream`，回的是 Promise（洛雪里是回调或 Promise 两种都有的写法，脚本一般 `await`）。
  `updateAlert` 事件不弹窗、不开它带的链接。
- **上游变了怎么跟**：平台接口变了改 `main/catalog.ts` 里那一家的请求和归一化，`test/unit/lxmusic/scriptsAndCatalog.test.ts`
  用写好的答复管归一化，抓不到平台换了答复的样子，要在应用里试。洛雪给脚本加了新接口时改 `main/sandbox/runtime.ts`，
  `test/unit/lxmusic/sandboxRuntime.test.ts` 管接口的行为（`lx.utils` 与 Node 自带实现逐项对照）。

## 怎么用

命令面板（也出现在模组面板里这个模组的那一行）：

| 命令 | 什么时候有 |
| --- | --- |
| 导入自定义源脚本… | 一直有。选一个脚本文件（`.js`，也认 `.json`、`.txt`），单个最多 2 MB，最多存 16 个 |
| 切换自定义源脚本 | 存了不止一个脚本时。一次只用一个，和洛雪桌面版一样 |
| 移除自定义源脚本 | 有脚本时 |
| 切换搜索平台 | 当前脚本声明了不止一家平台时。一次搜一家 |

脚本原文、清单、当前选择存在模组自己的 `api.storage`，不碰 localStorage。歌曲 id 是 `<平台键>:<平台的歌曲 id>`
（`kw:123`、`tx:<mid>`），歌单、榜单、专辑是 `<平台键>:<p|c|a>:<id>`。

## 对应歌曲

洛雪的歌 id 就是 `<平台键>:<平台自己的 id>`，所以网易云、QQ、酷狗三家内置音源的歌可以只凭 id 换成洛雪的歌
（`songs@1.counterpartSources` / `getCounterparts`，实现在 `client/lxCounterparts.ts`）。把这三家的歌单转存成 Folia 歌单时选
「改由洛雪音源播放」，用的就是它。

| 来源音源 | 用它的哪个值 | 洛雪的歌 id |
| --- | --- | --- |
| `netease` | `id`（数字歌曲 id） | `wy:<id>` |
| `qq` | `id`（songmid）；`publicId`（数字 songid）一并记进 `data.songId`，有些脚本要 | `tx:<songmid>` |
| `kugou` | `id`（歌曲 hash，转成小写） | `kg:<hash>` |

- 只按 id 换算，不发请求、不搜索：id 的样子不对就答没有（QQ 的歌没有 songmid、酷狗的不是 32 位 hash），不按歌名歌手去找。
- 只答当前脚本支持的平台（脚本取不了某家的地址，换过去也播不了）。没有脚本时三家照样声明，但宿主看到音源没配好不会来问
  （界面上能提示去导入脚本），真问了也全答没有。
  换了脚本、支持的平台变了，client 入口会调 `handle.changed()`。
- 答出来的歌带着传进来的歌名、歌手、专辑名、封面、时长；专辑和歌手打不开页面（没有它们的 id）。
- 酷我没有对应的内置音源，所以不在表里。
- 换过去的 QQ 歌没有 `mediaMid`、`albumMid`，酷狗歌没有 `audioId`（这些在来源音源自己的 `data` 里，不给别的音源看）。
  脚本拿到的 `musicInfo` 里这几项是空的；要它们才能取地址的脚本，这首歌会播不了，按平常的播放失败处理。

## 隔离（改这里的代码前先读）

脚本是不可信的第三方代码。它跑在模组自己的隐藏沙箱窗口里，联网只有一条路：

1. **窗口**（`main/sandboxHost.ts`）：`api.windows.hidden` 开的沙箱渲染进程，上下文隔离、没有 preload、没有 Node，所以页面里
   没有 `window.electron`。分区是受信表认领的内存分区 `folia-lxmusic-sandbox`，和宿主、别家音源的会话分开，里面没有任何
   cookie。分区的 http(s) 全部由 `intercept` 在本地应答，其余协议指向一个不存在的代理，权限一律拒绝，禁 WebRTC、开窗、
   跳转和 webview。页面的 CSP 是 `default-src 'none'`，只放行内联脚本、`eval`（混淆过的脚本要用）和对沙箱自己那个假源的
   `connect-src`；再加 `sandbox allow-scripts allow-same-origin`，所以 `alert` / `confirm` / `print`、下载、弹窗、表单都没有。
   窗口静音，分区上的下载一律取消（`will-download`）。
2. **出口**（`main/egress.ts`、`main/egressGuard.ts`）：`lx.request` 是页面里对固定假地址 `https://lx-sandbox.invalid/__lx/request`
   的一次 POST，`intercept` 接住后交给出口。出口用 Node 的 `http` / `https` 加自己的 `lookup`：解析出地址、判过、连的就是
   判过的那个地址，连上后再核对一次对端地址。跳转不自动跟，每一跳重新判（最多 8 跳），跨源时去掉 cookie 与 authorization。
   拦的地址：回环、私网、链路本地（含 169.254.169.254）、`100.64.0.0/10`、`::ffff:` 映射 / NAT64 / 6to4 / Teredo 里包着的
   IPv4、ULA、组播、未指定地址、文档与保留段，字面的 `localhost`、`.local`、没有点的主机名。一个名字解析出多个地址时，
   有一个不许就整个不许。只许 http(s)。
   另外照这台机器的网卡表判：网卡自己的地址（`own-address`）和网卡所在的在链子网（`on-link`）也不许。没有 NAT 的公网 IPv6
   和直接拿到的公网 IPv4 不在任何保留段里，本机上监听全部网卡的服务、同网段的路由器和 NAS 只能靠这一条挡住。
   邮件、IRC 这类不该用 HTTP 去碰的端口不许连。回给脚本的只有拦的原因，不带主机名和解析出的地址。
   `/__lx/request` 的 POST 超过 4 MB 不读进主进程；回答最多 8 MB（按解压后算）。请求的个数和快慢见下面「限制」一节。
3. **音频**：脚本给的地址不交给主窗口。播放器拿到的是 `folia-mod://lxmusic/_media/stream/…?once=<令牌>`（`api.media.serve`），
   由同一个出口带 Range 转发；回的不是音频（只认 `audio/*`、`video/*`、`application/ogg`、`application/octet-stream` 和没写类型的）、
   状态不是 200 / 206、或声明的长度超过 4 GiB 就答 502，没签发过的令牌答 410。令牌在这次运行里 6 小时内有效（播放器要分段取、要拖动），
   名字叫 `once` 是宿主媒体接口的参数名。所以脚本给一个内网地址
   也打不到，CDN 的 302 也跟得上。
4. **曲库**：搜歌、榜单这些请求是模组自己的代码发的，地址写死，走 `api.net.fetch`（默认会话、不带凭据、跟系统代理）。
   脚本碰不到这条路。

几条有意的取舍：

- **出口不走系统代理**。走了代理就看不到解析出的地址，按 IP 的判定也就没了。代价是只能靠代理上网的机器上脚本的请求会失败；
  开着 TUN 的没有这个问题。
- **解析出来的 `198.18.0.0/15` 不拦**（写在地址里的拦，TUN 网卡自己的地址也拦）。它是代理软件 fake-ip 模式的占位地址段：
  拦了，开着 TUN 的用户一首歌都放不了。**代价是这类用户身上按 IP 的判定基本失效**：脚本请求一个 A 记录指向内网或回环的
  域名时，这里看到的是占位地址，真正连到哪由代理软件决定，而常见的规则（私网地址直连）会把它送进内网。也就是说，开着
  fake-ip 的 TUN 时，恶意脚本够得着路由器管理页和本机服务，这里只挡得住字面写出来的地址和本地名字。没有不伤这类用户的
  解法（向固定的 DoH 再问一次真实记录挡得住最简单的那种，挡不住针对性的应答，也没做）；这是导入脚本前要知道的残余风险。
- **没有再套 `sandbox` iframe**。独立的沙箱渲染进程比同进程的 iframe 隔得更开，页面里也没有要瞒着脚本的东西。
- **开发放行**：环境变量 `FOLIA_LXMUSIC_DEV_ALLOW=<主机>:<端口>` 让出口放行一个本机地址，只在从源码跑（`process.defaultApp`）
  时读，打包后的应用不认。桌面实测用它把假音频服务接进来（`test/manual/fakeSourceNetwork/lxmusic.mjs`）。

## 限制（`main/rateLimit.ts`）

脚本是别人写的，所以出口不只管「去哪」，也管「多少、多快、多久」：不让它把这台机器当成发请求的工具，也不让一个不肯结束的
回答占住宿主。数值在 `main/rateLimit.ts` 的 `LIMITS`，下面是依据。正常的脚本取一首歌的地址发 1 到 3 个请求（带重试的到 5 个），
播放器还会预取下一首；连着切十首歌也就三十来个请求，分散在两三个主机上。搜歌、榜单、公开接口的歌词是模组自己发的，不经出口，
不在这里算。

| 限制 | 数值 | 超了怎样 |
| --- | --- | --- |
| 每秒请求数，按目标主机 | 一口气 20 个，之后每秒 2 个 | 等到轮到它；要等超过 10 秒的直接拒绝 |
| 每秒请求数，整个模组 | 一口气 40 个，之后每秒 4 个 | 同上。换着主机名发也绕不过这一条 |
| 音频转发的每秒请求数，按目标主机 | 一口气 60 个，之后每秒 10 个 | 同上，播放器那边答 429 |
| 音频转发的每秒请求数，整个模组 | 一口气 120 个，之后每秒 20 个 | 同上 |
| 同时在途的 `lx.request`，按目标主机 | 4 个 | 排队 |
| 同时在途的 `lx.request`，整个模组 | 8 个，另排队 16 个 | 队满了拒绝 |
| 同时转发的音频流 | 8 条 | 关掉最久没人读的那条 |
| 一条音频流的字节数 | 4 GiB | 断开（声明的 `content-length` 超过的直接答 502） |
| 音频上游不来数据 | 30 秒 | 断开 |

- 每秒请求数是出口里的闸（`createEgress` 的 `gate`），**每一跳过一次**：跳转、音频转发、带 Range 的分段都算。地址先判、
  再过闸，被拦的去处不占名额。等的时间算在这次请求自己的时限里（`lx.request` 最长 60 秒）。
  一直按上限发，一小时是一万四千多个请求，分到一个主机上七千多个：够不上像样的刷量，正常听歌碰不到「之后」那一档。
- 桶有两套：脚本的 `lx.request` 一套，音频转发一套。音频是播放器发起的，脚本把自己的额度用光了也不该让歌放不出来。
  音频那套宽得多：拖动进度条时播放器会连着发带 Range 的请求，每个请求经 CDN 的跳转是两三跳（实测连着二十次读取、
  每次两跳，按脚本那套的数值要等十秒）。脚本催不动播放器，它能左右的只有每个请求跳几次（最多 8 跳）。
- 没等到令牌就被中止的请求（它自己的时限到了、窗口没了）把令牌还回去：不然一串一秒就超时的请求一个都没真发出去，
  却能让桶一直欠着。钟用单调的 `performance.now()`，系统时间往回调不会把桶扣成一大笔欠账。主机名不分大小写，结尾的点不算。
- 脚本的窗口销毁时（换脚本、删脚本、不答、主窗口关掉、模组停下），它还在途和还在排队的 `lx.request` 一起中止，
  不会占着新脚本的名额，也不会在窗口没了之后才发出去。
- 被拒绝时脚本拿到的是 `rate limited (too many requests)` 或 `rate limited (too many requests at once)`，音频那边答 429。
- 4 GiB：一小时的 24 bit / 192 kHz FLAC 大约 2.5 GiB，留了余量。没写 `content-length` 的回答就靠这一条截断。
- 30 秒只在「播放器要数据、上游不给」时计。播放器缓冲够了会停下不读（暂停时也是），那段时间上游是被我们暂停的，不算它慢，
  也就不会因为用户暂停了半小时而断流。断开后播放器那边是一次读取出错，照平常的播放失败处理。
- 记主机的桶最多 256 个，多了丢最久没用的；丢掉的主机下次从满桶开始，所以兜底的是整个模组那一个桶。

## 没做的

- 咪咕（`mg`）：公开接口不稳，PR #1177 里也没有。脚本声明了它也不会出现在平台列表里。
- 脚本的 `pic` 动作：封面用公开接口给的。`lyric` 动作做了，脚本没声明或答不上时退回公开接口的歌词。
- 脚本的自动更新（`updateAlert`）：不弹、不下。要换脚本就重新导入。
- 网页版：没有。脚本要一个能隔离运行第三方代码、又能替它跨域联网的地方，网页版给不了，所以 `src/services/onlineMusic/web/`
  里没有它的文件，网页构建不带这个模组。
- 登录、红心、歌单增删：这家没有账号。
- 窗口空闲回收：没做。脚本的窗口在换脚本、不答、主窗口关掉时才销毁，期间它的定时器一直能跑；它经出口发的请求受
  上面「限制」一节的几道闸管。
